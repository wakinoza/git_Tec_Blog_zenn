## 本文

ユニットテストにおいて、メソッドが想定外の入力に対して正しく例外をスローするかを検証することは非常に重要です。

この記事では、JUnit 5標準の検証方法と、AssertJを用いた例外検証手法をまとめていきます。

テスト対象クラスは、以下の通りです。

```Java
public class Calculator {
    private int total = 0;

    public int divide(int a, int b) {
        if (b == 0)
            throw new ArithmeticException("0で除算することはできません");
        return a / b;
    }

    /**
     * @param a 加算する値 (0以上1,000,000,000以下)
     * @throws IllegalArgumentException 不正な値の場合
     */
    public int add(int a) {
        if (a < 0)
            throw new IllegalArgumentException("負の数は加算できません: " + a);
        if (a > 1_000_000_000)
            throw new IllegalArgumentException("大きすぎる値は加算できません: " + a);
        
        total += a;
        return total;
    }

    public int getTotal() {
        return total;
    }
}
```

上記クラスでは、divideメソッドの第2引数に0が渡された場合と、addメソッドの引数に不正な値が渡された場合に、それぞれ例外をスローします。

## 1\. JUnit標準機能による例外検証

まずは、divideメソッドについて、適切な例外がスローされているかを確認します。
JUnit 5で例外のクラスのみを検証する場合、通常は static import を用いて assertThrows と記述します。

例外を検証するコードは以下の通りです。

```Java
class CalculatorTest {

    Calculator calc;

    @BeforeEach
    void setUp() {
        calc = new Calculator();
    }

    @Test
    @DisplayName("異常系：0で除算すると例外が発生すること")
    void testDivideByZeroException() {
        assertThrows(ArithmeticException.class, () -> calc.divide(10, 0));
    }

    //その他のテストメソッド
}
```

assertThrowsメソッドは、第1引数に期待する例外クラスを、第2引数に例外の発生を期待する実行コードをラムダ式で記述します。
これにより、期待される例外がスローされるかを検証します。

次に、addメソッドを検証していきます。
addメソッドは、不正な値が引数に渡されると例外をスローしますが、値によって例外メッセージが異なります。
例外の型をチェックするだけでは不十分なため、例外メッセージも検証を行います。

assertThrowsは、発生した例外オブジェクトそのものを戻り値として受け取ることができます。
その戻り値を使って、どのようなエラーメッセージが出ているか検証できます。

addメソッドのテストコードは以下の通りです。

```Java

@Test
@DisplayName("異常系：負の数を加算すると例外が発生すること")
void testAddNegativeException() {
  IllegalArgumentException exception =
      assertThrows(IllegalArgumentException.class, () -> calc.add(-1));

  // 例外メッセージの検証
 assertTrue(exception.getMessage().contains("負の数は加算できません"));
}

@Test
@DisplayName("異常系：大きすぎる値を加算すると例外が発生すること")
void testTooLargeException() {
  IllegalArgumentException exception =
      assertThrows(IllegalArgumentException.class, () -> calc.add(1_000_000_001));

  // 例外メッセージの検証
  assertTrue(exception.getMessage().contains("大きすぎる値は加算できません"));
}
```

assertThrowsの戻り値である例外オブジェクトからメッセージを取り出し、assertTrueメソッドで期待されるメッセージと一致しているかを検証しています。
メッセージに入力値が含まれるため、contains を用いて部分一致で検証しています

## 2\. AssertJによる例外検証

実務では、AssertJという外部ライブラリも利用します。
AssertJは、IDEの補完機能と相性が良い「メソッドチェーン」を採用しており、複数の検証を簡潔に記述できます。また、検証に失敗した際のエラーメッセージの情報量が多いため、原因の切り分けが容易になるメリットがあります。

AssertJを用いた例外検証のコード例は、以下の通りです。
assertThatThrownByメソッドを使用すると、例外の型、メッセージ、さらには原因例外（cause）の有無までを一気にチェックできます。

```Java
import static org.assertj.core.api.Assertions.*;


@Test
@DisplayName("異常系：AssertJを用いた例外の詳細検証")
void testAddExceptionWithAssertJ() {
    assertThatThrownBy(() -> calc.add(-1))
        .isInstanceOf(IllegalArgumentException.class)  // 例外クラスの検証
        .hasMessageContaining("負の数は加算できません")  // 例外メッセージの検証
        .hasNoCause();                                  // 原因例外がないことの確認

}
```

上記のテストケースでは、1つのメソッドに、例外クラスの検証・例外メッセージの検証、原因例外がないかどうかまで一度に検証できます。

##  まとめ

-  単に例外がスローされること（assertThrows）を確認するだけでなく、メッセージや原因例外（cause）まで検証することで、意図しない箇所で発生した同型の例外を誤って「パス」として判定してしまうリスクを最小化します。

- JUnit 5標準はシンプルで依存関係を最小限に抑えられます。一方で、AssertJの流れるようなインターフェース（Fluent Interface）は、テストの意図を自然言語に近い形で表現できるため、複雑な検証を行う際のコードの保守性を高めます。
