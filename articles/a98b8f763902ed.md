## 1\. ONBUILD命令とは

Dockerfileを利用すると、DockerHub公式のイメージからカスタムなイメージを作ることができます。
そのため、1つの開発プロジェクトで複数のDockerfileを作成し、用途別の複数のカスタムイメージを利用するケースがよく見られます。

しかし、それら複数のDockerfileに共通する命令（社内ルールや共通する仕様など）があった場合、１つずつのDockerfileに同じ命令を記述する必要があります。
同じ記述を複数のFileに記述しなければならない場合、記述忘れや記述間違いによってエラーが起きる可能性もあります。

そのようなケースでは、プロジェクトや社内で共通する仕様を記載したカスタムな「ベースイメージ」をあらかじめ作成するという手法が用いられます。
この「ベースイメージ」を作成するための便利な命令が「ONBUILD」命令です。

ONBUILD命令は、複数のイメージに共通する命令を記述する方法です。
その特徴は、命令を記述したDockerfile自体のビルド時には実行されず、そのイメージをベースとして利用する派生イメージのビルド時に初めて実行される点にあります。

ベースイメージのONBUILD命令は、ベースイメージを利用したすべての派生イメージがビルドされる際に必ず実行されます。
共通のルール、セキュリティ（非rootユーザーでの実行の強制）、環境設定など、プロジェクトや社内で標準化したい命令をベースイメージのONBUILD命令に記載することで、チーム全体の標準化を実現できるのです。
また、開発者はベースイメージ側の共通処理を意識することなく、固有の追加命令の記述に注力できます。

具体的なONBUILD命令の仕組みは、以下の通りです。

1. ベースイメージをDockerfileで作成する。このとき、ベースイメージのDockerfileにONBUILD命令として、派生イメージで実行したい命令を記述します。
2. ベースイメージがビルドされる際、ONBUILD命令の内容を「トリガ」として抽出し、ベースイメージのメタデータをして登録されます。（この時点ではONBUILD命令は実行されていません）
3. ベースイメージから、別の派生イメージを作ります。派生イメージのビルド時、FROM命令の実行プロセスにおいて、ベースイメージにONBUILDトリガーが登録されているかをチェックします。トリガーが存在する場合、それらを登録順に実行します。すべてのトリガの処理が成功すると、FROM命令は終了し、次のビルド工程に進みます。
4. 派生イメージが最後までビルドできた段階で、最終イメージからトリガ情報が削除されます。

ONBUILD命令に、FROMやONBUILD命令自体を再帰的に記述することはできません。

また、ONBUILD命令は、命令を記述したベースイメージから派生したイメージ（子イメージ）では実行されますが、派生イメージからさらに派生したイメージ（孫イメージ）には受け継がれません。


## 2\. コード例

では、実際にONBUILD命令を動かしてみましょう。

まずは、ベースイメージを作成します。

```Dockerfile.base
FROM alpine:latest

# ベースイメージ自体のビルド時に実行されるもの
RUN echo "Base image is being built..."

# 派生イメージのビルド時に初めて実行されるもの
ONBUILD RUN echo "Derived image build started at: $(date)" > /build_info.txt
```

ベースイメージビルド時に実行されるRUN命令と、ONBUILDのRUN命令が記載されています。
ONBUILD命令には、実行した日時を取得し、文字列を格納したテキストファイルを作成する指示が書かれています。

次に、上記のDockerfileからベースイメージをビルドします。
Dockerfileを記載したディレクトリまで移動し、以下のコマンドを実行します。
イメージ名は「my-base」とします。

```Bash
docker build -f Dockerfile.base -t my-base .
```

ビルドログを見ると、以下の情報が見られます。

```
 => [2/2] RUN echo "Base image is being built..."
```

RUN命令の「RUN echo "Base image is being built..."」は見えますが、ONBUILD命令の記述はありません。
念のため、ONBUILD命令で指定したファイルが存在するかを確認します。

```Bash
docker run --rm my-base cat /build_info.txt
```

以下のようなメッセージが表示され、ファイルがまだ存在しないことがわかります。

```
can't open '/build_info.txt': No such file or directory
```

次に、派生イメージのDockerfileを作成します。派生イメージは、ベースイメージをFROMするだけのシンプルなものを用意します。

```Dockerfile.app
FROM my-base
```

上記の派生イメージをビルドします。

```Bash
docker build -f Dockerfile.app -t my-app .
```

ビルドログを見ると、ベースイメージで記述したONBUILD命令が実行されているのがわかります。

```
 => [2/2] ONBUILD RUN echo "Derived image build started at: $(date)" > /build_info.txt
```

派生イメージで、ファイルが存在するかを確認します。

```Bash
docker run --rm my-app cat /build_info.txt
```

今回は、ファイルの存在と文字列情報を確認できました。

```
Derived image build started at: Wed Mar 11 00:00:00 UTC 2026
```

## 3\. ONBUILD命令のデメリット

ONBUILD命令は強力な自動化ツールですが、その反面運用には注意が必要です。

ONBUILDは、派生イメージ側のソースコードを一見しただけでは、ビルド時にどのような命令が実行されているのか分かりません。そのため、派生イメージのビルド失敗の原因がベースイメージ側のONBUILD命令にあると、エラー解消に時間がかかる場合があります。

また、ONBUILDでADDやCOPYを使用する場合、コピーされるファイルは「派生イメージをビルドしているディレクトリ（ビルドコンテキスト）」のものです。ベースイメージ作成者が想定したディレクトリ構造が派生イメージのビルド環境にないと、ビルドが即座に失敗してしまいます。

そのためONBUILDは、社内や共通プロジェクト内など、命令の内容が周知できる範囲内で使用することが望ましいでしょう。
