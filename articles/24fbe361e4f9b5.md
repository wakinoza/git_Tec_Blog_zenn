## はじめに

- AWS SOAの取得を目指して勉強中です。
- AWSのイベント駆動アーキテクチャについて学習する中で、イベント駆動の起点にはどのような方式があるのか気になりました。
- 本記事では、イベントの発生を最初に検知・取得する方式に焦点を当て、AWSの代表的なサービスとユースケースを整理します。
- 間違い等あれば、指摘いただけると助かります。

## 結論

AWSでは、イベントの発生を検知して後続処理につなげる仕組みとして、Push型、ポーリング型、メトリクス評価型などが利用されます。

- Push型：イベントソース（イベント発生元のリソース）から通知やデータを配信する方式。S3のイベント通知やKinesis Data StreamsのEnhanced Fan-Outなどが該当します。

- ポーリング型：取得側がキューやストリームを定期的に読み取り、データを取得する方式。LambdaのイベントソースマッピングやEventBridge Pipesなどが該当します。

- メトリクス評価型：メトリクスを継続的に評価し、閾値や条件を満たした場合に状態変化を検知する方式。CloudWatch Alarmsなどが該当します。

イベント発生元から通知を受け取る場合はPush型、キューやストリームからデータを取得する場合はポーリング型、メトリクスの閾値超過などを検知する場合はメトリクス評価型が利用されます。

## 1\. イベント駆動アーキテクチャとは？

イベント駆動アーキテクチャ（Event-Driven Architecture：EDA）とは、システム内で発生した「イベント」を契機として、後続の処理を実行するアーキテクチャです。

「イベント」とは、システム内で発生した状態変化や出来事を指します。

イベントの例として、以下のようなものがあります。

- `S3`にファイルがアップロードされた
- `DynamoDB`のレコードが更新された
- `EC2`のCPU使用率が一定の閾値を超えた

イベント駆動アーキテクチャでは、イベントの発生元と処理を実行する側を分離できるため、システム間の疎結合化や非同期処理を実現できます。

AWSでは、イベントの発生元となるサービスとイベントを検知・取得するサービスを組み合わせることで、イベント駆動アーキテクチャを構成します。

## 2\. イベントの検知・取得方式

AWSのイベント駆動アーキテクチャでは、イベントの発生を通知によって受け取る方式や、キュー・ストリームからデータを取得する方式など、さまざまな仕組みが利用されます。

本記事では、イベントの検知・取得の入口となる仕組みを、次の3つのパターンに整理します。
これらの分類は、イベントの検知・取得方法を理解するための便宜的な整理、AWS公式の分類ではありません。

- Push型（イベント通知・データ配信）
- ポーリング型
- メトリクス評価型

これらは排他的な分類ではありません。
それぞれのパターンを組み合わせて、より有用な構成を作成することも可能です。


### 2\.1 Push型（イベント通知・ストリーミング配信型）

イベントソース（イベントの発生元）やデータ配信サービスが、イベント通知やデータを後続のリソースへ送信する方式です。
Push型のうち、イベント通知型ではイベントの発生を契機にイベント通知が送信され、ストリーミング配信型ではデータ配信サービスからコンシューマーへデータが送信されます。
本記事では、イベント通知だけでなく、ストリーミングデータの配信方式もPush型として扱います。

イベントソースが起点となって情報を送信するため、後続のリソースがイベントの有無を問い合わせる必要がありません。

代表例：
- `Amazon S3`(以下、`S3`)のイベント通知
- `Amazon Kinesis Data Streams`のEnhanced Fan-Out

【`S3`のイベント通知】

`S3`では、オブジェクトの作成・削除などを契機にイベント通知を発行できます。

例えば、`S3バケット`で`EventBridge Event Bus`へのイベント送信を有効化すると、オブジェクトがアップロードされた際に、`S3`から`EventBridge Event Bus`へイベントが送信されます。
`EventBridge Event Bus`は、受信したイベントに対してルールを評価し、条件に一致したイベントを`Lambda`へ配送します。


```
S3
 │ オブジェクト作成
 ▼
EventBridge Event Bus
 │ イベント受信・ルールによる判定
 ▼
Lambda
```

【`Kinesis Data Streams`のEnhanced Fan-Out】


`Kinesis Data Streams`は、ストリーミングデータを収集・保持し、複数のコンシューマー（後続の処理を行うアプリケーション）が読み取れるようにするサービスです。

例えば、大量のログやIoTデータを複数のコンシューマーで低遅延で処理するケースで用いられます。

Enhanced Fan-Outを利用しない「共有スループット方式」では、複数のコンシューマーが同じシャード（データの書き込み・読み取りを担う単位）の読み取りスループットを共有します。この場合、コンシューマーは、GetRecords APIを利用したポーリングによりデータレコードを取得します。

一方、「Enhanced Fan-Out」を利用すると、コンシューマーごとに専用の読み取りスループットが割り当てられます。
コンシューマーはSubscribeToShard APIでHTTP/2接続を確立します。`Kinesis Data Streams`は、HTTP/2接続を通じて、シャードのデータをPush型で配信します。

### 2\.2 ポーリング型

後続のリソースが、イベントソースからデータを取得する方式です。

ポーリングとは、後続リソースが主体となって、イベントソースのデータやイベント発生の有無を問い合わせ、利用可能なデータを取得する仕組みです。

代表例：
- `AWS Lambda`（以下、`Lambda`）のイベントソースマッピング
- `Amazon EventBridge Pipes`（以下、`EventBridge Pipes`）

【`Lambda`のイベントソースマッピング】

`Lambda`のイベントソースマッピングは、`Lambda`サービスが`SQS`や`DynamoDB Streams`などのイベントソースをポーリングし、取得したメッセージやレコードをバッチとして`Lambda`関数に渡す機能です。
ポーリングは`Lambda`サービス側で管理されるため、開発者が`Lambda`関数内にポーリング処理を実装する必要はありません。

例えば、`SQS`に注文処理のメッセージが登録されると、`Lambda`がメッセージを取得して注文処理を実行する構成が考えられます。

```
SQS
 │ メッセージ登録
 ▼
Lambdaイベントソースマッピング
 │ ポーリング・取得
 ▼
Lambda
 │
 ▼
注文処理
```

また、`DynamoDB Streams`をイベントソースに指定すると、`Lambda`のイベントソースマッピングがテーブルの追加・更新・削除を記録したストリームをポーリングし、変更内容に応じた後続処理を実行します。

【`EventBridge Pipes`】

`EventBridge Pipes`は、対応するイベントソースをポーリングしてデータを取得し、必要に応じてフィルタリングや加工を行ったうえで、後続リソースへ渡すサービスです。

`Lambda`のイベントソースマッピングでは、取得したデータを`Lambda`関数へ渡して処理します。`EventBridge Pipes`では、データのフィルタリングや変換に加え、必要に応じてEnrichment（データの拡充・加工）も可能です。
また、`Lambda`以外の後続リソースにもデータを連携できます。

例えば、`DynamoDB Streams`から変更情報を取得し、特定の条件に合致するレコードだけをSQSへ連携する構成が考えられます。

```
DynamoDB
 │ データ変更
 ▼
DynamoDB Streams
 │
 ▼
EventBridge Pipes
 │ ポーリング・フィルタリング
 ▼
SQS
```

`EventBridge Pipes`でポーリングできるイベントソースは、対応するサービスに限られます。

一方、イベント通知やポーリングによるデータ取得とは異なり、`CloudWatch Metrics`に記録されたメトリクスを評価することで、閾値超過などの状態変化を検知する方法もあります。


### 2\.3 メトリクス評価型

メトリクスを継続的に評価し、設定した条件を満たした場合に状態変化を検知する方式です。

メトリクスを評価することで、イベント通知機能を持たないリソースについても、`CloudWatch Metrics`で取得可能な数値をもとに状態変化を検知できます。
また、単発の変更だけでなく、一定時間にわたる閾値超過や複数のメトリクスを組み合わせたイベント検知も可能です。

代表例：
- `Amazon CloudWatch Metrics`（以下、`CloudWatch Metrics`）
- `Amazon CloudWatch Alarms`（以下、`CloudWatch Alarms`）

`CloudWatch Metrics`は、AWSリソースやアプリケーションから収集したメトリクスを保存・提供します。

`CloudWatch Alarms`は、メトリクスが設定した閾値を超えた状態が一定期間続いた場合などに、アラーム状態へ遷移します。
この状態変化を契機として、SNSによる通知や、EventBridgeを経由した後続処理を実行できます。

例えば、EC2のCPU使用率が一定時間にわたって80%を超えた場合に、アラーム状態へ遷移させ、SNSを通じて通知する構成が考えられます。

```
EC2
 │ CPU使用率
 ▼
CloudWatch Metrics
 │
 ▼
CloudWatch Alarms
 │ 閾値・条件を評価
 ▼
SNS
 │
 ▼
通知
```



## まとめ

| 方式             | イベント検知・取得の主体           | 特徴                                         | 代表例                                            |
| ---------------- | ---------------------------------- | -------------------------------------------- | ------------------------------------------------- |
| Push型           | イベントソース・データ配信サービス | 通知やデータを後続へ送信する                 | S3イベント通知、Kinesis EFO                       |
| ポーリング型     | 後続のリソース                     | ソースからデータを読み取る                   | Lambdaイベントソースマッピング、EventBridge Pipes |
| メトリクス評価型 | 監視・評価側                       | メトリクスを条件と照合して状態変化を検知する | CloudWatch Alarms                                 |
