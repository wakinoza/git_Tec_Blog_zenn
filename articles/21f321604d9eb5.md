## はじめに

- AWS SOA（SysOps Administrator - Associate）の取得を目指して勉強しています。
- EC2の起動時に発生する `Invalid device name` エラーとブロックデバイスマッピングについて調べてみました。
- 間違い等あれば、指摘いただけると助かります。

## 1. `Invalid device name` エラー

Amazon EC2 インスタンスを起動する際に出るエラーとして、`Invalid device name エラー`があります。
エラーの原因として、公式ドキュメントでは以下が挙げられています。

   1. 選択したAMIですでに使用されているデバイス名を使用している
   2. ルートボリューム用に予約されたデバイス名を使用している
   3. 同じ起動要求内で、別のボリュームに使用されているデバイス名を使用している
   4. OSで有効ではないデバイス名を使用している

利用可能なデバイス名は、OSや仮想化の種類によって決まっています。
そのため、利用可能ではないデバイス名を指定すると、原因4の「OSで有効ではないデバイス名」であるとして、`Invalid device name エラー`が発生する可能性があります。

この記事では、原因1～3に挙げられている、AMIや起動時の設定におけるデバイス名の競合・制約について考えます。

## 2. EC2とEBSの基本的な関係

まず、EC2とEBSの関係を整理します。

- EC2：AWSが提供する仮想サーバー
- EBS（Elastic Block Store）：EC2に接続するブロックストレージ
- デバイス名：EC2に接続するEBSやインスタンスストアなどのブロックデバイスを、EC2側で識別するための名前

EC2では、ストレージを接続する際にデバイス名を利用します。

:::message
デバイス名はEC2側で使用されるものであり、OS上で認識される実際のデバイス名とは異なる場合があります。
:::

次に、EC2起動時に使用するデバイス名と、その割り当てを管理する「ブロックデバイスマッピング」の仕組みについて考えていきます。

## 3. AMIのブロックデバイスマッピングとは

ブロックデバイスマッピングとは、EC2インスタンスに接続するストレージと、そのストレージに割り当てるデバイス名の対応関係を定義する仕組みです。

AMI（Amazon Machine Image）には、EC2起動時に使用するブロックデバイスマッピングが定義されています。
AMIからEC2を起動すると、AMIに定義されたブロックデバイスマッピングに基づいて、OSデータなどを格納するルートボリュームや追加ボリュームの構成が決まります。

例えば、AMIに次のようなブロックデバイスマッピングが定義されているとします。

| ストレージ       | デバイス名  |
| ---------------- | ----------- |
| ルートボリューム | `/dev/sda1` |
| 追加ボリューム   | `/dev/sdf`  |

このAMIからEC2を起動すると、AMIのブロックデバイスマッピングに基づいてルートボリューム（/dev/sda1）と、追加ボリューム（/dev/sdf）が割り当てられます。

つまり、AMIにはOSやソフトウェアの情報だけでなく、「起動時にどのストレージを、どのデバイス名で接続するか」というブロックデバイスマッピングも定義されているといえます。

また、AMIに定義されていないストレージをEC2起動時に追加でリクエストすることや、AMIに定義されたブロックデバイスマッピングをEC2起動時に上書きすることも可能です。
EC2起動時にマッピングを追加でリクエストすることで、同じAMIから異なるストレージ構成のEC2を作成することができます。

## 4. Invalid device name が発生する原因

前述の通り、AMIにブロックデバイスマッピングを定義することで、指定されたデバイス名に基づいてストレージが割り当てられます。

では、AMIに定義されたブロックデバイスマッピングと、EC2起動時に追加指定するブロックデバイスマッピングが競合したらどうなるでしょうか？

例えば、AMIで定義されているデバイス名を、起動時に追加するボリュームにも指定した場合はデバイス名が競合します。
このようなデバイス名の競合がある場合に、Invalid device name エラーが発生する可能性があります。


### 4.1 AMIで使用されているデバイス名を指定した場合

例えば、選択したAMIに次のようなブロックデバイスマッピングが定義されているとします。

| ストレージ                    | デバイス名  |
| ----------------------------- | ----------- |
| ルートボリューム              | `/dev/sda1` |
| AMIに定義された追加ボリューム | `/dev/sdf`  |

このAMIからEC2を起動する際、起動時に追加するEBSにも `/dev/sdf` を指定したとします。

| ストレージ                    | デバイス名  |
| ----------------------------- | ----------- |
| ルートボリューム              | `/dev/sda1` |
| AMIに定義された追加ボリューム | `/dev/sdf`  |
| 新しく追加するEBS             | `/dev/sdf`  |

この場合、既存のマッピングと新しいマッピングで、同じデバイス名を使用しています。

EC2は起動時にストレージをデバイス名で識別するため、同じ名前を複数のストレージに割り当てることはできません。

そのため、デバイス名の競合が起き、`Invalid device name` エラーが発生する可能性があります。

### 4.2 ルートボリューム用に予約されたデバイス名

デバイス名には、ルートボリューム用に予約されているものもあります。

例えば、Linux HVM AMIでは、AMIによって `/dev/sda1` や `/dev/xvda` がルートボリューム用として使用されます。
これらのデバイス名を追加EBSに指定すると、デバイス名の競合や予約名の制約によって、エラーが発生する可能性があります。


## 5. Invalid device name エラーが発生した場合に確認すること

Invalid device name エラーが発生した場合は、以下を確認します。

- デバイス名が使用可能なものであるかを、AWS公式ドキュメントで確認する。
- 指定したデバイス名がAMIのブロックデバイスマッピングと競合していないか確認する。

起動時にエラーが発生した場合は、AMIのブロックデバイスマッピングをAWS CLIの `describe-images` コマンドなどで確認します。


##  まとめ

今回、`Invalid device name` エラーを調べたことで、EC2起動時のストレージ構成について理解を深めることができました。

特に重要だと感じたのは、以下の3点です。

- AMIには起動時のブロックデバイスマッピングが定義されている。
- EC2に接続するストレージにはデバイス名を指定する。
- デバイス名が既存のマッピングや予約名と競合すると、起動時にエラーになる可能性がある。

今回のエラーは、単にデバイス名の形式が間違っているだけでなく、AMIに定義されたストレージ構成との関係も重要だとわかりました。
