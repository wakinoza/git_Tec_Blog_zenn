## はじめに

- 現在、LinuCレベル１の取得を目指して勉強中です。
- 前回の記事で、PATHハイジャックについてまとめました。

https://zenn.dev/wakinoza/articles/f0748972a0c13c

- この記事では、VirtualBox上のUbuntu 24.04環境でPATHハイジャックの実証実験（PoC）を行った結果をまとめています。

- この記事で紹介しているコマンド操作は、実務環境では非推奨です。もし、再現する場合は、実務環境とは切り離した学習用環境で実行することを推奨します。
- 間違い等あれば、指摘いただけると助かります。

## 結論

- Ubuntu 24.04環境でも、PATHハイジャックは再現できることを確認しました。
- この攻撃は特殊な脆弱性ではなく、Linuxがコマンドを検索・実行する仕組み（PATH検索）を悪用することで成立します。
- 一方で、PATHに「.」や書き込み可能なディレクトリを含めないことや、特権プログラムでPATHに依存しない実装を行うことなど、開発者や管理者が基本原則を守ることで、多くのケースは対策できます。

## 動作環境

- Windows 11
- Oracle VirtualBox
- Ubuntu 24.04.4

## 1\. タイポを悪用したPATHハイジャック実証実験

### 1\.1 実験

まず、ホームディレクトリ配下に test ディレクトリを作成してください。
その後、一般ユーザー（攻撃者を想定）として ~/test/lss に罠スクリプトを仕込み、実行権限（+x）を付与してください。

```Bash
# 1. 新しいディレクトリを作成
mkdir ~/test

# 2. ~/testディレクトリに移動
cd ~/test

# 3. lsコマンドのタイポであるlssファイルを新規作成し、悪意のあるスクリプトを仕込む
echo -e '#!/bin/bash\necho "[HACKED]"\n/bin/ls "$@"' > lss

# 4. 悪意のあるlssファイルに実行権限を付与する
chmod +x lss

# 5. lsコマンドで、実行権限付きのlssファイルが存在することを確認
ls -l
```

![lsコマンドのスクショ画像](/images/S1_ls.png)

次に、PATHの末尾に「.」を追加してください。

```Bash
# 6. PATHの末尾に「.」を追加して、脆弱な状態を再現する
export PATH=$PATH:.

# 7. PATHの末尾に「.」が追加されていることを確認
echo $PATH
```

![echoコマンドのスクショ画像](/images/S1_echoPATH.png)

`ls`コマンドのタイポである「lss」を実行してください。

```Bash
# 8. lssを実行する
lss
```

![lss実行後のスクショ画像](/images/S1_lss.png)

結果：攻撃者が配置したプログラムが実行された。

`ls`コマンドのタイポで「lss」を実行しただけで、悪意のあるファイルを実行してしまいました。


### 1\.2 後片づけ

実証実験の後片づけをします。
まずは、lssファイルを削除してください。

```Bash
# 1. ~/test ディレクトリに移動する
cd ~/test

# 2. lssファイルを削除する
rm lss
```

次に、PATHを修正します。
PATHの変更は、現在のシェルだけで有効なので、現在のシェルを終了することで、PATHを元の状態に戻せます。
以下のコマンドを実行してください。

```Bash
exit
```

再度シェルを立ち上げても、PATHは/etc/profileから読み込まれるため、元の正常なPATHに戻っています。

## 2\. root権限で悪意あるプログラムを実行させる実証実験


### 2\.1 実験

まず、一般ユーザー（攻撃者役）として /tmp/ls に罠スクリプトを仕込み、実行権限（+x）を付与してください。

```Bash
# 1. /tmpディレクトリに移動
cd /tmp

# 2. lsファイルを新規作成し、悪意のあるスクリプトを仕込む
echo -e '#!/bin/bash\necho "[HACKED]"\n/bin/ls "$@"' > ls

# 3. 悪意のあるlsファイルに実行権限を付与する
chmod +x ls

# 4. lsコマンドで、実行権限付きのlsファイルが存在することを確認
ls -l
```
![lsコマンドのスクショ画像](/images/S2_ls.png)

次に、rootユーザーに切り替えて、PATHの先頭に「.」を追加してください。

```Bash
# 5. rootユーザーに切り替える（パスワードを求められます）
sudo su -

# 6. 【重要】rootユーザーのPATHの先頭に「.」を追加して、脆弱な状態を再現する
export PATH=.:$PATH

# 7. PATHの先頭に「.」が追加されていることを確認
echo $PATH
```

![echoコマンドのスクショ画像](/images/S2_echoPATH.png)

rootユーザーが、システムの確認などのために /tmp ディレクトリに移動し、中身を見ようと ls コマンドを実行したとします。
以下のコマンドを実行してください。

```Bash
# 8. rootユーザーが /tmp ディレクトリに移動する
cd /tmp

# 9. ls コマンドを実行する
ls
```
![ls実行後のスクショ画像](/images/S2_hacked.png)

結果：root権限で攻撃者が配置したプログラムが実行された。

`ls`コマンドの結果出力の前に、悪意のあるスクリプトである「HACKED」が出力されています。
悪意のあるユーザーが準備したlsファイルを、rootユーザーが実行してしまったことを示しています。

rootユーザーが/tmpにいる状態でコマンドを実行すると、カレントディレクトリは/tmpであるため、PATH中の「.」は/tmpを意味します。
また、「.」はPATHの先頭にあるため、通常のlsコマンドの実行ファイルよりも、/tmpに配置された悪意のあるlsファイルのほうが先にPATH検索されます。
そのため、rootユーザーは、lsコマンドを実行したつもりが、悪意のあるlsファイルを実行してしまったのです。

今回は実証実験のために、rootユーザー自身が意図的にPATHを危険な設定へ変更しています。
通常のUbuntuのデフォルト設定では、rootユーザーのPATHにカレントディレクトリ（.）が含まれることはありません。

実験に用いた悪意のあるスクリプトは文字列を出力するのみですが、実際の攻撃においては、バックドアの設置やSUIDビット付き実行ファイルの配置など、システムを掌握するための処理が行われる可能性があります。

### 2\.2 後片づけ

実証実験の後片づけをします。
まずは、lsファイルを削除してください。

```Bash
# 1. /tmp ディレクトリに移動する
cd /tmp

# 2. lsファイルを削除する
rm ls
```

次に、rootユーザーのPATHを修正します。
PATHの変更は、現在のシェルだけで有効なので、rootシェルを終了することで、PATHを元の状態に戻せます。
以下のコマンドを実行してください。

```Bash
exit
```

再度rootユーザーとしてsudoしても、新しいログインシェルでは、シェル初期化ファイルからPATHが再設定されるため、exportで行った一時的な変更は元に戻ります。

## 3\. PATHハイジャックを防ぐには

PATHハイジャックの恐ろしさがわかったところで、具体的な対策について、4つの点で説明していきます。

### 3\.1 PATHに「.」や書き込み可能なディレクトリを含めない（基本原則）

PATHハイジャック対策として、最も基本かつ重要なのは、環境変数PATHにカレントディレクトリ（.）や、一般ユーザーが書き込み可能なディレクトリ（/tmpなど）を含めないことです。

PATHに登録されたディレクトリは、コマンドを実行するたびにシステムが探索対象とします。そのため、攻撃者が書き込み可能なディレクトリがPATHに含まれていると、悪意のある実行ファイルが正規のコマンドより先に実行されたり、タイポしたコマンド名を悪用されたりする危険性があります。

本記事で実証したように、PATHの先頭に.を追加すると、カレントディレクトリ内に配置された悪意のある実行ファイルが、本来のシステムコマンドより優先して実行されます。また、PATHの末尾に.を追加した場合でも、ユーザーのタイポを狙った悪意のあるプログラムが実行される可能性があります。

そのため、Linuxでは次のような設定は避けるべきとされています。

```Bash
# ❌ カレントディレクトリを追加
export PATH=.:$PATH

# ❌ 書き込み可能なディレクトリを追加
export PATH=$PATH:/tmp

# ❌ 空要素(::)（POSIXではカレントディレクトリとして扱われる）
export PATH=/usr/bin::/bin
```

PATHには、システム管理者が管理する信頼できるディレクトリ（/usr/binや/binなど）のみを登録し、カレントディレクトリのプログラムを実行する場合は、PATH検索に依存せず、`./script.sh`のように相対パスを明示して実行することが推奨されます。

### 3\.2 外部コマンドは必要に応じて絶対パスで呼び出す

PATHハイジャックを防ぐ方法として、開発者が実装時に行える代表的な対策が、外部コマンドを絶対パスで呼び出すことです。

通常、コマンドをファイル名だけで指定すると、システムは環境変数PATHを参照して実行するプログラムを探索します。
この場合、実際にどの`ls`が実行されるかは、実行時のPATHの内容に依存します。もしPATHが攻撃者によって改ざんされていた場合、本来の`/bin/ls`ではなく、悪意のあるプログラムが実行される可能性があります。

一方、絶対パスを指定すると、PATHの探索自体が行われません。
絶対パスを指定すれば、システムは指定された実行ファイルを直接実行するため、PATHハイジャックの影響を受けません。

この考え方は、シェルスクリプトや各種プログラミング言語でも共通です。
特に、管理者権限で動作するプログラムや、SUIDプログラム、Cronジョブなど、特権で実行される処理では、PATHに依存したコマンド呼び出しを避け、必要に応じて絶対パスを明示することが推奨されています。

### 3\.3 sudoのsecure_pathにより、特権実行時はPATHが安全な値に置き換えられる

ここまでは、開発者が注意すべき事項を説明してきました。
Linuxやミドルウェアには、PATHハイジャックを防ぐための防御機能が用意されています。

その一つが、「secure_path」です。

Linuxでは、管理者権限でコマンドを実行する際に`sudo`が広く利用されています。

`sudo`には、「secure_path」という設定が用意されており、有効になっている環境では、sudo経由で実行されたコマンドの環境変数PATHを、管理者が定義した安全な値へ置き換えることができます。

Ubuntuでは、デフォルトで次のような設定になっています。


```Bash
# sudoersファイルからsecure_pathの設定行のみを抽出して確認する
sudo grep secure_path /etc/sudoers

# 結果：Defaults secure_path="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
```

この設定が有効な場合で、一般ユーザーが以下のようにPATHを書き換えていたとします。

```Bash
export PATH=/tmp:$PATH
```

一般ユーザーが`sudo`コマンドを実行した場合、元の環境のPATHはそのまま引き継がれません。
「secure_path」で定義された安全なPATHに置き換えた上で、指定されたコマンドを実行します。
そのため、/tmpなどに配置された悪意のある実行ファイルが探索対象となることを防ぎ、PATHハイジャックのリスクを低減できます。

ただし、「secure_path」はあくまで`sudo`を経由して実行されるコマンドに対する保護機能です。

本記事で実証したように、管理者がログイン後に自らPATH変更を行った場合や、特権プログラム自体が不適切なPATHを利用する設計になっている場合は、「secure_path」では防ぐことはできません。

そのため、secure_pathはPATHハイジャック対策の一つではありますが、基本原則である「PATHに.や書き込み可能なディレクトリを含めない」「特権プログラムではPATHに依存したコマンド実行を行わない」と組み合わせて運用することが重要です。

#### 3\.3\.1 実証実験
「secure_path」の挙動を実験してみましょう。

まず、一般ユーザーの状態で、PATHに「/tmp」を追加してください。

```Bash
# 1 PATHに「/tmp」を追加する
export PATH=/tmp:$PATH

# 2 PATHを確認する。
echo $PATH
```

![echoコマンドのスクショ画像](/images/S3_echoPATH.png)

次に、`sudo`コマンドを実施して、PATHを表示してください。

```Bash
# 3 sudoコマンドを実行し、PATHを確認する
sudo printenv PATH
```

![sudo実行後のスクショ画像](/images/S3_sudo.png)

`sudo`コマンド実行時のPATHが、元のPATHとは異なる、「secure_path」に置き換わっていることが確認できます。

#### 3\.3\.2 後片づけ

今回は一時的な変更なので、そのままシェルを閉じれば元のPATHに戻ります。

```Bash
exit
```

### 3\.4 /tmpなどにnoexecを付与し、一時ディレクトリからの実行を制限する

Linuxでは、/tmpや/var/tmpなどの一時ディレクトリに対して、マウントオプション（ファイルシステムの動作を制御する設定）の一つである「noexec」を適用することで、そこに配置された実行ファイルの起動を制限できます。

例えば、/tmpが「noexec」でマウントされている場合、攻撃者が悪意のある実行ファイルを/tmpへ配置したとしても、そのファイルを直接実行することはできません。

ただし、「noexec」はPATHハイジャックそのものを防ぐ機能ではありません。
一時ディレクトリからのプログラム実行を制限することで、PATHハイジャックをはじめとする、一時ディレクトリを悪用した攻撃の成立を難しくできます。

現在のマウントオプションは、次のコマンドで確認できます。

```Bash
mount | grep ' /tmp '
```

noexecが設定されている場合は、次のような出力になります。

```Bash
tmpfs on /tmp type tmpfs (rw,nosuid,nodev,noexec,...)
```

一方で、noexecマウントオプションは実行を完全に防ぐわけではありません。

例えば、以下のようにインタプリタを明示してスクリプトを実行した場合、スクリプトファイル自体は実行されず、bashプロセスがテキストファイルとして読み込んで解釈・実行します。
そのため、noexecが設定されていても、処理は実行されます。

```Bash
bash /tmp/script.sh
```

## まとめ

- Ubuntu 24.04環境でも、PATHハイジャックが成立することを実証しました。
- PATH検索の仕組みを悪用することで、意図しないプログラムが実行されることを確認しました。
- sudoのsecure_pathやnoexecなど、LinuxにはPATHハイジャックのリスクを軽減する仕組みが用意されています。
- ただし、これらは万能ではなく、PATHに.や書き込み可能なディレクトリを含めないことや、必要に応じて絶対パスでコマンドを実行することが基本的な対策となります。
