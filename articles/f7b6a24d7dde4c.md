## 1\. パラメータテスト

ユニットテストで十分な検証を行うためには、1つのテスト対象に1回検証するだけでは不十分なことが多いでしょう。そのため、1つのテスト対象に対して、複数のテストデータで検証を行います。しかし、テストデータごとにテストケースを記述していては、多くのテストコードが重複し、可読性が低下するだけでなく、変更時の変更漏れの原因になります。

「一つのテストケースで、複数のテストデータを検証したい」そんなニーズに応えるのが、「パラメータテスト」です。

パラメータテストでは、一つのテストケースで複数のテストデータを検証できます。
テストデータごとにテストケースを記述する必要もなく、コードが重複しないため、変更も容易です。
パラメータテストを実施する場合は、テストメソッドに`@ParameterizedTest`アノテーションを付与します。

また、検証したいテストデータを専用のアノテーションからテストメソッドに渡します。

データを渡すアノテーションの代表的なものを、以下にまとめます。

| アノテーション | 向いているケース                                             |
| -------------- | ------------------------------------------------------------ |
| @ValueSource   | 引数が1つだけで、値が単純な時。                              |
| @CsvSource     | 引数が複数あり、コード内にサクッと書きたい時。               |
| @MethodSource  | 引数が複雑(オブジェクト)な時、またはデータを使い回したい時。 |
| @CsvFileSource | データ量が膨大な時、または外部ファイルで管理したい時。       |
| @EnumSource    | Enumの全パターンを網羅したい時。                             |

代表的な`@ValueSource`、`@CsvSource`、`@MethodSource`を利用したコード例は以下のとおりです。

### 1.1 `@ValueSource`

１回の検証に引数を1つ渡したい場合には`@ValueSource`アノテーションを用います。

以下は、数値が正の数かどうかを判定するメソッドを検証しています。検証のため、`@ValueSource`で複数の検証用データを渡しています。

```java
import static org.assertj.core.api.Assertions.assertThat;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;

class CalculatorTest {

    // テスト対象のメソッド
    boolean square(int number) {
        return number > 0;
    }

    @ParameterizedTest
    @ValueSource(ints = {1, 5, 100})
    void 数値が正の数か正しく判定されること(int input) {
        boolean result = square(input);

        // AssertJによる検証
        // 期待値：true
        assertThat(result)
            .as("%d が正の数かチェック", input)
            .isTrue();
    }
}
```

ちなみに、失敗時に表示するメッセージを指定するas()の引数に記載されている「%d 」には、失敗したテストで使用されていた値が動的に埋め込まれます。AssertJの `.as()` や `.describedAs()` メソッドは、Javaの `String.format()` と同じ形式(書式指定子)をサポートしているため、変数の中身をメッセージに含めることができます。as()に指定子を記述することで、テストケース失敗時のエラーメッセージに失敗した引数を表示させることができるため、テスト失敗時の原因究明が容易になります。

このテストケースでは、整数型を引数とするため「%d 」という指定子を利用しています。その他のデータ型での指定子は以下のとおりです。

| 指定子 | 型                         | 例                                            |
| ------ | -------------------------- | --------------------------------------------- |
| `%d`   | 整数 (int, longなど)       | `as("ID: %d のテスト", id)`                   |
| `%s`   | 文字列 (String)            | `as("ユーザー名: %s のバリデーション", name)` |
| `%f`   | 浮動小数点 (double, float) | `as("計算結果: %f を確認", value)`            |
| `%b`   | 真偽値 (boolean)           | `as("フラグが %b であること", flag)`          |

### 1.2 `@CsvSource`

1回の検証に複数の値を引数として渡したい場合は、値をコンマまで区切ったCSV形式で記述します。
ダブルクォーテーションで囲まれた固まりが一回分のテストデータとなります。

以下は、２乗した値を返すメソッドを、`＠CsvSource`を利用して検証しています

```java
import static org.assertj.core.api.Assertions.assertThat;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;

class CalculatorTest {

    // テスト対象メソッド
    int square(int number) {
        return number * number;
    }

    @ParameterizedTest(name = "第{index}回：入力値 {0} のとき、期待値が {1} であること")
    @CsvSource({
        " 0,   0",  // 境界値
        " 1,   1",  // 正常系
        " 5,  25",  // 正常系
        "-3,   9",  // 負の数
    })
    void squareメソッドの計算テスト(int input, int expected) {
        int actual = square(input);

        // AssertJで検証
        assertThat(actual)
            .as("入力値 %d に対する計算結果の検証", input)
            .isEqualTo(expected)            // 期待値と一致するか
            .isGreaterThanOrEqualTo(0);      // 常に0以上か(追加の検証もチェーン)
    }
}
```

上のテストメソッドでは、`@ParameterizedTest` の name属性を記述しています。as()を利用するとエラーメッセージの指定できますが、JUnitの実行結果一覧にも値を表示させたい場合は、`@ParameterizedTest` の name属性を利用します。name属性にメッセージを記述すると、IDEのテスト結果画面に「第1回：・・・」「第2回：・・・」と実行順に結果が表示されるため、複数のテスト結果を把握しやすくなります。

### 1.3 `@MethodSource`

`@CsvSource` は手軽ですが、テストデータを文字列で記述するため、型安全ではありません。

`@MethodSource` を利用すると、テストデータを生成する専用メソッドから引数を供給できるため、テストデータの再利用性が高まります。
また、複雑なオブジェクトなど、事前準備が必要なテストケースにも柔軟に対応できます。

以下がコード例です。
まず、テスト対象となる会員ドメインと、料金計算ロジックを持つクラスを定義します。

```java
// Member.java
public record Member(String name, int age, boolean isGoldCard) {}

// DiscountService.java
public class DiscountService {
    public double calculateDiscountRate(Member member) {
        if (member.isGoldCard()) return 0.2;
        if (member.age() < 18) return 0.1;
        return 0.0;
    }
}
```

次に`@MethodSource` を用いたテストクラスです。テストメソッドのほかに、テストデータを供給するメソッドを別に定義しています。
Arguments.of()メソッドは、テストメソッドに渡す引数のセット(Argumentsインスタンス)を作成する静的ファクトリメソッドで、1つ以上の引数を可変長引数で受け取ります。これらをStream.of() などでまとめることで`Stream<Arguments>`としてデータを供給します
Argumentsは引数のセットを表します。

```java

class DiscountServiceTest {

    private final DiscountService service = new DiscountService();

    @ParameterizedTest(name = "{index}: {1}")
    @MethodSource("provideMemberTestData")
    void 会員種別に応じた割引率が正しく計算されること(Member member, String description, double expected) {
        double actual = service.calculateDiscountRate(member);

        assertThat(actual)
            .as(description)
            .isEqualTo(expected);
    }

    /**
     * テストデータを供給するメソッド
     */
    private static Stream<Arguments> provideMemberTestData() {
        return Stream.of(
            // 引数: Memberオブジェクト, テストケースの説明, 期待値
            Arguments.of(new Member("田中", 25, true),  "ゴールド会員は一律20%引き", 0.2),
            Arguments.of(new Member("佐藤", 17, false), "一般の未成年は10%引き", 0.1),
            Arguments.of(new Member("鈴木", 40, false), "一般の成人は割引なし", 0.0)
        );
    }
}
```

なお、テストデータを供給するメソッドは、「static」である必要があります。その理由は、JUnit5のライフサイクルに関係あります。
JUnit5では、デフォルト設定で、テストメソッドごとにテストインスタンスを新しく生成する仕様になっています。このデフォルト仕様では、テストデータ取得後にテストインスタンスを生成するというライフサイクルであるため、データ取得時にテストインスタンスが存在しません。そのため、インスタンス生成前でも利用できる「static」である必要があるのです。
もし、クラスにつき１つのテストインスタンスを生成するライフサイクルを設定(`@TestInstance(Lifecycle.PER_CLASS)`)すると、`@MethodSource`をstaticにする必要がなくなります。

## 2\. 適切なデータとは

前章で、同一のテストメソッドで複数のテストデータを検証する方法を説明しました。

しかし、そもそも適切なテストデータとはどんなものでしょうか？

入力可能な値を全て検証できれば安全かもしれませんが、膨大なテストケースを記述しなければならないため、現実的ではありません。

そのため、必要十分な「適切」なデータセットを構成する必要があります。

### 2.1 ブラックボックステストとホワイトボックステスト

どのように「適切」なテストデータを作成するのでしょうか？

その問いに答えるために、まず代表的なテストアプローチを２つ説明します。

ユニットテストを行う際に、ブラックボックステストとホワイトボックステストという２種類のアプローチがあります。

ブラックボックステスト：内部のコードを見ずに、テストを行う方法。仕様の実装忘れを見つけやすく、リファクタリングしてもテストコードを変更しなくて良いという利点があります。

ホワイトボックステスト：コードの詳細からテストケースを構築します。テストの抜けもれを検証しやすく、デッドコード(どんなデータを渡しても到達しないコード)を見つけやすくなります。

実際のユニットテストでは、ブラックボックステストとホワイトボックステストという2つの考え方を組み合わせて検証を行います。

具体的には、以下のような流れが多いでしょう。

１. ブラックボックステスト方式でテストデータを作成し、仕様を満たしているかを確認する。

２. 仕様を満たしていることを確認後、網羅率(カバレッジ)を計測して、ホワイトボックステスト方式で検証漏れ部分がないかをチェックし、品質を担保する

上記のユニットテストの流れを踏まえると、パラメータテストのテストデータは、まずはブラックボックステストのアプローチで構成することが望ましいでしょう。

では、ブラックボックステストではどのようなアプローチでテストデータを作成するのでしょうか。

代表的なアプローチは以下の4つです。

- 同値分割
- 境界値分析
- 組み合わせ
- 異常系

### 2.2 同値分割

同値分割とは、同様の結果をもたらす値を「同値クラス」としてグループ化するテスト技法です。各同値クラスから代表値を選んでテストを実施します。代表値で正しく動作することが確認できたら、同じ同値クラスの他の値も正しく動作するとみなします。

### 2.3 境界値分析

プログラムが「境界値」付近で不具合を起こしやすいという性質を利用したテスト技法です。

あるソフトウェアで、「18歳未満であると割引が適用される」という要件があったとします。この場合は「18歳」が境界値となります。そのため、近傍の「17歳」と「18歳」をテストデータとして検証し、分岐の仕様が正しく実装できているかを確認します。

### 2.4 組み合わせ

入力値の組み合わせによって結果が変わる場合は、組み合わせを考慮してテストデータを選択します。ただし、検討する要素が多い場合は、組み合わせの数も膨大になるため、テストケースを絞り込む場合もあります。

### 2.5 異常系

特定の入力に対して、異常なデータ(データ型が違う、空文字、null、範囲外の値など)をシステムが正しく「エラー」として弾いているか、予期せぬ動作を起こさないかを検証します。

### 2.6 コード例

ここで、コード例でテストデータの選出を実演してみましょう。

入場料を計算するメソッドがあるとします。入場料は年齢(age：18歳以上か)、日(isHoliday：平日か休日か)、会員(isMember：会員か非会員か)によって、変化します。
ageが、負の値もしくは150歳以上の場合は不正な値として例外をスローします。

これらの仕様を実装したメソッドは以下のとおりです。

```java
// テスト対象クラス
public class EntranceFeeCalculator {

    /**
     * 入場料を計算するメソッド
     *
     * 異常値:
     *  age < 0 または age >= 150 の場合は IllegalArgumentException
     */
    public int calculateFee(int age, boolean isHoliday, boolean isMember) {

        if (age < 0 || age >= 150) {
            throw new IllegalArgumentException("不正な年齢です: " + age);
        }

        int fee = (age < 18) ? 1000 : 2000;

        if (isHoliday) {
            fee += 200;
        }

        if (isMember) {
            fee -= 300;
        }

        return fee;
    }
}
```

では、上のメソッドを検証するため、適切なテストデータを選出します。

まずは、同値分割を行います。ageは18歳未満と以上、isHolidayはtrueとfalse、isMemberはtrueとfalseに分けられます。

ageは、18歳以上の同値クラスと、18歳未満の同値クラスからそれぞれ代表値を選出します。ageには、18歳という境界値が存在するため、境界値の検証も可能な「18歳」と「17歳」を同値クラスの代表値と境界値として選出します。

次は、それぞれの要素の組み合わせを検証します。
複雑な条件の組み合わせを整理するため、まずデシジョンテーブルを作成し、そこから不要な組み合わせを整理してテストケースを抽出します。

まず、全ての組み合わせのデシジョンテーブルは以下の通りです。

| No  | 年齢 (age)  | 休日 (isHoliday) | 会員 (isMember) | 期待値 |
| --- | ----------- | ---------------- | --------------- | ------ |
| 1   | 18以上 (18) | 平日(false)      | 非 (false)      | 2000   |
| 2   | 18未満 (17) | 平日 (false)     | 非 (false)      | 1000   |
| 3   | 18以上 (18) | 休日 (true)      | 非 (false)      | 2200   |
| 4   | 18以上 (18) | 平日 (false)     | 会 (true)       | 1700   |
| 5   | 18未満 (17) | 休日 (true)      | 非 (false)      | 1200   |
| 6   | 18未満 (17) | 平日 (false)     | 会 (true)       | 700    |
| 7   | 18以上 (18) | 休日 (true)      | 会 (true)       | 1900   |
| 8   | 18未満 (17) | 休日 (true)      | 会 (true)       | 900    |

この中から、テストの品質を落とさずに、テストデータを減らしていきます。

テストデータを絞り込む際には、「各条件が正しく機能するか」と「条件が重なったときに異常が起きないか」という視点でデータを見ていきます。

１、各条件が正しく機能するか：他の条件分岐が仕様通りでも、１つの条件分岐に実装ミスがあれば、全体の結果が異常となってしまいます。そのため、まず、１つ１つの条件分岐が正しく実装できているかを確認します。具体的には、上の表のno.1を基本形として、ageのみが違うもの(no.2)、isHolidayのみが違うもの(no.3)、isMemberのみが違うもの(no.4)のテストを実施します。この4つのテストデータを検証することで、1つ1つの条件分岐が正しく実装できていることを確認できます。

２、条件が重なったときに、異常が起きないか：次に確認するのが、2つ以上の条件が重なったときに異常が起こるかどうかです。その検証のために、no.1の正反対の条件であるno.8を検証します。これにより、複数条件を組み合わせた場合に異常が出ないかを確認します。

no.1~4とno.8のテストデータが必要であることがわかりました。では、no.5~no.7のテストデータはどうでしょうか？

実は、no.5~no.7は場合によっては省略が可能です。その理由は、no.5~no.7で検証している項目が、no.1~4とno.8で検証している項目と重複しているからです。

例えば、no.5は、no.1の状態から、ageとisHolidayの条件が違います。ageの条件が正しく動作することがno.2で、isHolidayの条件が正しく動作することはno.3で確認しています。また、age<18とisHoliday=trueという条件が重なった状態は、no.8で検証しています。

このようにno.5~7はその他のテストデータで検証している項目と重複しているため、no.5の条件でのみ特有のバグが発生する可能性は低いでしょう。そのため、テストの実行コストを下げるために省略される場合があります。

最後に、異常系の検証を行います。

ageは、負の数もしくは150歳以上の場合は例外をスローします。異常系の検証では、不正な値が仕様通り例外をスローするかなどを検証します。

まず、ageを異常系を含めて再度同値分割すると、負の数、18未満の正常値、18以上の正常値、150以上の4つの同値クラスに分けられます。正常値は、正常系で検証されているため、残る負の数と150以上から代表値-1,150を抽出します。

また、0（有効最小値）と149（有効最大値）にそれぞれ分岐の境界値があるため、境界値の付近の0と149もテストデータに追加します。

最終的なテストデータ案は、以下のとおりです。

| 分類                 | No  | 年齢 (age) | 休日 (isHoliday) | 会員 (isMember) | 期待値 (expected) | テストの意図 / 狙い                              |
| -------------------- | --- | ---------- | ---------------- | --------------- | ----------------- | ------------------------------------------------ |
| 正常系 (基本)        | 1   | 18         | false            | false           | 2000              | 基本形: 成人・平日・一般(すべての基準)           |
| 正常系 (境界/単項目) | 2   | 17         | false            | false           | 1000              | 子供割引: 18歳の境界(未満)の確認                 |
| 正常系 (境界/単項目) | 3   | 18         | true             | false           | 2200              | 休日加算: 休日フラグ単体での動作確認             |
| 正常系 (境界/単項目) | 4   | 18         | false            | true            | 1700              | 会員割引: 会員フラグ単体での動作確認             |
| 正常系 (組み合わせ)  | 5   | 17         | true             | true            | 900               | 全部盛り: 子供・休日・会員が重なった時の干渉確認 |
| 正常系 (最大境界)    | 6   | 149        | false            | false           | 2000              | 有効最大値: 150歳未満のギリギリを確認            |
| 正常系 (最小境界)    | 7   | 0          | false            | false           | 1000              | 有効最小値: 0歳での動作確認                      |
| 異常系 (下限外)      | 8   | -1         | false            | false           | 例外              | 異常値: 負の数で正しくエラーが出るか             |
| 異常系 (上限外)      | 9   | 150        | false            | false           | 例外              | 異常値: 150歳以上で正しくエラーが出るか          |

上のテストデータを実装したテストコードは以下の通りです。

```java

class EntranceFeeCalculatorTest {
    private EntranceFeeCalculator calculator;

    /**
     * 各テスト実行前にインスタンスを生成
     */
    @BeforeEach
    void setUp() {
        calculator = new EntranceFeeCalculator();
    }

    // --- 正常系のテスト ---
    @ParameterizedTest(name = "{index}: 年齢={0}, 休日={1}, 会員={2} => 期待値={3}円")
    @CsvSource({
        // 年齢, 休日, 会員, 期待値
        " 18, false, false, 2000 ",
        " 17, false, false, 1000 ",
        " 18, true,  false, 2200 ",
        " 18, false, true,  1700 ",
        " 17, true,  true,   900 ",
        "  0, false, false, 1000 ",
        "149, false, false, 2000 "
    })
    void 入場料計算ロジックの網羅テスト(int age, boolean isHoliday, boolean isMember, int expected) {
        assertThat(calculator.calculateFee(age, isHoliday, isMember))
            .as("年齢:%d の時の料金が正しくない", age)
            .isEqualTo(expected);
    }

    // --- 異常系のテスト ---
    @ParameterizedTest(name = "{index}: 不正な年齢 {0} の場合に例外がスローされること")
    @ValueSource(ints = {-1, 150})
    void 不正な年齢の場合は例外をスローする(int invalidAge) {
        assertThatThrownBy(() -> calculator.calculateFee(invalidAge, false, false))
            .isInstanceOf(IllegalArgumentException.class)
            .hasMessageContaining("不正な年齢です");
    }
}

```

まずは、上のテストデータでブラックボックステストを行い、仕様通りかを確認します。テストに失敗する場合や、カバレッジが低い場合は、随時テストケースを追加していきます。

以上が、ユニットテストの基本的な流れです。

なお、テストデータを作成する技法はこの記事で紹介したもの以外にも多数あります。

例えば、「2つの項目の組み合わせ」を厳密に検証したい場合は、「ペア構成法」などの技法を使いテストデータを選択します。

テスト技法は多数あるので、仕様に合ったテスト技法を選択する必要があります。

## まとめ
- 重複の排除と可読性の向上: `@ParameterizedTest` を活用することで、1つのテストメソッドで多角的な検証が可能になり、メンテナンス性の高いテストコードを実現できる。

- 用途に応じた最適なデータ供給: 単純な値なら `@CsvSource`、複雑なオブジェクトや型安全性を重視する場合は `@MethodSource` と、状況に応じて最適なアノテーションを選択することが重要である。

- 戦略的なテストデータ選定: 全件テストは現実的ではないため、境界値分析や同値分割、そして項目の組み合わせ(ペア構成法など)といったテスト技法を論理的に適用し、最小のコストで最大の品質を担保する。
