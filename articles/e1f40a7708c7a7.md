## はじめに

- 現在、LinuCレベル１の取得を目指して勉強中です。
- Linuxの時刻管理の概要と、用語を整理しました。
- 間違い等あれば、指摘いただけると助かります。

## 結論

Linuxでは、「ハードウェアクロック」と「システムクロック」という2種類の時計を利用して時刻を管理しています。

しかし、これらの時計はハードウェアの特性上、少しずつ現実の時刻からずれていきます。
時刻のずれは、証明書エラーや認証失敗、ログ解析の困難化など、システム運用に大きな影響を及ぼします。

そのため、LinuxではNTP（Network Time Protocol）によって定期的に時刻を補正し、複数のコンピューター間で時刻を同期しています。


## 1\. ハードウェアクロックの仕組み

Linuxでは、時刻を管理する時計として主に「ハードウェアクロック」と「システムクロック」の2つがあります。

ハードウェアクロックは、PCの電源がオフの状態でも「今が何時か」を忘れないための回路です。

ハードウェアクロックは、マザーボード上のRTC（Real Time Clock）機能によって管理される時計です。
このICは、マザーボード上のボタン電池（CMOS電池）によって電力が供給されているため、PCの主電源がオフの状態であっても時を刻み続けます。（電池切れになると時計がリセットされる場合があります）
RTCはBIOS/UEFIの設定画面から時刻を確認・設定できることから、「BIOSクロック」と呼ばれることもあります。

RTCの主な役割は、OSが起動していない間の時刻を維持し、システム起動時にカーネルに対して時間の初期値を提供することにあります。
Linuxカーネルは起動時にRTCを参照し、その時刻情報を基に後述するシステムクロックを初期化します。

| 用語                   | 意味                                                                                                                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ハードウェアクロック   | LinuxがRTCとして扱う、電源OFF中も動作する時計。                                                                                                                                          |
| RTC（Real-Time Clock） | マザーボード上の時計機能。ハードウェアクロックとほぼ同義                                                                                                                                 |
| CMOS                   | 半導体製造技術（Complementary Metal-Oxide-Semiconductor）の名称。RTCそのものではないが、歴史的にはRTC設定を保持するCMOS RAMとともに使われていたため、RTCを「CMOS時計」と呼ぶことがある。 |
| CMOS電池               | RTCなどへ電力を供給するバックアップ電池                                                                                                                                                  |
| BIOSクロック           | BIOS/UEFI画面で設定・表示される時計。実体はRTC                                                                                                                                           |

## 2\. システムクロックの仕組み

Linuxでは、現在時刻を管理するために「システムクロック」を利用します。

システムクロックとは、Linuxカーネルがメモリ上で管理している論理的な時計です。

Linux起動時、カーネルはRTC（ハードウェアクロック）から時刻を読み込み、その値を利用してシステムクロックを初期化します。

初期化後は、通常の時刻管理ではRTCを参照せず、Linuxカーネルが独自に時刻を管理します。

PCが稼働している間、カーネルはクロックソースで経過時間を計測し、ハードウェアタイマーからの通知を利用しながらシステムクロックを更新します。

| 用語                 | 意味                                                                                                                        |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| システムクロック     | Linuxカーネルが管理する現在時刻                                                                                             |
| ハードウェアタイマー | 時間経過をOSへ通知する仕組み。電源OFF中も時刻を保持するハードウェアクロック（RTC）とは別物                                  |
| タイマー割り込み     | ハードウェアタイマーが一定時間の経過をカーネルへ通知する割り込み                                                            |
| クロックソース       | 時刻計測の基準となるハードウェア。代表例としてTSC、HPET、ACPI PM Timerなどがある。Linuxは複数の候補から適切なものを選択する |

## 3\. 時刻がずれる理由

ハードウェアクロックと、システムクロックという2つの時計を説明しました。
しかし、この2つの時計は、その特性や環境によって、少しずつ世界共通の基準時刻（協定世界時：UTC）からずれていきます。このように時計が徐々にずれていく現象をドリフト（Clock Drift）と呼びます。

ハードウェアクロックは、水晶発振器（クオーツ）の一定の周波数で振動する性質を利用して時間を計測しています。しかし、クオーツの物理振動は、経年劣化や温度変化によって変動してしまいます。
そのため、一般的な水晶発振器を搭載したコンピューターでは、1日に数秒（数ppm〜数十ppm）程度の誤差が生じる可能性があります。


昔のLinuxでは、一定周期のタイマー割り込みを利用した時刻管理の割合が大きく、CPU負荷や割り込み遅延の影響を受けやすい時代がありました。
現在のLinuxでは、高分解能タイマー（High Resolution Timer）やTickless Kernel（NO_HZ）、高精度なクロックソース（TSC、HPETなど）の導入により、システムクロックの精度は大きく向上しています。
しかし、システムクロックも、最終的にはクロックソースなどの物理的なハードウェアを基準として時刻を計測しています。これらのハードウェアは水晶発振器などの物理的な発振源に依存しているため、ズレを完全にゼロにすることはできません。


また、仮想化環境におけるシステムクロックは、CPUスケジューリングや仮想クロックの仕組みにより、物理環境より時刻のずれが生じやすくなる場合があります。
特に、ゲスト仮想マシンの稼働を一時的に中断する「サスペンド（一時停止）」や、後に再開させる「レジューム（再開）」処理を実行した場合、サスペンド中はゲストOSが実行されません。
そのため、再開直後のゲストOSのシステムクロックはサスペンドした時間で停止した状態となります。
通常はハイパーバイザーとの時刻同期機能やゲストエージェントによって自動補正されますが、一時的なずれが生じるリスクがあります。

このように、ハードウェアクロックもシステムクロックも、少しずつ世界共通の基準時刻からずれていくことが避けられません。
そのため、定期的に正しい時刻へ補正する別の仕組みが必要になります。

| 用語                                      | 意味                                                                                                |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 協定世界時（UTC）                         | 世界共通の基準となる時刻。Linuxでは時刻管理の基準として利用される。                                 |
| 水晶発振器（クオーツ）                    | 一定の周波数で振動する性質を利用して時間を計測する部品。RTCやハードウェアタイマーなどの基準となる。 |
| ppm（Parts Per Million）                  | 時計の精度を表す単位。100万分の1を表し、値が小さいほど精度が高い。                                  |
| 高分解能タイマー（High Resolution Timer） | ミリ秒より細かい精度で時刻を管理するLinuxの仕組み。                                                 |
| Tickless Kernel（NO_HZ）                  | 必要なときだけタイマー割り込みを発生させる仕組み。不要な割り込みを減らし、効率と精度を向上させる。  |
| ハイパーバイザー                          | 仮想マシン（VM）を管理するソフトウェア。CPUやメモリなどの物理リソースを各VMへ割り当てる。           |



## 4\. 時刻ずれによるトラブル例

では、システムの時刻にずれが生じると具体的にどのようなトラブルが生じるのでしょうか。
4つの具体例を見ていきます。

### 4\.1 セキュリティ証明書（SSL/TLS）の検証

Webサイトの保護やAPI通信の保護に用いられるSSL/TLSサーバー証明書、およびクライアント証明書には、検証可能な「有効期間の開始日時と終了日時（満了日時）」が設定されています。
そのため、システムクロックが証明書の有効期間外であると、TLSライブラリやブラウザ、アプリケーションが証明書を無効と判断する可能性があります。
場合によっては、システム間で定常実行されるバックグラウンドのバッチ処理や、HTTPSを利用するAPI通信やWebサービスなどが即座に切断されるケースもあり得ます。

### 4\.2 認証システムにおける「Kerberos 5分ルール」

Active Directory（AD）やLinuxのKerberos認証環境ではリプレイ攻撃を防御するため、発行する認証チケットの有効期限と生成タイムスタンプを厳格に照合します。
そして、クライアントPC、アクセス対象のアプリケーションサーバー、およびキー配布センター（KDC / ドメインコントローラー）の間の時刻差が「5分（300秒）」を超えた場合、セキュリティシステムは認証要求を不正なものとみなし、認証を即座に破棄します（「Kerberos 5分ルール」）。
認証が破棄されると、従業員のADドメインログインが拒絶、共有ファイルサーバーへのアクセス遮断、SSOを介した業務システムやSaaSへの接続失敗といった事態が発生します。
Active Directoryでは既定値として5分が設定されていますが、設定変更も可能です。

### 4\.3 ログの信頼性低下

複数のシステムのログを一か所に集める場合、それぞれの環境のシステムクロックが異なると、ログに記載された時刻に食い違いが生じます。結果、トラブル時の処理の流れを正確に把握することが困難になり、原因究明のコストが増加します。

### 4\.4 cronなどの定期実行の異常

cronはシステムクロックを基準としてジョブを実行します。
そのため、時刻が大きくずれると、本来実行されるべきジョブが予定時刻に実行されなかったり、逆に想定外の時刻に実行されたりする可能性があります。

| 用語                           | 意味                                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------------------------ |
| SSL/TLS                        | 通信内容を暗号化し、安全に通信するための仕組み。WebサイトのHTTPSでも利用される。                       |
| サーバー証明書                 | サーバーの正当性を証明する電子証明書。有効期間が設定されている。                                       |
| API                            | ソフトウェア同士が機能やデータをやり取りするための仕組み。                                             |
| Kerberos                       | 時刻情報を利用して認証を行う認証プロトコル                                                             |
| Active Directory（AD）         | Windows環境で利用されるユーザー・コンピューターの統合管理システム。                                    |
| KDC（Key Distribution Center） | Kerberosで認証チケットを発行するサーバー。Active Directoryではドメインコントローラーがこの役割を担う。 |
| SSO（Single Sign-On）          | 一度の認証で複数のシステムへログインできる仕組み。                                                     |

## 5\. ズレを防ぐためのシステム：NTP

システムクロックのズレを解決し、ネットワークに接続されたすべてのサーバー間で統一された時刻を構築するための標準通信プロトコルが作られました。
それが、NTP（Network Time Protocol）です。

NTPでは、「原子時計」や「GPS」といった、極めて高精度な基準時計を持つNTPサーバーが存在します。
個々のシステムは、定期的にNTPサーバーへ問い合わせを行い、基準時計と時刻を比較することで、システムクロックを補正します。

しかし、世界中のシステムがNTPサーバーに問い合わせると、NTPサーバーに負荷がかかります。
そこで、NTPは、時計の正確性とクエリ負荷の分散を両立させるため、「Stratum（ストラタム）」と呼ばれるピラミッド型の構造を設計しています。

- Stratum 0 (物理参照源): 原子時計やGPS受信機などの基準時計。IPネットワークには直接接続されず、Stratum 1サーバーへ時刻を提供します。
- Stratum 1 (プライマリサーバー): Stratum 0と直接接続し、時刻を同期している最上位のNTPサーバー群。
- Stratum 2 (セカンダリサーバー): ネットワーク経由で複数のStratum 1サーバーを参照し、自身の時刻を維持します。NTPの通信には共通してUDPポート123が使用されます。多くの企業内NTPサーバーや、一部の公開NTPサーバーはこの階層に位置します。
- Stratum 3以降: 直上のStratum 2サーバーを参照し、階層を掘り下げます。

現在の多くのLinuxディストリビューションでは、NTPクライアントとして chrony（chronyd） が標準的に採用されています。

実務では、特定のNTPサーバーだけと同期するのではなく、3つ（推奨は4つ以上）の独立したNTPサーバーを同時に参照することが一般的です。
NTPは複数のサーバーから取得した時刻を比較し、異常な値を除外した上で、最も信頼できる時刻を採用します。

| 用語                         | 意味                                                                        |
| ---------------------------- | --------------------------------------------------------------------------- |
| NTP（Network Time Protocol） | ネットワーク経由でコンピューターの時刻を同期するためのプロトコル。          |
| NTPサーバー                  | 他のコンピューターへ正しい時刻を提供するサーバー。                          |
| Stratum                      | NTPサーバーの階層を表す番号。数字が小さいほど基準時計に近い。               |
| UDP                          | コネクションを確立せずに通信するプロトコル。NTPではUDPポート123を使用する。 |


## 6\. トラブルなくずれを補正するシステム

NTPは、システムクロックを基準時計に同期します。
しかし、システムクロックを一瞬で基準時計へ合わせると、トラブルになることがあります。
時刻補正前と補正後でログの時刻に矛盾が生じたり、cronの定期実行が実行されなかったり、重複したりする可能性があります。
そこで、システム内の時刻の連続性を保ちつつ、システムクロックを補正する必要があります。

ここでは、chronyd や ntpd といったNTPクライアント／サーバーソフトウェアが採用している時刻補正方式を2つ紹介します。

- Step（ステップ）モード
システムクロックを、基準時刻へと即座に補正する手法。
特性: システムクロックを一度に基準時刻へ補正します。
用途: システム初期起動時（タイムスタンプが数分から数日ズレている状況など）において、短時間で強引に同期を成立させたい場合に限定して使用されます。
リスク: 実行中のデータベースや、cron等のバッチタイマーに深刻な矛盾をもたらすため、システム定常稼働中の実行は原則として推奨されません。

‐ Slew（スリュー）モード
クロックの進む速度（周波数）を一時的に調整し、時間の連続性（単調増加性）を維持したまま、現実の時刻へと時間をかけて収束させる手法。
特性: 時間が決して過去に戻ることがないため、ファイルシステムのタイムスタンプの逆転や、データベースのトランザクションログの順序破綻を引き起こすリスクを大幅に低減できます。
用途: 通常運用ではこちらが使用されます。
リスク: 緩やかな補正であるため、基準時間に完全同期するまでに時間がかかります。周波数調整レート（スリューレート）はNTPクライアントによって異なります。

現在のLinuxのchrony等のNTPクライアントでは、通常はSlewモードを利用します。
Stepモードによる補正は、デーモン起動直後の初期同期など、特定の条件に限定して許可する設定が一般的です。

| 用語                       | 意味                                                                 |
| -------------------------- | -------------------------------------------------------------------- |
| Step（ステップ）           | システムクロックを一度に正しい時刻へ補正する方式。                   |
| Slew（スリュー）           | システムクロックの進む速度を調整し、徐々に正しい時刻へ近づける方式。 |
| 単調増加性（Monotonicity） | 時刻が過去へ戻らず、常に前へ進む性質。                               |

## 7\. 補足：NTS（Network Time Security）


従来のNTPは、時刻同期を目的として設計されたプロトコルであり、通信相手が本物であることを十分に検証する仕組みを備えていませんでした。
そのため、悪意のある第三者が偽のNTPサーバーになりすまして誤った時刻を配信したり、通信内容を改ざんしたりするリスクが指摘されていました。

こうした問題を解決するために策定されたのが、NTS（Network Time Security）です。

NTSはTLSを利用してNTPサーバーを認証し、安全に暗号鍵を交換したうえで時刻同期を行います。
これにより、なりすましや中間者攻撃（Man-in-the-Middle Attack）による不正な時刻情報の注入を防ぐことができます。
NTSは「時刻をより正確にする技術」ではなく、「正しいNTPサーバーと安全に時刻同期を行うためのセキュリティ技術」と言えます。

現在では、chrony 4.0以降をはじめ、NTSに対応したNTPソフトウェアが普及しており、Cloudflareなどの公開NTPサーバーでもNTS対応サービスが提供されています。

| 用語                                         | 意味                                                                                                                                        |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| TLS（Transport Layer Security）              | インターネット通信を暗号化し、通信相手を認証するためのプロトコル。HTTPSでも利用される。                                                     |
| 中間者攻撃（Man-in-the-Middle Attack：MitM） | 通信の途中に第三者が入り込み、通信内容の盗聴や改ざんを行う攻撃。                                                                            |
| なりすまし攻撃                               | 正規のサーバーを装い、偽の情報を送信する攻撃。                                                                                              |
| Cloudflare                                   | インターネットの通信を高速化・安全化するクラウドサービスを提供する企業。NTSに対応した公開NTPサーバー（time.cloudflare.com）も提供している。 |

## まとめ

本記事では、Linuxにおける時刻管理の仕組みについて解説しました。

- Linuxには「ハードウェアクロック」と「システムクロック」の2種類の時計が存在する
- ハードウェアクロックはOS停止中の時刻を保持し、起動時にシステムクロックを初期化する
- システムクロックはLinuxカーネルが管理し、通常はRTCとは独立して動作する
- 水晶発振器などの物理的な特性により、時計は少しずつUTCからずれる
- 時刻のずれは、SSL/TLS証明書の検証失敗やKerberos認証エラー、ログ解析の困難化などの原因となる
- NTPはネットワーク経由で正しい時刻を取得し、システムクロックを定期的に補正する
- 時刻補正には「Step」と「Slew」があり、通常運用では時間の連続性を保てるSlew方式が利用されることが多い

Linuxでは普段あまり意識することのない「時刻」ですが、多くのシステムは正しい時刻を前提として動作しています。
