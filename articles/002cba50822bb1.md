## はじめに

- AWSのEC2にSSH接続する際、ローカルに保存した秘密鍵ファイルのアクセス権に関するエラーに遭遇しました。
- この記事では、Windows11のACL（アクセス制御リスト）の仕組み、SSH接続時のエラーの解除方法、WindowsのACLをPowerShellで操作する方法を紹介します。
- 間違い等あれば、指摘いただけると助かります。

## 結論

- Windowsでは、ACL（アクセス制御リスト）とACE（アクセス制御エントリ）を使って、ユーザーやグループごとのアクセス権を管理します。
- Windowsのアクセス制御では、オブジェクトのDACLとユーザーのAccess Tokenに含まれるSIDなどをもとに、実効アクセス権が判断されます。
- `icacls`コマンドを使うことで、ACLの確認やアクセス権の追加・削除、継承の設定などをコマンドラインから操作できます。
- 今回のSSHエラーは、秘密鍵ファイルに不要なアクセス権が継承されていたことが原因でした。継承されたアクセス権を削除し、必要なユーザーにRead権限を設定することで解消できました。


## 1\. SSH時に起きたアクセスエラー

AWSのEC2にローカルからSSHで接続しようとした際に、エラーに遭遇しました。

事前準備として、EC2のキーペアを作成し、ローカル（C:\Secrets\app\）に秘密鍵ファイル（app-ec2-key.pem）を保存していました。

`ssh`コマンドで秘密鍵のパスを指定してSSH接続を試みたところ、以下のエラーが出て、接続に失敗しました。

```Plain
Permissions for 'C:\Secrets\app\app-ec2-key.pem' are too open
```

何のエラーか調べてみると、秘密鍵ファイルのアクセス権が安全でない状態になっているため、OpenSSHが秘密鍵の使用を拒否していることがわかりました。

秘密鍵が他のユーザーなどに読み取られると、その秘密鍵を利用した認証を第三者に悪用される可能性があります。
そのため、OpenSSHは秘密鍵ファイルのアクセス権が広すぎる場合、その秘密鍵を使用した接続を拒否します。

今回のエラーも、秘密鍵ファイルに必要以上のアクセス権が設定されていることが原因と考え、アクセス権を確認することにしました。


## 2\. ACL（アクセス制御リスト）

まず、Windows環境のアクセス権について説明します。

Linuxでは、一般的に所有者・グループ・その他に対する「パーミッション」でアクセス制御を行います。

一方、Windowsでは、ACL（アクセス制御リスト：Access Control List）を用いて、「誰に対して」「どのような操作を許可／拒否するか」というアクセス制御ルールを定義します。

ACLは、ACE（アクセス制御エントリ：Access Control Entry）の集合として構成されています。
ACEは、特定のユーザーやグループなどに対して、どのようなアクセスを許可するか、または拒否するかを定義したアクセス制御ルールです。

例えば、あるファイルに以下のようなACLが設定されているとします。
```
ACL
├─ Alice → Readのみ許可
├─ Bob   → Read + Writeを許可
└─ Admin → Full Control
```

この場合、「Alice → Readのみ許可」が1つのACEです。

ACEとACLをまとめると、以下になります。

- ACE：特定のユーザーやグループに対する1つのアクセス制御ルール
- ACL：複数のACEをまとめたアクセス制御ルールの集合

実際のWindows環境では、個々のユーザーに直接権限を設定するよりも、部署や役職などをグループとしてまとめ、グループに対して権限を設定する方法が一般的です。

```
営業部 → Read + Write
経理部 → Read
管理者 → Full Control
```

例えば、上のように設定しておけば、ユーザーが部署を異動した場合も、所属するグループを変更することでアクセス権を管理しやすくなります。


## 3\. 設定可能なアクセス権

次に、ACEでどのような定義が可能なのかを見ていきましょう。

### 3\.1 基本アクセス権

ACEでは、ファイルやフォルダに対するアクセス権を細かく指定できます。
ファイルやフォルダだけでも、多数の個別権限があります。

一般的なアクセス権操作では、これらの個別権限をまとめた「基本アクセス権」を利用することが一般的です。
以下は、ファイルやフォルダに対する代表的な基本アクセス権を、概要として整理したものです。

| 基本アクセス権       | 概要                                               |
| -------------------- | -------------------------------------------------- |
| Full Control         | 読み取り・書き込み・削除・権限変更など、ほぼすべて |
| Modify               | 読み取り・書き込み・削除など。権限変更は含まない   |
| Read & Execute       | ファイルの読み取りと実行                           |
| List folder contents | フォルダ内のファイルやサブフォルダを一覧表示する   |
| Read                 | ファイル・フォルダの内容や属性を読み取る           |
| Write                | ファイル・フォルダへの書き込み                     |

### 3\.2 継承

アクセス権は、ファイルやフォルダごとに設定できます。

しかし、ファイルやフォルダを作成するたびに個別にアクセス権を設定するのは煩雑です。

そこで利用されるのが「継承」です。

継承を利用すると、親フォルダに設定したアクセス権を、配下の子フォルダやファイルに引き継ぐことができます。

例えば、以下のようなフォルダ構成があるとします。

```
C:\Parent
    │
    └─ child
        │
        └─ file.txt
```

C:\Parentからアクセス権を継承するように設定すると、継承可能なACEがchildフォルダやfile.txtに引き継がれます。

これにより、フォルダ以下に大量のファイルが存在する場合でも、親フォルダのアクセス権を設定することで、配下のファイルやフォルダをまとめて管理できます。

一方、秘密鍵など、親フォルダからアクセス権を引き継がせたくないファイルでは、継承を無効化することも可能です。


### 3\.3 許可と拒否

ACEでは、アクセスを許可（Allow）するか、拒否（Deny）するかを設定できます。

例えば、以下のようなACLがあったとします。
```
Users → Allow Read
Bob   → Deny Read
```
BobがUsersグループのメンバーだったとしても、Bobに対して個別にReadを拒否するACEが設定されています。

このように、グループに対してアクセスを許可しながら、特定のユーザーに対して個別にアクセスを拒否するという細やかな設定が可能です。

なお、ACLではACEの順序もアクセス判定に影響するため、単純に「拒否ACEが存在するか」だけでアクセス結果が決まるわけではありません。



## 4\. Windowsのアクセス制御の仕組み

ここまで説明したACL・ACEが、Windows内部でどのようにアクセス判定に利用されるのかを整理します。

Windowsのオブジェクトには、それぞれセキュリティ記述子（Security Descriptor）が付与されています。
セキュリティ記述子の内容は、以下の通りです。

- Owner：オブジェクトの所有者。所有者には、ACLを変更するための特別な権限上の意味があります。
- DACL（Discretionary Access Control List）：「誰に何を許可・拒否するか」の定義。
- SACL（System Access Control List）：「誰が何をしたら監査ログを残すか」の定義

DACLとSACLには、それぞれACEが設定されています。
簡略化すると以下のような構成です。

```
Security Descriptor
├─ Owner
├─ DACL
│   ├─ ACE
│   ├─ ACE
│   └─ ACE
└─ SACL
    ├─ ACE
    └─ ACE
```

Windowsのアクセス制御では、アクセス許可・拒否を定義するACLは、Security Descriptorに含まれるDACLとして管理されています。
ここからは、Windowsのアクセス許可を扱うACLを、より正確な用語である「DACL」として説明します。

### 4\.1 Access Tokenとアクセスチェック

ユーザーがオブジェクトへアクセスすると、WindowsはユーザーのAccess Token（アクセストークン）と、オブジェクトのDACLを使用してアクセス可否を判断します。

Access Tokenは、ユーザーSID（Security Identifier：セキュリティ識別子）、所属グループのSID、その他のセキュリティ情報などを含む情報です。

例えば、AliceがDevelopersとManagersというグループに所属している場合、Access Tokenには概念的に以下のような情報が含まれます。

```
Alice
├─ User SID
├─ Group SID: Developers
├─ Group SID: Managers
└─ その他のセキュリティ情報
```

一方、対象オブジェクトのDACLには、以下のように複数のACEが設定されているとします。

```
DACL
├─ Alice      → Read
├─ Bob        → Read + Write
├─ Developers → Read + Write
├─ Managers   → Read + Write
└─ Admin      → Full Control
```

Aliceがオブジェクトへアクセスすると、Access Tokenに含まれるユーザーSIDやグループSIDとDACL内のACEを照合し、ACEの許可・拒否や順序などを考慮して、要求されたアクセス権が許可されるかを判断します。

概念的には、以下のような流れです。

```
ユーザー
  ↓
Access Token
  ├─ User SID
  ├─ Group SID
  └─ その他のセキュリティ情報
        ↓
対象オブジェクトのDACL
        ↓
ACEを評価
        ↓
要求したアクセス権を許可できるか判断
```

このようにして判断された、ユーザーが実際に利用できるアクセス権を「実効アクセス権（Effective Access）」といいます。

なお、DACLではACEの順序もアクセス判定に影響します。
概念的には、WindowsはDACL内のACEを順番に評価し、要求されたアクセス権について許可または拒否を判断します。そのため、AllowとDenyのACEが混在する場合は、ACEの順序にも注意が必要です。

### 4\.2 DACLが空の場合とNULL DACL

DACLについて、注意が必要な状態があります。

DACLにACEが1つも設定されていない場合、アクセスを許可するACEが存在しないため、アクセスは拒否されます。

一方、DACLそのものが設定されていない状態を「NULL DACL」といいます。
NULL DACLではアクセス制御による拒否が行われないため、そのオブジェクトに対して要求されたアクセスがすべて許可されます。

「DACLにACEが1つもない」と「NULL DACL」は似ていますが、挙動は大きく異なるため注意が必要です。


## 5\. icaclsコマンドの使い方

PowerShellなどのコンソール上で、ファイルやフォルダのアクセス制御を行う場合は`icacls`コマンドを利用できます。

### 5\.1 権限の表示


```Bash
icacls <ファイルやフォルダのパス>
```

例えば、以下のような結果が表示されます。

```Plain
BUILTIN\Administrators:(I)(F)
NT AUTHORITY\SYSTEM:(I)(F)
BUILTIN\Users:(I)(RX)
Alice:(M)
Bob:(DENY)(W)
```

BUILTIN\AdministratorsやBUILTIN\Usersの「BUILTIN」 は、Windowsに組み込まれているローカルグループを指します。
そのため、BUILTIN\Administratorsは「このWindowsコンピューターのAdministratorsグループ」を表し、BUILTIN\Usersは「このWindowsコンピューター上のUsersグループ」 を表します。

NT AUTHORITY\SYSTEMは、通常のユーザーではなく、Windows自身やサービスなどが利用するWindowsのSYSTEMアカウントを指します。

AliceとBobはユーザー名です。

`icacls`コマンドでは、アクセス権だけでなく、ACEの継承状態などが（）内に記号で表示されます。
代表的な表記は、以下の通りです。


| 表記   | 意味                                   |
| ------ | -------------------------------------- |
| `F`    | Full access                            |
| `M`    | Modify                                 |
| `RX`   | Read & Execute                         |
| `R`    | Read                                   |
| `W`    | Write                                  |
| `I`    | 継承されたACE                          |
| `OI`   | 子ファイルへの継承                     |
| `CI`   | 子フォルダへの継承                     |
| `IO`   | 自身には適用せず、子に継承するためだけ |
| `DENY` | 拒否                                   |

`icacls`コマンドの出力では、許可ACEに「Allow」という文字列は表示されず、(F) や (M)、(RX) などのアクセス権が表示されます。
拒否ACEの場合は、(DENY) が付加されます。

上の表記を見ると、先ほどの`icacls`コマンドで表示したアクセス制御の設定が理解できます。
簡略化すると、以下の通りです。

| ACE                     | 読み方                                 |
| ----------------------- | -------------------------------------- |
| `Administrators:(I)(F)` | Administratorsに継承されたFull Control |
| `SYSTEM:(I)(F)`         | SYSTEMに継承されたFull Control         |
| `Users:(I)(RX)`         | Usersに継承されたRead & Execute        |
| `Alice:(M)`             | AliceにModify                          |
| `Bob:(DENY)(W)`         | BobにWriteを拒否                       |

この設定を見ると、AliceにはModifyの権限が与えられているように見えます。
しかし、実際には、Aliceが所属するグループ、親からの継承、拒否ACEなどの情報を総合して実効権限が計算されるため、このACEだけを見てAliceの実効アクセス権がModifyであるとは断言できません。

### 5\.2 権限の追加

C:\dacl-testファイルに、CarolのRead権限を追加したい場合は、以下のコマンドを実行します。

```Bash
icacls "C:\dacl-test" /grant Carol:(R)
```

### 5\.3 権限を削除

C:\dacl-testファイルから、Aliceに対するACEを削除したい場合は、以下のコマンドを実行します。

```Bash
icacls "C:\dacl-test" /remove Alice
```

この操作で削除されるのは、Aliceに直接設定されたACEです。
Aliceが所属するグループ経由で付与された権限は削除されません。

### 5\.4 権限をバックアップする

DACLはファイルに保存してバックアップできます。
C:\dacl-testのDACLをdacl_backup.txt に保存するには、以下のコマンドを実行します。

```Bash
icacls "C:\dacl-test" /save dacl_backup.txt
```

### 5\.5 権限を復元する

保存した権限を利用して、権限を復元できます。
C:\dacl-testのDACLをdacl_backup.txtを用いて復元する場合には、以下のコマンドを実行します。

```Bash
icacls "C:\dacl-test" /restore dacl_backup.txt
```

### 5\.6 継承の設定

例えば、以下の構成で、C:\dacl-test から child にアクセス権を継承させているとします。

```
C:\dacl-test
└─ child
```

継承を有効にし、親フォルダから継承可能なACEを子フォルダへ継承したい場合は、以下のコマンドを実行します。

```Bash
icacls "C:\dacl-test\child" /inheritance:e
```

逆に、継承を無効にし、すでに継承しているACEを削除したい場合は、以下のコマンドを実行します。

```Bash
icacls "C:\dacl-test\child" /inheritance:r
```

すでに継承しているACEを残したまま継承を無効にしたい場合は、以下のコマンドを実行します。

```Bash
icacls "C:\dacl-test\child" /inheritance:d
```

## 6\. アクセスエラーの対応方法

DACLについて学習したところで、冒頭のエラーを解消します。
エラーの原因は、秘密鍵ファイルのアクセス権が広すぎることでした。

まずは、秘密鍵ファイルのアクセス権を確認します。

```Bash
icacls "C:\Secrets\app\app-ec2-key.pem"
```

実行結果は以下の通りです。

```Plain
BUILTIN\Administrators:(I)(F)
NT AUTHORITY\SYSTEM:(I)(F)
BUILTIN\Users:(I)(RX)
NT AUTHORITY\Authenticated Users:(I)(M)
```

(I)は継承されたアクセス権を表します。
ファイルに、継承したアクセス権が付与されていることがわかります。

SSH接続で問題になるのは、以下の部分です。

```Plain
BUILTIN\Users:(I)(RX)
NT AUTHORITY\Authenticated Users:(I)(M)
```

UsersにRX（読み取りと実行）とAuthenticated UsersにM（変更）のアクセス権が付与されています。
これらのACEによって、現在のユーザー以外のユーザーにも、グループ経由で秘密鍵を読み取れる権限が付与される状態になっていました。
この状態が、OpenSSHが「too open」と判断した原因だと考えられます。

エラーの解消のため、継承されたアクセス権を削除し、現在のユーザーにRead権限を設定します。
Linuxの600のように、所有者以外からのアクセスを制限した状態に近い考え方です。

まずは、継承しているアクセス権を削除します。

```Bash
icacls "C:\Secrets\app\app-ec2-key.pem" /inheritance:r
```

その後、「必要最小限の権限」とするために、現在のユーザーにRead権限を設定します。

```Bash
icacls "C:\Secrets\app\app-ec2-key.pem" /grant:r "$env:USERNAME:R"
```

`/grant:r` の 「:r」 は、指定ユーザーに対する既存の明示的な許可ACEを置き換える指定です。

この状態で再度アクセス権を確認します。

```Bash
icacls "C:\Secrets\app\app-ec2-key.pem"
```

結果は以下の通りです。

```Bash
user:(R)
```

user(現在のユーザー)にRead権限が設定され、先ほど確認した継承ACEはなくなっています。
この状態で、再度SSH接続を試みると、問題なく実行できました。

継承されたアクセス権を削除し、現在のユーザーにRead権限を設定したところSSH接続が成功しました。このことから、今回のエラーは秘密鍵ファイルのアクセス権設定が原因だったと判断できます。


## まとめ
- WindowsではACL（アクセス制御リスト）を使って、ユーザーやグループごとにファイル・フォルダへのアクセス権を制御する。
- ACLはACE（アクセス制御エントリ）の集合であり、ACEによって「誰に」「どの操作を」「許可／拒否するか」を定義する。
- Windowsでは、Security DescriptorのDACLに設定されたACEと、ユーザーのAccess Tokenに含まれるSIDを照合して実効アクセス権を判断する。
- `icacls`コマンドを使うことで、ACLの確認やアクセス権の追加・削除、継承の有効・無効化などをコマンドラインから操作できる。
- 秘密鍵などの重要なファイルは、必要なユーザーだけがアクセスできるよう、最小権限でACLを設定することが重要である。
- 今回のEC2へのSSHでは、継承されたアクセス権を削除し、現在のユーザーにRead権限だけを付与することでエラーを解消した。
