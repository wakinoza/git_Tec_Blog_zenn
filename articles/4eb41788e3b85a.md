## はじめに

- AWSの学習のため、自作Spring BootアプリをAWS上に段階的にデプロイしています。
- この記事では、個人開発時に実装した最低限のセキュリティ対策を説明します。
- 間違い等あれば、指摘いただけると助かります。

## 結論

セキュリティ対策として、Security Groupによる通信制御、OSのパッケージ更新、MySQLのインターネットからの直接接続を制限、専用Linuxユーザーによるアプリ実行、Secrets Managerによる認証情報管理と、IAMロールによる最小権限の設定を実施しました。
一方、SSHによる管理アクセスやHTTP通信などは今後の改善課題として残っています。

なお、これらは個人開発環境で実施した最低限の対策であり、実運用を想定した場合には、HTTPS化、管理アクセスの強化、監視・ログ管理など、追加の対策が必要です。

## 動作環境

- Windows11
- Visual Studio Code
- Oracle Java 21
- Spring Boot 4
- MySQL 8.4.6
- AWS
    - EC2 : Amazon Linux 2023

## 1\.アプリケーションの構成

アプリケーションは、Java/Spring Bootで書かれたTodoアプリです。
DBにMySQLを利用しています。
コードは、GitHubで公開しています。

https://github.com/wakinoza/todo_app

今回、アプリケーションをAWSにデプロイしました。

AWSのサービスを理解することを目的としているため、まずはEC2単体のシンプルな構成を選択しました。

今後、RDS・ALBの追加、Dockerでのデプロイなど様々なサービスを利用したデプロイを検証する予定です。

現在のAWS構成は以下の通りです。

```
Internet
    │
    ▼
Internet Gateway
    │
    ▼
Public Subnet
    │
    ▼
EC2
 ├─ Spring Boot
 └─ MySQL
```

VPCにPublic Subnetを１つ作成し、その中にEC2インスタンスを１つ配置しています。
アプリケーションのJARとMySQLが１つのEC2の中で起動する、非常にシンプルな構成です。

他のサービスを利用するデプロイの基準として、最小限のサービスでのデプロイを実装しました。

最低限の構成ではありますが、インターネット上にサービスをデプロイするため、最低限のセキュリティ対策を実装しました。
この記事では、今回のデプロイで行ったセキュリティ対策について、説明していきます。

## 2\. Security Group

Security Groupは、EC2などのAWSリソースに対する仮想ファイアウォールです。
リソースへのインバウンド（受信）とアウトバウンド（送信）の通信について、許可するトラフィックを設定できます。

Security Groupを付与されたリソースは、明示的に許可されたトラフィックを受け入れますが、許可されていない通信は基本的に受け入れられません。

また、Security Groupはステートフル（許可した通信の戻り通信を自動的に許可する仕組み）という仕組みを持つため、許可した通信の戻り通信は自動的に許可されます。


### 2\.1 SSHを自宅IPに制限

EC2へのSSHが必要であったため、自宅のグローバルIPに限定して22番ポートを解放しました。

```
SSH : TCP 22
Source : 自宅のグローバルIP/32
```

### 2\.2 MySQL 3306番ポートを外部公開しない

今回は、1つのEC2上にアプリケーションとDBの両方を起動しています。
そのため、DBであるMySQLにインターネットから直接接続させる必要がありません。

したがって、Security GroupではMySQL用のTCP 3306番ポートへのインバウンド通信を許可していません。

## 3\. OS・アプリケーション実行環境への対策

### 3\.1 EC2作成直後にOSのパッケージを更新

OSのパッケージには、既知の脆弱性（攻撃に悪用される可能性のあるソフトウェア上の問題）を修正するセキュリティ更新が含まれています。

EC2作成時点で利用可能なパッケージ更新を適用するため、EC2作成直後にパッケージを更新しました。

具体的には、以下のコマンドを実行しました。

```Bash
sudo dnf update -y
```

### 3\.2 Spring Bootを専用Linuxユーザーで実行

EC2では、Amazon Linux 2023を利用しました。

root権限でアプリケーションを実行すると、アプリケーションの脆弱性を悪用された場合に、攻撃者がroot権限でOS上の操作を行えるリスクがあります。

そのため、EC2上では、Spring Bootを専用の一般ユーザー「springboot」で実行しました。

## 4\. 認証情報とAWS権限の管理

### 4\.1 認証情報をSecrets Managerで管理

AWSにおいて機密情報を管理するサービスとして、AWS Secrets Managerがあります。

ローカル環境では、DBの認証情報は.envファイルで管理していました。
今回のデプロイにおいて、DBのユーザー名とパスワードを、AWS Secrets Managerに保存しました。

これにより、DBの認証情報をアプリケーションのソースコードなどにハードコードせずに管理できます。
アプリケーションからSecretを取得するための権限は、次節で説明するIAMロールによって付与しました。

```
EC2
 │
 │ IAMロール
 ▼
Spring Boot
 │
 │ GetSecretValue
 ▼
Secrets Manager
 │
 ▼
DB認証情報
```

### 4\.2 EC2にIAMロールを付与してSecretを取得

AWS Secrets Managerに保存した認証情報をアプリケーションから取得するため、EC2にIAMロールを関連付けました。

EC2上のSpring Bootアプリケーションは、このIAMロールに付与された権限を利用してSecrets ManagerのAPIを呼び出し、DB認証情報を取得します。

IAMロールに許可した権限は以下の通りです。

```
secretsmanager:GetSecretValue
対象リソース：todo-app/dbのみ
```

最小権限を意識し、Spring Bootアプリケーションがシークレットを取得するために必要な `secretsmanager:GetSecretValue`のみをIAMロールに許可しました。
また、対象リソースもアプリケーションのDB認証情報を保存したシークレットに限定しています。

## 5\. 残っているセキュリティ上の課題

### 5\.1 SSHによる管理アクセス

EC2へのアクセスは、現時点ではSSHを使用しています。

アクセス元を自宅IPアドレスに限定していますが、SSH用の22番ポートを利用した管理アクセスは残っています。

今後は、SSH用のポートを解放する必要がないAWS Systems Manager Session Managerへの移行を検討しています。

### 5\.2 HTTP通信

現時点では、Spring BootへのアクセスはHTTPで行っています。

今後、ALBを導入する際にHTTPSを利用し、クライアントとALB間の通信を暗号化する構成を検討しています。

### 5\.3 Secrets Manager の自動ローテーション

現時点では、シークレットの自動ローテーションを設定していません。

DB認証情報の自動ローテーションを設定すると、Secrets ManagerとDB側の認証情報を連携して定期的に更新できます。
これにより、認証情報が長期間同じ値のままになることを防ぎ、認証情報が漏洩した場合に、その認証情報が利用され続ける期間を短縮できます。

## まとめ

- Security Groupで不要なインバウンド通信を制限した
- MySQLの3306番ポートをインターネットへ公開しなかった
- OSのパッケージを更新した
- Spring Bootをrootではなく専用Linuxユーザーで実行し、権限を必要最小限にした
- Secrets Manager＋IAMロールでDB認証情報を管理した
- SSH管理やHTTPS化などは今後の課題とした
