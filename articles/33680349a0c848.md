## はじめに

- 現在、LinuCレベル１の取得を目指して勉強中です。
- Linuxの勉強をしていると、様々な場所でプロセス、スレッド、タスクなどの用語が登場します。
なんとなく意味は分かりますが、違いは何かと聞かれても答えられそうにないので、言葉の定義を調べてみました。
- 間違い等あれば、指摘いただけると助かります。


## 結論

現代のLinuxにおけるプロセス、スレッド、タスク、およびリソース管理は、以下の3つの仕組みが相互に連携することで成り立っています。

- 論理管理レイヤー（POSIX / pthread / シェル）:
  アプリケーションの移植性を担保する標準規格。プロセス（仮想メモリ・FDの隔離壁）やスレッド（メモリ共有型の実行枠）、およびそれらを束ねるセッションやプロセスグループ、ジョブといった「論理的な境界」を定義します。
- 物理制御レイヤー（Linuxカーネル機能としての cgroups v2 と、その管理を担う systemd）:
　物理リソース（CPU、メモリ、I/O）の分配と隔離を行うカーネルの機能が「cgroups」です。現代のLinuxでは、初期化システムである「systemd」がこのcgroupsのインターフェースとして機能し、スライス、サービス、スコープという階層構造を用いて論理レイヤーのプロセス群にハードウェア資源の上限を課します。
- カーネル実行スケジューリングレイヤー（Linuxカーネル）:
  最深部の実行基盤。カーネル内部では、プロセスもスレッドも「task_struct」を基盤とした共通の仕組みで表現され、共有するリソースの違いによって区別されています。

この記事では、これら3つの仕組みがどのように役割分担しながら連携しているのかを整理していきます。

## 1\. POSIXとpthread

まずは、プロセスの扱い方がどのように変わっていったのか、その歴史をざっくり追っていきます。

初期のコンピュータ（UNIX系）では、処理（プロセス）の流れは、OSによって異なっていました。そのため、AというOSで動くアプリが、BというOSでは動かないという問題が発生していました。

そこで登場したのが、「POSIX（Portable Operating System Interface）」です。

POSIXは、IEEEが策定した、アプリケーションがOSの機能を利用するための標準インターフェース規格です。
各OSがPOSIXという共通の規格を守ることで、POSIX準拠でC言語のプログラムを書けば、LinuxでもmacOSでも、ソースコードをそのままコンパイルして動かすことが可能になり、プログラムの移植性を高めることができました。

本記事のテーマに関係するPOSIXの主要な概念として、以下の4つがあります。

- 1. fork() : 現在のプロセスを複製して新しいプロセス（子プロセス）を作り出すためのシステムコール。（※実際のLinuxカーネル内部の実装では、メモリを即座に丸ごとコピーするのではなく、「Copy-on-Write (CoW)」という最適化技術を用いることで、高速なプロセス生成を実現しています。）
- 2. exec() : 現在のプロセスのPIDを維持したまま、実行中のプログラムイメージを別のプログラムへ置き換えるシステムコール
- 3. プロセスグループ (Process Group) : パイプライン（|）などでつながった複数のプロセスを、1つのプロセスグループ（PGID）に所属させる。これにより、カーネルは複数のプロセスに一斉に終了シグナル（SIGINT）を送ることができる
- 4. セッション (Session) : 複数のプロセスグループをさらに大きくまとめた、ログインからログアウトまでの一連の活動単位。ユーザーがログインしたときに1つのセッション（SID）が作られ、その中で起動したシェルやプロセスグループはすべてそのセッションに帰属します。ユーザーが端末を閉じたりネットワークが切断されたりすると、カーネルは端末を制御していたセッションリーダー（シェル）やフォアグラウンドのプロセスグループに対してハングアップシグナル（SIGHUP）を送ります。通常はこれを受けたシェルが、自身の管理下にあるジョブ（バックグラウンドプロセス含む）にも終了シグナルを伝播させるため、一括でプロセスが終了します。

しかし、プロセスの流れは規格化されましたが、マルチスレッドの並行処理までは統一化されていませんでした。
そこで、1990年代にはマルチスレッドの規格として、IEEEが新たに「POSIX thread（pthread）」を策定しました。

pthreadは、「複数の処理（スレッド）がメモリ空間を共有しながら並行して動く」という並行実行モデルを定義した規格です。
各OSが「pthread」を守ることにより、特定のOS用に書かれたマルチスレッドプログラムを別のOSに移植することが可能になりました。

POSIXはPOSIX Threads（pthread）仕様を取り込み、マルチスレッドプログラミングも標準化しました。

Linuxにおいては、当初LinuxThreadsという独自実装が使われていましたが、カーネル2.6以降でPOSIXに完全準拠したNPTL（Native POSIX Thread Library）が導入されたことで、1つのメモリ空間を共有し、プロセス切り替えよりもオーバーヘッドの少ない並行処理を行うための土台が標準化されました。

## 2\. cgroupsの導入

POSIXやpthreadにより、様々なOSでマルチスレッドのプログラムを移植できるようになりました。
しかし、ここで新しいニーズが生まれます。
それが、リソース管理です。

1台のサーバー上で複数のサービスや仮想環境を同時運用するようになると、特定のサービスがCPUやメモリを使い切らないよう制御する必要が生まれました。
POSIXにも ulimit（setrlimit システムコール）というリソース制限の仕組みはありましたが、以下のような欠点がありました。

- プロセス単位（またはユーザー単位）でしか制限できず、サービス（アプリケーション）単位での制限ができません。
- リソースの「階層的な制限（グループ化）」や、親ノードから子ノードへの「動的なリソースの再分配（重み付け制御）」が不可能です。

これらのリソース管理のニーズに応えるため、Linuxでは「cgroups（Control Groups）」という独自のリソース管理システムを導入しました。
cgroupsは、複数のプロセスをグループとしてまとめ、そのグループ全体に対してリソース(CPU、メモリ、I/O)を階層構造（ツリー形式）で制御します。

POSIX規格などが定める「プロセスグループ」がシグナル送信などの論理的な制御を目的とするのに対し、cgroupsはCPUやメモリといった物理リソースや、プロセス生成数の上限（PID制限）といったシステムリソースの分配・隔離に特化しています。

現代のLinuxのプロセスは、POSIXの互換性を守りつつ、リソース管理は cgroups で行う構造になっています。
cgroupsには、v1とv2という2つのバージョンがあり、現在ではv2が主流になっています。

:::message
このcgroupsによる「プロセスをグループにまとめ、物理リソースを厳密に隔離する」という仕組みは、現代のDockerなどのコンテナ技術を支える土台となっています。コンテナが独立した環境のように振る舞えるのは、namespaceによる隔離と、cgroupsによるリソース制御が組み合わさっているためです。
:::

## 3\. カーネルによる実行スケジューリング

現代のLinuxでは、POSIXがプロセスやスレッドといった論理的な実行単位を定義し、cgroupsがそれらに対するリソース制御を提供しています。

では、なぜcgroupsはプロセスやスレッドのCPU使用率やメモリ消費量を制御できるのでしょうか。
その鍵となるのが、Linuxカーネルが管理する「タスク（task_struct）」です。

Linuxカーネルの内部では、プロセスもスレッドも「task_struct」を基盤とした共通の仕組みで表現され、共有するリソースの違いによって区別されています。

cgroupsはこの最深部に割り込み、各タスクに対して「お前はサービスAのcgroup配下だからCPUはここまで」「お前はスコープBだからメモリはここまで」という物理的な制約を強制します。

つまり現代のLinuxでは、POSIXがプロセスやスレッドといった論理的な実行単位を定義し、cgroupsがそれらに対するリソース制御を提供し、最終的にLinuxカーネルが task_struct 単位でCPUへスケジューリングしています。

これら3つの仕組みは厳密な親子関係ではなく、それぞれ異なる観点から同じタスク群を管理しています。
役割の違いを整理すると、概ね以下のようになります。
（以下は厳密な実装階層ではなく、それぞれの管理対象を理解するための概念図です。）

```plain
【リソース管理の軸（systemd / cgroups v2）】    【論理・実行管理の軸（POSIX / Linuxカーネル）】
  └── スライス (.slice)                         セッション (SID)
        ├── サービス (.service)                   └── プロセスグループ (PGID)
        └── スコープ (.scope)                         └── プロセス (PID)
              │                                           └── スレッド (TID)
              │                                                │
              └──────────────────────┐ ┌───────────────────────┘
                                     ▼ ▼
                       【カーネル実行スケジューリングレイヤー】
                        タスク (task_struct) ── スケジューラが扱う真の実行単位
```

## 4\. Linuxのタスク階層構造

前章のツリー構造を参考に、各レイヤーの詳細を説明します。

### 4\.1 スライス (Slice)

現代のLinuxにおいて、cgroupsはツリー構造でリソースを管理しています。そのツリーの最上位でリソース割り当てを決めているのがスライス（Slice）です。

systemdによるcgroups管理において、中間ノードに当たるのがスライスであり、末端ノード（リーフ）に当たるのが後述するサービス（Service）やスコープ（Scope）です。

cgroups v2では、リソースコントローラを有効にした中間ノードにプロセスを配置しないという運用ルール（No Internal Process Rule）が採用されています。
そもそも標準の`kill`コマンドは「PID」や「PGID」に対してシグナルを送る仕組みであるため、ユーザーが標準コマンドでスライスを直接指定してプロセスを一括終了するような操作は基本的には行いません
（※近年cgroups v2自体には cgroup.kill という一括終了の機能も追加されましたが、実運用ではsystemdのインターフェースを介してサービスやスコープ単位で安全にライフサイクルを制御するのが一般的です）

スライスはその代わり、「スライスに定められたCPUやメモリの分配比率を厳密に制御する」という役割に特化しています。

かつて、POSIXの古い制限（ulimit）はPID単位で制限をかけていました。
しかし、プロセスそのものに制限をかけても、プロセスが増殖（fork()）していくと、「１つ１つのプロセスは制限を守っているが、合計するとメモリを食いつぶしている」という状態が発生してしまいます。

そこでスライスは、配下にあるすべてのサービスやスコープが消費する「リソースの合計値」に上限を課します。
これにより、内部でどれだけプロセスが増殖しようとも、スライスという外枠に割り当てられたリソース総量を絶対に突破させない制御が可能になります。
スライスとは、システム全体のCPU/メモリを食いつぶさないための防波堤のような区分なのです。

標準的なLinuxシステムでは、ルートスライス（-.slice）の配下に、system.slice、user.slice、machine.slice といった主要なスライスが用意されています。
スライス内で、リソースの分配比率をさらに細分化する場合は、スライスの配下に「サブスライス」を設けます。

- system.slice（システムスライス）
Webサーバー（nginx）やSSH（sshd）など、OSの維持やサービス提供に必要な「バックグラウンドデーモン」が利用する枠です。

- user.slice（ユーザースライス）
管理者がSSHでログインした際のシェル（bash）など、「人間が操作するプロセス」が利用する枠です。ユーザーIDごとに1つのサブスライスが作成されます。

- machine.slice（マシンスライス）
KVMなどの仮想マシンや、コンテナが利用する枠です。ホストOS自身の処理と、仮想マシン・コンテナ間のリソース割り当てを完全に切り分けるための区分として機能します。

### 4\.2 サービス/スコープ (Service/Scope)

systemdによるcgroups管理において、末端ノード（リーフ）に当たるのがサービス（Service）やスコープ（Scope）です。
個別のアプリケーション単位のレイヤーであり、「メモリは何GBまで」といった具体的なcgroupsの設定が可能です。

どちらもcgroups v2のルールに従ってリソースの制限を受け、PIDを保持する点では同じですが、その「プロセスの生まれ方」が異なります。

サービスは、/etc/systemd/system/ などの下にある設定ファイル（ユニットファイル）をsystemdが読み込み、systemd自身が親となって起動したプロセス群を指します。起動から停止まで、すべての生存期間をsystemdがコントロールします。例えば、nginx.service（Webサーバー）、sshd.service（リモート接続受付）、crond.service（定期タスク実行）などシステムに常駐するデーモンなどがこれに当たります。

スコープは、systemdの外の世界（シェルや別アプリ）で起動したプロセス群を指します。
systemdの管理外で生まれるプロセスであっても、cgroupsの制限下に置けなければ、厳密なリソース管理はできません。そのため、systemdの外の世界で起動したプロセスを「スコープ」という枠に紐づけることで、後付けでcgroupsの制限をかけています。例えば、session-1.scope（ユーザーがSSHログインした際に開いた bash などのシェルや、その中で実行したコマンド群）などがこれに当たります。

|                 | サービス（.service）               | スコープ（.scope）                              |
| --------------- | ---------------------------------- | ----------------------------------------------- |
| プロセス（PID） | 保持する                           | 保持する                                        |
| 誰が起動するか  | systemd が直接起動する             | systemd外で生成されたプロセスを収容する         |
| 設定ファイル    | 必要（.service ファイル）          | 原則不要（プログラムがAPI経由で動的に生成する） |
| 主な用途        | バックグラウンド常駐デーモンの管理 | ユーザーセッション等のリソース後付け制限        |

### 4\.3 セッション (Session)

POSIXの論理管理において、最上位に位置する管理枠が「セッション」です。

セッションはユーザーのログインや、プロセスのデーモン化（独立）の際に実行される `setsid()` システムコールなどによって作られる、論理的な一連の活動単位です。
ユーザーがシステムにログインした際、最初に起動するシェルを起点として1つのセッションID（SID）が生成され、その中で起動したシェルやプロセスグループはすべてこのセッションに帰属します。

セッションの役割は「ライフサイクルの連動」です。
ユーザーが端末を閉じたりログアウトしたりすると、通常は関連するプロセスグループへハングアップシグナル（SIGHUP）が送られます。
（実務で長時間かかるジョブをバックグラウンドで安全に実行し続けたい場合は、`nohup <コマンド> &` を使用するか、tmux や screen を利用して、シェルセッションとプロセスツリーを切り離す設計が必要です。）

実は、多くの対話的なログイン環境では、POSIXのセッションは 前節のスコープで紹介した「session-*.scope」と対応付けられています。
（ただし、`setsid()` による新しいセッション生成やデーモン化などのケースでは、必ずしも単純な1対1対応になるとは限りません）

伝統的なPOSIXの世界で「セッション」と呼ばれている論理的な塊に対し、cgroupsで物理リソースの制限をかけるために、systemdが後付けで紐づけた枠（スコープ）の名前が session-1.scope なのです。

セッションは、cgroupsという物理レイヤーとPOSIXという論理レイヤーの境目に当たる部分なので、混乱しやすいところです。

### 4\.4 プロセスグループ (Process Group)

プロセスグループは、パイプ(|)などで繋がった複数のプロセスを、1つのまとまりとして同期させるための論理枠です。
複数のプロセスが同じプロセスグループID（PGID）を共有します。
`Ctrl + C` を押したときに、関係する複数のプロセスに一斉にシグナルを届けるための境界（バウンダリ）となります。

具体例を見ていきましょう。
以下のコマンドを実行したとします。

```Bash
cat access.log | grep "404" | wc -l
```

3つのコマンドがパイプでつながれています。
このコマンドは、内部では`cat`, `grep`, `wc` という3つのプロセス（PID）が同時に起動しますが、1つのPGIDを共有しています。
そのため、これら3つのプロセスは、同じ1つのPGIDでまとめて制御可能です。

### 4\.5 プロセス (Process)

プロセスは、POSIXの世界において、プログラムが具体的な処理を行うためのベースとなる論理枠です。
他のプロセスから隔離された独自の仮想メモリ空間やファイル記述子が割り当てられています。

:::message
ファイル記述子（ファイルディスクリプタ / FD: File Descriptor）とは、カーネルが、プロセスに対して発行する「開いているファイルや接続の管理番号（整理番号）」のことです。

もしプロセスが、ハードディスクの物理的な記憶場所やネットワークのメモリ領域を直接操作してしまうと、プログラムのバグや予期せぬ衝突によって、他の重要なデータを破壊してしまうリスクがあります。そのため、ファイルの中身や状態は、ユーザー（プロセス）からは絶対に見えないカーネル空間に厳重に保管されています。

プロセスがファイル等を操作したい場合は、まずカーネルにファイルのオープンを依頼（システムコール）します。カーネルはファイルを開き、その状態を記録した管理表のインデックス番号である「FD」をプロセスに返します。

プロセスは、データの読み書きを行いたいときは常にこの「FD（管理番号）」をカーネルに提示します。カーネルはその番号を頼りに目的のファイル情報を引き出し、プロセスのメモリ空間（バッファ領域）へと安全にデータをコピーします。
:::

プロセスは、POSIXの伝統的なシステムコールである`fork()` と `exec()` によって作られます。
動いている親プロセスの実行状態を引き継いだ子プロセスを作成し（fork）、その子プロセスが新しいプログラムをメモリ上に読み込む（exec）ことで、新しいプロセスが誕生します。

固有の「プロセスID（PID）」を持っており、`kill <PID>` コマンドを使って、そのプロセス単体を終了させたり、CPUの優先度を変更したりすることが可能です。

### 4\.6 スレッド / タスク (Thread / Task)

プロセスの内部で、実際にCPUを動かして具体的な計算や処理を担当しているのが「スレッド」であり、それをLinuxカーネルが管理する際の実体が「タスク」です。

【スレッド (Thread)：プロセス内の「実行の筋道」】
プロセスは独自のメモリ空間を持った「安全な部屋」ですが、その部屋の中で実際に働く作業員のようなものがスレッドです。
TID（Thread ID）を保有しています。

かつては1つのプロセスに1つのメインスレッドしかありませんでしたが、現代のマルチコアCPUの性能を引き出すため、1つのプロセス内で複数のスレッドを同時に動かす「マルチスレッド（POSIXにおいては pthread）」が標準的に使われています。

スレッドの最大の特徴は、「同じプロセス内のメモリ空間（変数や開いているファイル記述子など）を、全員で共有して働く」という点です。
プロセスを新しく増やす（fork()）と、ページテーブルの複製やアドレス空間管理が必要になるため一定のオーバーヘッドが発生します。
しかしスレッドであれば、一般にプロセス切り替えよりもアドレス空間切り替えのコストが小さいため、スレッド切り替えの方が軽量です。

【タスク (Task)：カーネル最深部での「真の姿」】
POSIXの論理レイヤーから見ると、「プロセス」と「スレッド」は明確に区別されています。
しかし、Linuxカーネルの実行スケジューリングレイヤーから見ると、両者に本質的な違いはありません。

Linuxカーネルは、CPUの計算時間を割り当てる実行単位をすべて 「タスク（Task）」 という共通の枠組みで管理しています。
このタスクを表す内部のデータ構造が「task_struct」です。

カーネルの実行スケジューリングレイヤーにおいては、「プロセスの作成」はメモリやFDを共有しない新しいタスクを作ること、「スレッドの作成」はメモリやFDを共有する新しいタスクを作ることとして処理されています。

Linuxでは、`fork()` や `pthread_create()` は内部的に `clone`系のシステムコールを利用して実装されています。
`clone()` を呼ぶ際に、「メモリ空間（CLONE_VM）やファイル記述子（CLONE_FILES）を親と共有する」というフラグを立てれば「スレッド」になり、共有しなければ独立した「プロセス」になります。
カーネルから見れば、どちらも等しく並列に並んだ「タスク」の1つとして扱われ、順番にCPUへと投入されていきます。

:::message
【カーネル内部のID逆転現象】
POSIXの規格を守るため、Linuxカーネル内部（task_struct）では、逆転したようなIDの割り当てが行われています。

task.pid ＝ 内部的なタスク固有のID（ユーザー空間で見える TID：スレッドID）

task.tgid ＝ スレッドグループのリーダーID（ユーザー空間で見える PID：プロセスID）

カーネルにとっては「すべては固有の pid を持つ独立したタスク」であり、それらが同じ tgid を共有している状態を、ユーザー空間に対して「1つのプロセスの中の複数のスレッド」として見せかけているのです。
:::

## 5\. ジョブって何？

これまで説明してきたツリー構造には、どこを見ても「ジョブ」という要素がありませんでした。
では、シェル操作で日常的に使われる「ジョブ」とは、一体何なのでしょうか？

結論から言うと、「ユーザーがシェルを通じて直接命令したプロセス（グループ）」を、ユーザー空間側で扱いやすくするために抽象化したものが「ジョブ」と呼ばれています。

カーネル内部には「ジョブ」というデータ構造はありません。
カーネルにとっては、シェル管理のタスクもシステム常駐のデーモンも、プロセスグループ（PGID）という同じデータ構造（struct signal_struct 内のメンバなど）として管理しています。

では、ジョブとそれ以外のプロセスグループの違いはどこにあるのでしょうか。

それは、「そのプロセスグループが所属するセッションが、制御端末（TTY）を保持しているかどうか」にあります。

歴史的に、1つのターミナル（TTY）を複数のプロセスグループで共有・切り替えするために、カーネルには `tcsetpgrp()`（端末の制御権を特定のPGIDに与えるシステムコール）という仕組みが用意されました。シェルはこのカーネルの機能を利用し、ユーザーに対して「ジョブ」という直感的なインターフェースを提供しています。

つまり、カーネルが管理するプロセスグループのことは単にプロセス（グループ）と呼び、そのうち「シェルが制御対象として管理するプロセスグループ」を、特別に「ジョブ」という便利な名前で呼んでいるにすぎません。

内部的にはどちらも同じカーネルのプロセスグループ管理機構（PGID）を使っていますが、シェルが制御端末（TTY）の管理機能を使ってユーザーに見せている「ユーザー用インターフェース」こそが「ジョブ」の正体なのです。


## まとめ

本記事で解説した各用語の定義と、それぞれのレイヤーにおける役割を以下にまとめます。

| 用語             | 属するレイヤー  | 主な役割・本質                                                                      |
| :--------------- | :-------------- | :---------------------------------------------------------------------------------- |
| スライス         | 物理（cgroups） | 物理リソースやシステムリソース分配の「総量」を決める最上位の防波堤。PIDを持たない。 |
| サービス         | 物理（cgroups） | systemdが直接起動・管理する、常駐デーモンのための物理制限枠。                       |
| スコープ         | 物理（cgroups） | ユーザーセッションなど、systemd外で生まれたプロセスへの後付けの物理制限枠。         |
| セッション       | 論理（POSIX）   | ログインからログアウトまでの一連の活動単位。SIGHUPによるライフサイクル連動の境界。  |
| ジョブ           | 論理（シェル）  | シェルがジョブ制御（Job Control）の対象として管理するプロセスグループ               |
| プロセスグループ | 論理（POSIX）   | パイプで繋がったプロセスのまとまり。Ctrl+Cなどのシグナルを同期送信する境界。        |
| プロセス         | 論理（POSIX）   | 独自の仮想メモリ空間とファイル記述子（FD）を持つ、独立した隔離枠。                  |
| スレッド         | 論理（pthread） | プロセス内でメモリ空間を共有して並行動作する、軽量な実行の筋道。                    |
| タスク           | カーネル内部    | スケジューラがCPUに割り当てる「真の実行単位（`task_struct`）」。                    |


一見すると複雑に見えるLinuxのタスク管理ですが、POSIXが論理的な実行単位を定義し、cgroupsがそれらに対するリソース制御を担い、最終的にLinuxカーネルが task_struct 単位でスケジューリングしています。

これらは上下に積み重なった単純な階層構造ではなく、それぞれが異なる観点から同じプロセス群やスレッド群を管理する仕組みです。

OSの低レイヤーな振る舞いを意識した設計・運用ができるエンジニアを目指し、今後もさらにカーネル内部の仕組みへの探求を深めていきます。
