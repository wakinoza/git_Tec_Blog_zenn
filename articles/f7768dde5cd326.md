## はじめに

- AWS SOAの取得を目指して勉強中です。
- この記事では、VPCから外部ネットワークへの通信方法、VPCエンドポイントについて説明していきます。
- 間違い等あれば、指摘いただけると助かります。

## 結論

VPCエンドポイントは、VPCから、VPC外のAWSサービスへインターネットを経由せずにプライベート接続するための仕組みです。

VPCエンドポイントとしてよく使われるサービスに、Gateway型とInterface型の2種類があります。

- Gateway型：ルートテーブルに専用ルートを追加し、S3やDynamoDBへの通信をAWSネットワーク内に転送します。
- Interface型：VPC内にENIを作成し、AWS PrivateLinkを利用して幅広いAWSサービスへプライベート接続します。

両者は通信経路や必要な設定、料金体系が異なります。
それぞれの仕組みを理解することで、接続先のAWSサービスやネットワーク構成に応じた適切なエンドポイントを選択できます。

## 1\. VPCから外部ネットワークへの通信方法

AWSには、VPC内に配置するEC2やRDSなどのリソースのほか、リージョン単位で提供されるS3やDynamoDB、SQSなどのマネージドサービスも存在します。

同一VPC内のリソース間の通信では、プライベートIPアドレスを用いた通信が可能です。
一方、VPC内のリソースからVPC外部のリソースにアクセスする場合、通常はインターネットを経由して通信します。

例えば、パブリックサブネットに配置されたEC2からインターネットに接続する場合、Internet Gateway（IGW）を利用します。
EC2にパブリックIPアドレスを割り当て、パブリックサブネットのルートテーブルにIGWをターゲットとするルートを設定することで、インターネットとの通信が可能になります。

一方、プライベートサブネットに配置されたEC2からインターネットに接続する場合は、NAT Gatewayを利用します。
NAT Gatewayは通常、パブリックサブネットに配置します。
プライベートサブネットのルートテーブルに、インターネット宛ての通信をNAT Gatewayへ転送するルートを設定します。
プライベートサブネットからの通信を受け取ったNAT Gatewayは、送信元のプライベートIPアドレスをNAT Gatewayに割り当てられたパブリックIPアドレス（Elastic IPアドレス）に変換します。
その後、IGWを経由してインターネットに転送します。

NAT Gatewayは、プライベートサブネットから開始されたアウトバウンド通信と、その応答通信を許可します。
一方、インターネット側から新しく開始された通信は許可しません。
そのため、プライベートサブネット内のリソースをインターネットから直接アクセスされない状態に保ちながら、インターネットへの接続を実現できます。

このように、VPC内のリソースから外部ネットワークにアクセスする場合、IGWやNAT Gatewayを利用することでインターネット通信を実現できます。

しかし、AWS内のリソースと通信する場合、必ずしもインターネットを経由する必要はありません。

例えば、プライベートサブネットに配置されたEC2から、Amazon S3やAWS Secrets ManagerなどのAWSサービスにアクセスする場合、「VPCエンドポイント」を利用することで、インターネットを経由せずにプライベート接続できます。


## 2\. エンドポイントとは

そもそも、エンドポイントとは何でしょうか。

エンドポイントとは、ネットワーク通信における接続先や到達点を表す言葉です。
AWSでも、さまざまなサービスやリソースでエンドポイントが利用されています。

エンドポイントを利用する場合、通信先をIPアドレスで直接指定することもできます。
しかし、AWSではDNSを利用することで、より簡単に通信先を指定できます。

DNS（Domain Name System）とは、ネットワーク通信において、ドメイン名をIPアドレスに名前解決する仕組みです。

AWSでは、サービスごとに用意されたドメイン名を指定することで、対応するIPアドレスを自動的に取得できます。

例えば、東京リージョンのAWS Secrets Managerにアクセスする場合、サービスのドメイン名（例：secretsmanager.ap-northeast-1.amazonaws.com）を指定することで、DNSが対応するIPアドレスを返します。

また、AWSはクラウドサービスであるため、サービスに対応するIPアドレスが動的に変更される場合もあります。
もし接続先をIPアドレスで指定していれば、対応するIPアドレスが変更になった場合に、修正が必要です。
しかし、接続先をドメイン名で指定している場合、DNSの情報が更新されれば、接続先情報を修正することなく、変更後のIPアドレスを利用できます。

このように、DNSを利用することで、ユーザーはIPアドレスを直接指定することなく、人間が扱いやすい文字列情報でエンドポイントなどの通信先を指定できます。

## 3\. VPCエンドポイント

VPCエンドポイントは、VPC内のリソースからAWSのマネージドサービスなどに対して、AWSのネットワークを利用したプライベート接続を実現する仕組みです。

VPCエンドポイントには複数の種類がありますが、AWSサービスへのプライベート接続では、主にGateway型とInterface型が利用されます。

この記事では、Gateway型とInterface型の仕組みについて説明します。


### 3\.1 Gateway型

Gateway型は、VPCのルートテーブルを利用して、AWSサービスへの通信経路を作成する方式です。

対応しているAWSサービスは、Amazon S3とAmazon DynamoDBの2種類です。

Gateway型では、通信元サブネットのルートテーブルに、AWSサービスのIPアドレス範囲を表すプレフィックスリストを宛先とし、Gateway型エンドポイントを転送先とするルートを追加します。

これにより、インターネットを経由することなく、AWSネットワーク内でS3やDynamoDBにアクセスできます。

また、Gateway型は追加料金が発生しないことも特徴です。

### 3\.2 Interface型

Interface型は、ENI（Elastic Network Interface）とAWS PrivateLinkを利用して、AWSサービスなどにプライベート接続する方式です。

Gateway型と異なり、S3・DynamoDBを含めた幅広いAWSサービスに対応しています。

Interface型では、指定したサブネットにエンドポイント用のENIを作成します。
ENIにはプライベートIPアドレスが割り当てられ、VPC内のlocalルートで通信が可能です。
ENIより先は、AWSが管理するPrivateLinkを利用して接続先のサービスと通信します。

Interface型は、AWSが管理するネットワークを利用して接続を実現できる一方、ENIを利用するため、時間単位の利用料金とデータ処理料金が発生します。

Gateway型とInterface型の違いをまとめると、次のようになります。

| 比較項目| Gateway型 | Interface型 |
| ---- | ---- | ---- |
| 通信方式 | ルートテーブル | ENI・PrivateLink |
| 対応サービス | S3・DynamoDB | S3、DynamoDBを含む多数のAWSサービス |
| 追加料金 | 無料　| 有料 |

Gateway型とInterface型は、どちらもインターネットを経由せずにAWSサービスへ接続するための仕組みですが、通信経路の作り方が異なります。


## 4\. Gateway型エンドポイントの仕組み

Gateway型エンドポイントは、VPCのルートテーブルを利用してVPC外のAWSサービスへの通信経路を作成する仕組みです。
対応しているサービスは、Amazon S3とAmazon DynamoDBのみです。

ここでは、プライベートサブネットに配置したEC2からS3へアクセスする場合を例に、通信の仕組みを説明します。

### 4.1 エンドポイントの作成とルートテーブルへの追加

まず、通信元のVPCにGateway型エンドポイントを作成し、接続先のAWSサービスとしてS3を選択します。

Gateway型エンドポイントの作成時に、通信元のEC2が配置されたサブネットのルートテーブルを指定します。

Gateway型エンドポイントを作成すると、指定したルートテーブルに、エンドポイントをターゲットとしたルートが自動的に追加されます。

S3の場合、宛先にはS3のIPアドレス範囲を表すAWS管理のプレフィックスリスト（複数のIPアドレス範囲をまとめて管理する仕組み）が使用されます。

| 宛先                     | ターゲット              |
| ------------------------ | ----------------------- |
| S3のプレフィックスリスト | Gateway型エンドポイント |
| 0.0.0.0/0                | NAT Gateway             |

このように設定することで、サブネットからS3宛ての通信はGateway型エンドポイントへ、それ以外のインターネット宛ての通信はNAT Gatewayへ転送されます。

なお、このエンドポイントルートはルートテーブル上から直接編集・削除できません。
エンドポイントを作成すると自動的に追加され、次のいずれかの操作によって削除されます。

- ルートテーブルとGateway型エンドポイントの関連付けを解除する
- Gateway型エンドポイント自体を削除する


### 4.2 S3への通信経路

次に、EC2からS3へアクセスした場合の通信経路を確認します。

1. EC2がS3のサービスドメイン名を指定して、アクセスします。
2. DNSによってS3のサービスドメイン名が、通信先サービスのパブリックIPアドレスに名前解決されます。
3. EC2から送信されたパケットの宛先IPアドレスを、サブネットのルートテーブルで確認します。
4. 宛先IPアドレスがS3のプレフィックスリストに一致するため、Gateway型エンドポイントへ転送されます。
5. Gateway型エンドポイントを経由し、AWSネットワーク内を通ってS3に到達します。

S3のサービスドメイン名が名前解決されると、一般的にはパブリックIPアドレスが返されます。
つまり、Gateway型エンドポイントからS3への通信は、パブリックIPアドレスを使ったルーティングです。

しかし、通信は、インターネットではなく、AWSネットワーク内で行われます。
そのため、宛先IPアドレスがパブリックIPアドレスであっても、Gateway型エンドポイントへの経路が選択されれば、インターネットを経由することはありません。

### 4.3 セキュリティ設定

Gateway型エンドポイント自体にセキュリティグループを関連付ける必要はありません。

ただし、通信元となるEC2などのリソースには、セキュリティグループによる通信許可の設定が必要です。

例えば、EC2からS3へHTTPS通信を行う場合、EC2のセキュリティグループでアウトバウンドのTCP 443を許可します。
通信先にはS3のマネージドプレフィックスリストを指定することもできます。

セキュリティグループはステートフル（許可した通信の応答を自動的に許可する仕組み）です。
そのため、アウトバウンド通信を許可すれば、その応答を受け取るためのインバウンドルールを追加する必要はありません。

また、ネットワークACLをデフォルト設定から変更している場合は、応答通信にも注意が必要です。

ネットワークACLはステートレス（通信の往復を個別に制御する仕組み）であるため、送信方向だけでなく応答方向の通信も明示的に許可する必要があります。

EC2からS3へHTTPS通信を行う場合、例えば次のようなルールが必要です。

| 設定対象 | 通信方向 | 設定内容 |
| ---- | ---- | ---- |
| EC2のセキュリティグループ | アウトバウンド | S3宛てのHTTPS通信（TCP 443）を許可 |
| ECのサブネットのネットワークACL | アウトバウンド |S3宛てのHTTPS通信（TCP 443）を許可 |
| EC2のサブネットのネットワークACL | インバウンド | S3からの応答を受け取るエフェメラルポートを許可 |


### 4.4 Gateway型エンドポイントの設定項目

Gateway型エンドポイントを作成する際には、主に次の項目を設定します。

| 設定項目               | 内容                                                                  |
| ---------------------- | --------------------------------------------------------------------- |
| VPC                    | エンドポイントを作成するVPC                                           |
| サービス               | 接続先のAWSサービス（S3またはDynamoDB）                               |
| ルートテーブル         | エンドポイントルートを追加するルートテーブル                          |
| エンドポイントポリシー | エンドポイント経由でアクセスできるAWSリソースや操作を制御するポリシー |

エンドポイントポリシーは、エンドポイント経由で利用できるAWSサービスのリソースや操作を制限するための設定です。

このように、Gateway型エンドポイントはルートテーブルに専用の経路を追加することで、S3やDynamoDBへのプライベートな通信を実現します。

## 5\. Interface型エンドポイントの仕組み

Interface型エンドポイントは、ENI（Elastic Network Interface：仮想ネットワークインターフェイス）とAWS PrivateLinkを利用して、VPCからAWSサービスへプライベート接続する仕組みです。

AWS PrivateLinkは、AWSが管理するネットワークを利用して、VPCとAWSサービスなどをプライベートに接続する技術です。

通常、異なるネットワーク間で通信する場合は、ネットワーク同士を接続するための経路やルーティングなどを考慮する必要があります。
しかし、PrivateLinkを利用すれば、エンドポイント用ENIから接続先のAWSサービスまでの通信経路はAWSが管理します。

そのため、ユーザーはAWSサービス側のネットワーク構成や通信経路を意識することなく、プライベート接続を利用できます。
ただし、利用側VPCのサブネットやセキュリティグループ、DNSなどの設定は必要です。

S3とDynamoDBしか対応していなかったGateway型とは異なり、Interface型は幅広いAWSサービスに対応しています。

ここでは、プライベートサブネットに配置したEC2からAWS Secrets Managerへアクセスする場合を例に、通信の仕組みを説明します。

### 5.1 エンドポイントの作成とENIの配置

Interface型エンドポイントを作成する際には、接続先のAWSサービスと、ENIを配置するサブネットを指定します。

ENI（Elastic Network Interface）は、EC2などのリソースに接続する仮想的なネットワークインターフェイスです。
物理サーバーに搭載されているネットワークカードを仮想化したものと考えると分かりやすいです。

ENIにはプライベートIPアドレスやMACアドレスが割り当てられ、ネットワーク上の通信先として機能します。
また、セキュリティグループを関連付けることで、ENIを通過する通信を制御できます。

Interface型エンドポイントを作成すると、指定したサブネットにENIが作成され、サブネットに割り当てられているCIDRのなかからプライベートIPアドレスが割り当てられます。

このENIが、利用側VPCとAWSサービスを接続するPrivateLinkの入口になります。

### 5.2 AWS PrivateLinkによる通信経路

次に、EC2からSecrets Managerへアクセスした場合の通信経路を確認します。

1. EC2がSecrets Managerのサービスドメイン名を指定してアクセスします。
2. DNSによってサービスドメイン名がInterface型エンドポイントのENIに割り当てられたプライベートIPアドレスに名前解決されます（Private DNSを有効にしている場合）。
3. EC2から送信されたパケットは、VPCのルートテーブルにあるlocalルートを利用して、ENIに到達します。
4. ENIに到達した通信は、AWS PrivateLinkを経由してAWSサービスへ転送されます。
5. AWSサービスがリクエストを処理し、応答を返します。

この仕組みにより、VPCからAWSサービスまでの通信をインターネットやNAT Gatewayを経由せずに行えます。

Gateway型のDNSでは、接続先のサービスドメイン名は、接続先のサービスのパブリックIPアドレスに変換されていました。
Interface型エンドポイントでの通信では、接続先サービスへの通信はPrivateLinkによって行われるため、接続先のサービスドメイン名は、ENIに割り当てられたプライベートIPアドレスに名前解決されます。


なお、Interface型エンドポイントでは、通常、エンドポイント専用のルートをルートテーブルに追加する必要はありません。
ENIはVPC内に配置されるため、同一VPC内のEC2からENIへのルーティングは、ルートテーブルにデフォルトで記載されているのlocalルートを利用して到達できます。

### 5.3 DNSによる名前解決

Interface型エンドポイントでは、Private DNSを有効にすることで、AWSサービスの標準ドメイン名をエンドポイント用ENIのプライベートIPアドレスに名前解決できます。

例えば、通信先のサービスが東京リージョンのSecrets Managerであれば、次のようなドメイン名を利用します。

`secretsmanager.ap-northeast-1.amazonaws.com`

Private DNSを有効にしておけば、EC2側でエンドポイント固有のDNS名を意識する必要はありません。通常のAWSサービスのドメイン名を指定するだけで、VPC内のInterface型エンドポイントを経由して通信できます。

一方、Private DNSを無効にしている場合は、エンドポイント固有のDNS名を利用するなど、別の方法で接続先を指定する必要があります。

### 5.4 セキュリティ設定

Interface型エンドポイントでは、ENIにセキュリティグループを関連付けます。

例えば、EC2とエンドポイント用ENIが同じサブネットにある場合、EC2からSecrets ManagerへHTTPS通信を行うには、次のような設定が必要です。

| 設定対象                             | 通信方向       | 設定内容                                            |
| ------------------------------------ | -------------- | --------------------------------------------------- |
| EC2のセキュリティグループ            | アウトバウンド | エンドポイントのENI宛てのHTTPS通信（TCP 443）を許可 |
| エンドポイントのセキュリティグループ | インバウンド   | EC2からのHTTPS通信（TCP 443）を許可                 |

EC2とエンドポイント用ENIが異なるサブネットにある場合は、それぞれのサブネットに関連付けられたネットワークACLで、通信の往路と復路を許可する必要があります。

| 設定対象                             | 通信方向       | 設定内容                                            |
| ------------------------------------ | -------------- | --------------------------------------------------- |
| EC2側サブネットのネットワークACL  | アウトバウンド | エンドポイントのENI宛てのHTTPS通信（TCP 443）を許可 |
| EC2側サブネットのネットワークACL | インバウンド   | 	エンドポイントからの応答を受け取るエフェメラルポートを許可    |
| エンドポイント側サブネットのネットワークACL  | インバウンド | EC2からのTCP 443を許可 |
| エンドポイント側サブネットのネットワークACL | アウトバウンド  | EC2への応答を送信するエフェメラルポートを許可    |

エンドポイントポリシーは、エンドポイント経由でアクセスできるAWSリソースや操作を制限するためのポリシーです。

エンドポイントポリシーだけでアクセス許可が付与されるわけではなく、IAMポリシーやリソースベースポリシーなどによるアクセス許可も必要です。

### 5.5 Interface型エンドポイントの設定項目

Interface型エンドポイントを作成する際には、主に次の項目を設定します。

| 設定項目               | 内容                                                                  |
| ---------------------- | --------------------------------------------------------------------- |
| VPC                    | エンドポイントを作成するVPC                                           |
| サービス               | 接続先のAWSサービス                                                   |
| サブネット             | エンドポイント用ENIを配置するサブネット                               |
| セキュリティグループ   | エンドポイント用ENIへの通信を制御するセキュリティグループ             |
| Private DNS            | AWSサービスの標準ドメイン名をENIのプライベートIPに名前解決する設定    |
| エンドポイントポリシー | エンドポイント経由でアクセスできるAWSリソースや操作を制御するポリシー |

Interface型エンドポイントは、ENIとAWS PrivateLinkを利用することで、VPC内のリソースからAWSサービスへプライベート接続を実現します。

Gateway型とは異なり、ENIにプライベートIPアドレスが割り当てられ、セキュリティグループによる通信制御が可能です。

## まとめ

今回は、VPCエンドポイントの仕組みと、Gateway型・Interface型の違いについて解説しました。

記事の要点は次のとおりです。

- VPCエンドポイントを利用すると、インターネットやNAT Gatewayを経由せずに、VPCからAWSサービスへプライベート接続できます。
- Gateway型は、ルートテーブルにエンドポイントルートを追加して通信を転送します。S3とDynamoDBに対応しており、追加料金は発生しません。
- Interface型は、VPC内に作成したENIとAWS PrivateLinkを利用して通信します。幅広いAWSサービスに対応しており、時間単位の利用料金とデータ処理料金が発生します。
- Interface型では、Private DNSを有効にすることで、AWSサービスの標準ドメイン名をエンドポイントのプライベートIPアドレスに名前解決できます。


VPC内のEC2からS3やDynamoDBへ接続する場合は、追加料金が発生しないGateway型が一般的な選択肢です。一方、その他のAWSサービスへ接続する場合や、PrivateLinkを利用した接続が必要な場合は、Interface型を検討します。
