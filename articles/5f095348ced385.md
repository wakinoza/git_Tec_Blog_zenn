## 1\. テストのライフサイクル管理

この記事では、Java言語のテストフレームワークであるJUnit5のライフサイクル管理について説明していきます。

ライフサイクル管理とは、複数のテストメソッド間で共通して使用される処理を別メソッドに切り出し、重複を排除する仕組みです。

例えば、以下のCalculatorクラスと、Calculatorクラスのテストクラスがあります。

```Java
public class Calculator {

  public int add(int a, int b) {
    return a + b;
  }

  public int multiply(int a, int b) {
    return a * b;
  }
}
```

```Java
import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

class CalculatorTest {

    @Test
    @DisplayName("加算のテスト：5 + 3 = 8 であること")
    void testAdd() {
      Calculator calc = new Calculator();
        assertEquals(8, calc.add(5, 3), "加算の結果が正しくありません");
    }

    @Test
    @DisplayName("乗算のテスト：5 * 3 = 15 であること")
    void testMultiply() {
        Calculator calc = new Calculator();
        assertEquals(15, calc.multiply(5, 3), "乗算の結果が正しくありません");
    }
}
```

テストクラスでは、2つのメソッドでテストを実施していますが、「Calculator calc = new Calculator();」の部分が重複しています。
特定のコードがソースコードのあちこちに点在すると、変更時の修正が煩雑化し、変更のコストが増大します。

new処理を別のメソッドに切り出すことで、重複を解消できます。
このような処理の共通化に利用できる便利なアノテーションがJUnit5にはあります。
それが、`@BeforeEach`と`@AfterEach`です。

## 2\. `@BeforeEach`と`@AfterEach`

`@BeforeEach`はテストメソッドが実行される前に、`@AfterEach`はテストメソッドが実行された後に、それぞれ自動的に呼び出されます。
すると、処理メソッドを呼び出すコードを記載しなくても、自動的に処理メソッドが実行されます。

上のテストクラスに `@BeforeEach`と`@AfterEach`を利用すると以下のようになります。

```Java
import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

class CalculatorTest {
    private Calculator calc;

    @BeforeEach
    void setUp() {
        calc = new Calculator();
        System.out.println("@BeforeEach");
    }

    @Test
    @DisplayName("加算のテスト：5 + 3 = 8 であること")
    void testAdd() {
        assertEquals(8, calc.add(5, 3), "加算の結果が正しくありません");
        System.out.println("加算のテスト");
    }

    @Test
    @DisplayName("乗算のテスト：5 * 3 = 15 であること")
    void testMultiply() {
        assertEquals(15, calc.multiply(5, 3), "乗算の結果が正しくありません");
        System.out.println("乗算のテスト");
    }

    @AfterEach
    void tearDown() {
        System.out.println("@AfterEach");
    }
}
```

テストメソッドのコードの重複が解消されています。
このコードをJUnit5で実行したコンソールは、以下の情報が表示されます。

```Plain
@BeforeEach
加算のテスト
@AfterEach
@BeforeEach
乗算のテスト
@AfterEach
```

テストメソッドに、setUp()やtearDown()メソッドを呼び出すコードを記述しなくても、テストメソッドの実行前と後に`@BeforeEach`と`@AfterEach`が呼び出されていることがわかります。

各アノテーションの実行タイミングを確認したところで、具体的なユースケースを整理します。

・インスタンスの初期化・初期値の格納：フィールドなどの内部状態を持つクラスをテストする場合は、先のテストメソッドの結果が次のテストメソッドに引き継がれ、テストが失敗するケースがあります。そのような失敗を防ぐため、テストメソッドごとにインスタンスを初期化し、必要ならば初期値を投入します。これによって常に内部情報が管理された状態になり、別のテストメソッドの結果によって影響を受けるという事態を回避できます。

・システムプロパティや環境変数の書き換え：「言語設定を英語に」などのようにシステムプロパティ設定を変更してテストを実施する場合、テスト後に設定を変更しなおさないと、後のテストメソッドに影響してしまいます。こういった、必ず行わなければならない後処理を`@AfterEach`に記載すると、設定を戻し忘れる心配がありません。

・テスト時間の計測：各テストメソッドの処理時間を調べたい場合は、`@BeforeEach`で開始時刻を、`@AfterEach`で終了時刻を記録することで、処理時間をログに出力できます。

## 3\. assertAll()の注意点

ここで一つ注意なのが、`@BeforeEach`と`@AfterEach`は「テストメソッド」ごとに実行されるのであって、検証ごとに実行されるのではないということです。

検証用メソッドの一つである「assertAll()」は一つのテストメソッドの中に複数の検証を記述することができます。
もし、assertAll()で内部状態を持つクラスの検証を複数記述すると、先の検証の結果が次の検証に影響を与えてしまいます。

以下は、内部情報を持つクラスのコード例です。

```Java
public class StatefulCalculator {
  private int total = 0;

  public int add(int a) {
    return total += a;
  }
}
```
このクラスは内部にフィールドを保持するため、複数の検証で同じインスタンスを使いまわすと、検証の順番によって結果が変わってきます。

```Java
import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

class StatefulCalculatorTest {

    @Test
    @DisplayName("assertAll内での状態汚染の実験")
    void testStateContamination() {
        StatefulCalculator calc = new StatefulCalculator();

        assertAll("同じインスタンスを使い回すことによる失敗",
            () -> {
                // 1つ目の検証:
                assertEquals(10, calc.add(10), "1回目のadd(10)は10になるべき");
            },
            () -> {
                // 2つ目の検証:
                //前の検証と同じメソッドだが、前の検証の結果をインスタンスが引き継いでいるため、結果が変わってくる
                assertEquals(10, calc.add(10), "2回目のadd(10)も10になるべき？");
            }
        );
    }
}
```

上のテストメソッドでは、2つ目の検証が失敗します。
１回目の検証と同じ引数ですが、内部状態（totalの値）が変化しているため、テスト結果は違ってきます。

テストの失敗ログだけを見ると、メソッドそのものにバグがあるようにも思えますが、これは前のテストが後のテストの状態を汚染してしまったことが原因であるため、テスト方法の失敗と言えます。

このように、assertAll()で内部状態を持つクラスのテストを複数行うと、前のテスト結果が次のテスト結果に影響を与えてしまうことがわかりました。
このような状態は望ましくありません。

そのため、内部に状態を持つクラスをテストする場合は、検証をassertAllにまとめず、個別のテストメソッドに切り分けることが必要です。

余談ですが、assertAllは、内部状態を持つインスタンスをテストする場合は後のテストを汚染してしまいますが、内部状態を持たないインスタンスの検証や、内部状態を持つインスタンスでも状態を変化させない検証では非常に有用です。
例としては、複数の引数を持つインスタンスの全項目を正しく保持しているかをチェックする場合などです。

```Java
@Test
@DisplayName("コンストラクタで渡した値が、全てのフィールドに正しく保持されていること")
void testConstructorAssignment() {
    UserProfile user = new UserProfile("Gemini", "gemini@example.com", 25);

    assertAll("プロフィール情報の全項目チェック",
        () -> assertEquals("Gemini", user.getUsername(), "ユーザー名が一致しません"),
        () -> assertEquals("gemini@example.com", user.getEmail(), "メールアドレスが一致しません"),
        () -> assertEquals(25, user.getAge(), "年齢が一致しません")
    );
}
```

上のコード例では、getterメソッドで状態を読みとっているだけなので、インスタンスの状態は変化していません。
そのため、後の検証を汚染してしまう心配なく、複数の検証を同時に行えます。

## 4\. `@BeforeAll`と`@AfterAll`

テストメソッドごとに必要な処理は、`@BeforeEach`と`@AfterEach`で実現できることがわかりました。
では、DB接続などの外部システムとの通信はどうでしょうか？

外部システムとの接続や接続解除の処理は重いため、テストメソッドごとに繰り返すと、テスト時間が非常に長くかかります。
また、DBに格納される値はテストメソッドごとに初期化やロールバックなどの処理が必要ですが、DB接続そのものは、複数のテストメソッドをまたいで継続しても問題ありません。

そのため、DBの接続は複数のテストメソッドを実施する前に1回だけ、DBとの接続解除は、すべてのテストメソッドが終了した後に１回だけ実施すれば問題ありません。
そのようなニーズに応えるアノテーションが、`@BeforeAll`と`@AfterAll`です。

テストクラスに複数のテストメソッドが存在する場合、`@BeforeAll`が付与されたメソッドは、テストメソッドが実施される前に１回だけ実行されます。
また、`@AfterAll`が付与されたメソッドは、すべてのテストメソッドが実施された後に１回だけ実行されます。

ちなみに、`@BeforeAll`と`@AfterAll`を付与するメソッドはstaticである必要があります。
その理由は、テストの独立性を保つために、テストメソッドごとにテストインスタンスを生成する仕様がJUnit5にあるためです。`@BeforeAll` はテストインスタンスの再生成前に実行されるため、 インスタンス生成前にも実行できるstaticメソッドとして定義する必要があるのです。
例外として、テストクラスに`@TestInstance(Lifecycle.PER_CLASS)` を設定することで、JUni5tはテストクラスのインスタンスを1クラスにつき1つと限定します。インスタンスがテスト開始時から終わりまで１つだけであることが保証されるため、 `@BeforeAll` を非staticとすることが可能になります。

DB処理を検証するテストクラスのコード例を見てみましょう。

```Java
package test;

import org.junit.jupiter.api.AfterAll;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeAll;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

class DbTest {

  @BeforeAll
  static void setupAll() {
    // DB接続処理
    System.out.println("@BeforeAll");
  }

  @BeforeEach
  void setUp() {
    // DBに初期値を投入する処理
    System.out.println("@BeforeEach");
  }

  @Test
  @DisplayName("DBのテスト１")
  void testDb1() {
    // DBの挙動のテスト
    System.out.println("DBのテスト１を実行");
  }

  @Test
  @DisplayName("DBのテスト2")
  void testDb2() {
    // DBの挙動のテスト
    System.out.println("DBのテスト2を実行");
  }

  @AfterEach
  void tearDown() {
    // DBの値を消去する処理
    System.out.println("@AfterEach");
  }

  @AfterAll
  static void tearDownAll() {
    // DBとの接続を解除する処理
    System.out.println("@AfterAll");
  }
}
```

上のコードを実行すると、以下の情報がコンソールに表示されます。

```Plain
@BeforeAll
@BeforeEach
DBのテスト１を実行
@AfterEach
@BeforeEach
DBのテスト2を実行
@AfterEach
@AfterAll
```

コンソールの表示から、`@BeforeEach`と`@AfterEach`はテストメソッドごとに実行されていて、`@BeforeAll`と`@AfterAll`は、複数のテストメソッドの最初と最後に１度ずつだけ実行されていることがわかります。


このように、`@BeforeEach`と`@AfterEach`と`@BeforeAll`と`@AfterAll`は、処理の特性に合わせて使い分けます。

## 5\. ステートレスな設計

ここまでの章で、JUnit5のライフサイクル管理の方法について話をしてきました。
しかし、そもそもこのライフサイクル管理、本当に必要なのでしょうか？

`@BeforeEach`や`@AfterEach`が必要となるのは、フィールドなどの内部状態を保持していたり、DBなど外部の状態を参照・変更している（＝副作用を伴う）クラスです。
先のテストメソッドで変化した状態が次のテストメソッドに引き継がれると、予期せぬ失敗をする可能性があるため、テストメソッドごとに初期化処理が必要でした。

しかし、もしテスト対象クラスが、関数型プログラミング用に、外部クラスの情報を参照・変更もせず、内部状態も持っていない（＝副作用がない）クラスだったらどうでしょうか？
そのようなクラスのメソッドは、戻り値に影響する要因は引数のみです。
そのため、引数さえ同じであれば、外部の状態にかかわらず、常に同じ戻り値を返します。
この性質を「参照透過性」と呼び、そのような設計を「ステートレス（状態を持たない設計）」と呼びます。

ステートレスなクラスでは、一つのインスタンスを複数のテストメソッドで使いまわしても、結果が影響しあうことはありません。
テストメソッドのたびにインスタンスをnewしたり、値を初期化する必要もありません。
つまり、ステートレスなクラスであれば、ライフサイクル管理は最低限でよく、テストが容易であるということです。

クラス設計がステートレスである利点は、テストの容易性だけではありません。
ステートレスなクラスは、外部状態を参照していないため、変更時の影響範囲が限定的です。
そのため、後々の変更が容易で、変更後もコードが複雑になりにくいのです。

つまり、ライフサイクル管理が不要でテストが容易なクラスを設計することが、ソフトウェア設計の理想である、「クリーンアーキテクチャ」を実現する一歩となるのです。

全てのクラスをステートレスにできれば理想ですが、現実には困難です。DBアクセスやセッション管理といった、外部リソースや内部状態を扱う「ステートフル」なクラスは、アプリケーションを構成する上で不可欠だからです。

重要なのは、これらを混同せず、「ステートレスな領域」と「ステートフルな領域」を明確に分離して設計することです。

- ステートレスな領域（ロジック中心）
計算や判定などのロジックをこの領域に集約します。副作用がないため、JUnit5のライフサイクル管理を意識する必要がほとんどなく、テストコードはシンプルになります。

- ステートフルな領域（状態管理中心）
外部リソースとの接点や状態保持をこの領域に限定します。ここではJUnit5のライフサイクル管理機能をフル活用し、テストごとに状態をリセットすることで、安全かつ再現性のあるテストを実現します。

このように領域を分離し、可能な限り「ステートレス」な範囲を広げることは、テストの容易性だけでなく、変更に強い柔軟な構造「クリーンアーキテクチャ」の実現に直結します。

テストコードを書いていて「ライフサイクル管理が複雑すぎる」と感じたときは、それは設計を見直すサインかもしれません。
「このロジックをステートレスなクラスに切り出せないか？」と一度立ち止まって考えることが、コードの品質を高める一歩となるはずです。

## まとめ

- 適切なアノテーションの選択: インスタンス単位の初期化（`@BeforeEach` / `@AfterEach`）とクラス単位の共通処理（`@BeforeAll` / `@AfterAll`）を使い分け、テストの実行速度と独立性を両立させる。

- 状態汚染への警戒: assertAll() 内での状態変化など、テストが互いに干渉する「状態汚染」を避けることが、信頼性の高いテストコードへの第一歩となる。

- テスト容易性の追求: 複雑なライフサイクル管理が必要となるステートフルな領域を切り出し、可能な限り「ステートレス（参照透過）」な設計を目指す。
