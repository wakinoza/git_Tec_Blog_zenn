## はじめに

- 個人開発として、GitHub Actionsで毎日自動実行し、気象庁の天気情報をメール通知するシステムを開発しています。
- 本記事では、開発そのものではなく、AIを開発パートナーとして利用するために行った情報管理・指示設計についてまとめます。
- プロジェクトの概要は、以下の記事でまとめています。

https://zenn.dev/wakinoza/articles/034a3f1795dd59

## 1.ドキュメント駆動開発前の課題

以前から、AIを利用した個人開発を行っていましたが、以下の点で課題を感じていました。

1. 過去の判断理由を自分自身が忘れる : 以前は個人開発の設計判断を記録する習慣がなく、属人的な記憶に頼っていました。そのため、時間がたつと、なぜこの設計や判断をしたのかが不明になり、ついには以前解消したはずのトラブルに再度見舞われる事態が発生しました。
2. チャットを変更するとAIが以前の経緯を保持できない : AIに適切な情報を与えることで、回答の精度を上げる試みをしていましたが、チャットを変更するたびに経緯や情報を説明しなおす必要があり、その作業が煩雑になってきました。

AIに適切な前提情報を渡せなければ、意図した回答や提案を得ることが難しくなります。
そこで、進捗や設計判断をドキュメントに保存し、AIが必要な情報を参照できる状態を作るため、「ドキュメント駆動開発」に着手しました。
本記事における「ドキュメント駆動開発」は、設計・判断・進捗・開発ルールなどの情報をドキュメントとして記述し、それを人間とAIの共通の情報源として利用する開発方法を指します。

プロジェクトでは、ChatGPT（Goプラン）およびAIエージェント（Codex CLI）を開発パートナーとして活用しています。



## 2.ドキュメント共有設計

ChatGPT内に開発専用プロジェクトを立ち上げ、以下のファイルをプロジェクトの参照資料として追加し、ChatGPTが開発時に利用できる情報源として管理しました。

まずは、プロジェクト開始前に、基本となるドキュメントを作成します。
当初作成したのは、以下の5つのファイルです。

| ファイル | 記載内容・役割 | Git管理 |
| Instructions | ChatGPTへの指示 | × |
| PROJECT_NOTES.md | 設計・判断・メモ | × |
| README.md | 公開用ドキュメント | ○ |
| 全体共通のAGENTS.md |複数プロジェクトで共通して適用するCodex CLI向けルール | × |
| プロジェクト固有のAGENTS.md | 当該プロジェクトだけに適用するルール | × |

最低限のファイルを作成し、ファイルが肥大化した場合は、肥大化部分を別のファイルに切り出すという方針でスタートしました。

運用開始後、PROJECT_NOTES.mdが肥大化したため、進捗を記述するPROJECT_ROADMAP.mdと、決定事項を記載するDECISIONS.mdを分離しました。

MVP完成時点では、ドキュメント構成は以下のようになりました。

| ファイル | 記載内容・役割 | Git管理 |
| Instructions |  ChatGPTの回答方針、開発支援スタイル、技術スタック、プロジェクトの運用規約を定義 | × |
| PROJECT_ROADMAP.md | プロジェクトのロードマップ、現在の実装進捗、未対応タスクの管理 | × |
| DECISIONS.md | 技術選定の理由（気象庁JSON vs Open-Meteo等）や各種検証結果（Cron遅延検証等）の記録 | × |
| README.md | プロジェクトの概要、システム全体のディレクトリ構造、起動手順 | ○ |
| 全体共通のAGENTS.md | 複数プロジェクトで共通して適用するCodex CLI向けルール | × |
| プロジェクト固有のAGENTS.md | 当該プロジェクトだけに適用するルール | × |

情報共有のために毎回経緯を説明する手間を減らし、プロジェクトの前提を共有した状態でAIとの開発を継続しやすくなりました。

## 3.ドキュメント共有の問題点

ドキュメントを運用する中で、新たに2つの問題が発生しました。

- 情報をどのファイルに記載するかというルール
- 情報の重複の発生

まず、情報をどのファイルに記載するかというルールです。
プロジェクトに関する情報は、PROJECT_ROADMAP.md、DECISIONS.md、README.md と3つのファイルに分かれていたため、どのファイルに記載すべきか悩むことがありました。

そこで、情報の配置のルールを見直しました。
まず、公開情報は、README.mdに記載する。
そして、非公開情報のうち、未実施の項目はPROJECT_ROADMAP.mdへ、決定済の事項はDECISIONS.mdへ記載するというルールにしました。
PROJECT_ROADMAP.mdは、現在の進捗状況のほかに、将来的に導入する予定の開発項目をまとめて記述することで、開発の実装漏れを防ぐ構成にしています。

次に、情報の重複の発生です。
情報配置のルールは設定しましたが、それでもファイル間での情報の重複が発生しました。
また、同じ情報が複数のファイルに記載されていることに気づかず、一方のファイルだけを修正してしまうケースがありました。
情報に矛盾があると、AIがどの情報を正しい前提として扱うべきか判断しづらくなり、回答の精度や一貫性に影響する可能性があります。

そこで、各フェーズが終わるごとに、Codex CLIでドキュメント間の重複や矛盾を検出し、人間が内容を確認した上で修正することで、ドキュメントの整合性を維持しています。



## 4.AIエージェント（Codex CLI）の運用と指示の一貫性・安全性向上
Codex CLIでは、毎回同じプロジェクトの前提や開発ルールを参照できるようにし、指示内容の一貫性と安全性を高める仕組みを試行錯誤しながら構築しています。

### 4.1. ガイドラインの階層化（AGENTS.md）
- 全体共通ルール: Codex 専用フォルダ内に AGENTS.md を配置し、複数プロジェクトで共通して適用するコーディングスタイルやコミット方針などを規定。
- プロジェクト固有ルール: 各プロジェクトのルートディレクトリにAGENTS.md を配置し、そのプロジェクト固有の技術スタックやディレクトリ構成、開発方針を記載。

これにより、エージェントがプロジェクトの文脈や制約事項を参照できるようにし、意図した開発方針に沿ってコード変更を提案できるか検証・調整を続けています。

### 4.2. 機密情報（.env）保護対策
AIエージェントがローカル環境のファイル（特に .env に含まれるメールアドレスやアプリパスワード等の機密情報）を誤って読み取ったり、回答やコード変更に含めたりするリスクを防ぐため、以下の対策を実施しました。

- Codexの操作対象からの分離（ディレクトリ外配置）:
.envをCodex CLIが操作するプロジェクトディレクトリの外へ配置し、通常のプロジェクト操作では機密情報を含むファイルを参照しない構成にしました。

- AGENTS.mdによる行動ルールの設定:
AGENTS.mdには「機密情報を表示・要求しない」「必要な場合は人間の承認を得る」といった行動ルールを記載しました。これはAIエージェントの操作方針を定めるためのものです。

### 4.3. AIに任せることと、人間が判断すること

このプロジェクトでは、リポジトリ内のコードやドキュメントを横断した調査はCodex CLI、設計や技術的な詳細の検討はChatGPT、最終的な設計判断は人間が行うという役割分担で開発を進めました。

具体的には、以下の通りです。

| 作業                       | 作業の主体      |
| -------------------------- | --------------- |
| 要件整理                   | 人間＋ChatGPT   |
| 技術比較                   | 人間＋ChatGPT   |
| ドキュメント整合性チェック | Codex CLI＋人間 |
| コード調査                 | Codex CLI       |
| リファクタリング案         | Codex CLI       |
| 設計判断                   | 人間            |
| 最終確認                   | 人間            |


### 4.4. AI エージェントの活用事例

このプロジェクトでのCodex CLIの活用事例は、以下の通りです。

- 情報が混在したプロジェクトドキュメントの分割
    - PROJECT_NOTES.mdを責務ごとに分割
- ドキュメント整合性チェック
    - 重複・矛盾・古い情報を検出
- モジュール分割
    - プロジェクト全体の構造を踏まえて分割案を検討
- リファクタリング
    - 責務・変数名・重複コードを確認
- 型注釈
    - 型注釈が不足している箇所を抽出

## 5.ドキュメント駆動によるAI協働の気づき

AIとの協働において重要だったのは、「AIに指示を出す前に、まず自分自身が設計や運用方針をドキュメント（DECISIONS.md や AGENTS.md）として言語化すること」でした。

実際に開発を始める前に、プロジェクトの構成や方針を細かく検討しておくことで、開発後の手戻りが少なくなったと感じています。

また、ドキュメントとして残すことで、人間にとっても設計の振り返りやポートフォリオの資料として活用できます。

今回の開発を通じて、AIとの協働では、AIの能力だけでなく、人間側がどれだけ前提条件を整理できているかも重要だと実感しました。

今後も、AIにコード生成やリファクタリングを任せるだけではなく、人間側で設計や判断をドキュメントとして整理し、それをAIとの共通の情報源として活用する方法を続けていきたいと思います。
