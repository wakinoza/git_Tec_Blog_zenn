## はじめに

- 「`__init__.py`は無くても良い」と本に書いてあるのですが、「無くても良いってどういう意味？」と気になったので調べてみました。
- この記事では、`__init__.py`の歴史的な変化・「名前空間パッケージ」についてまとめています。
- 間違い等あれば、指摘いただけると助かります。

## 結論

`__init__.py`について、この記事の要点は以下の4点です。

* Python 3.2以前では、`__init__.py`が通常のパッケージ（regular package）を構成するために必要でした。
* Python 3.3でPEP 420が導入され、`__init__.py`がなくても、条件を満たせば「名前空間パッケージ（namespace package）」としてパッケージを構成できるようになりました。
* そのため、現在のPythonでは「パッケージを構成するために`__init__.py`が必須」というわけではありません。
* 一方、`__init__.py`には現在も、パッケージの初期化や公開APIの整理という役割があります。

つまり、「`__init__.py`はなくてもよい」というのは、`__init__.py`が不要になったという意味ではなく、`__init__.py`がなくてもパッケージを構成できる仕組みが追加されたという意味です。


## 1\. `__init__.py`とは

Pythonを学び始めた当初、ディレクトリをパッケージと明示するために、`__init__.py`という名前のファイルをディレクトリ直下に配置すると学習しました。

しかし、学習を進めていると、パッケージを明示するために`__init__.py`は必要ない場合があるという記載を見つけました。
実際に、開発時にパッケージに`__init__.py`を作成しなくても、importが問題なく行えているケースが見られました。

そもそもこの`__init__.py`とは、どのようファイルなのだろうか？
気になったので、`__init__.py`とパッケージの歴史について調べてみました。


## 2\. Python 3.2以前

`__init__.py`を取り巻くパッケージの仕組みは、Python 3.3を境に大きく変わりました。
まずは、Python 3.2以前の`__init__.py`について説明していきます。

Python 3.2以前での主な役割は、「パッケージの目印」でした。
「パッケージ」とは、複数のモジュールをひとまとまりに束ねる単位です。

Pythonのimport機構は、検索対象のディレクトリに`__init__.py`が存在する場合、そのディレクトリを「通常のパッケージ（regular package）」として扱います。

例えば、以下のようなディレクトリ構成があったとします。

```text
mypackage/
├── __init__.py
├── foo.py
└── bar.py
```

Python 3.2以前のimport機構は、sys.pathなどを検索して「mypackage」という名前に対応するディレクトリを探します。
そして、そのディレクトリに`__init__.py`があると、通常のパッケージとして扱います。

import機構の流れを大まかに表すと、以下のようになります。

```text
import mypackage
       ↓
Pythonのimport機構が
「mypackageという名前のモジュール/パッケージを探す」
       ↓
mypackage/ を発見
       ↓
__init__.py を発見
       ↓
「これは通常のパッケージだ」と判断
```

このような仕組みのおかげで、mypackageパッケージ内のモジュールを次のようにimportできます。

```Python
from mypackage import foo
```


また、`__init__.py`には他の役目もありました。

パッケージが最初にimportされた際には、`__init__.py`に記述されたPythonコードが実行されます。
その仕組みを利用して、パッケージの初期化処理を記述したり、パッケージから公開する名前を整理したりすることもできます。

つまり、Python 3.2以前の`__init__.py`には、

- ディレクトリを通常のパッケージとして扱う
- パッケージの初期化処理を行う

といった役割があったのです。



## 3. 名前空間パッケージ

Python 3.3では、PEP 420によって「名前空間パッケージ（namespace package）」が導入されました。

名前空間パッケージとは、「1つのPythonパッケージを、複数のディレクトリに分散して構成できる仕組み」です。
つまり、importする側からは1つのパッケージに見えていても、実際のファイルは複数のディレクトリに分かれて存在することが可能になったのです。

### 3.1 `__init__.py`がなくてもパッケージとして扱える

Python 3.2以前では、通常のパッケージを構成するために`__init__.py`が必要でした。

一方、Python 3.3でPEP 420が導入されたことで、`__init__.py`を持たないディレクトリも、import機構による探索で条件を満たせば、名前空間パッケージとして扱われるようになりました。

例えば、以下のような構成です。

```text
mypackage/
├── foo.py
└── bar.py
```

この場合、`mypackage/`には`__init__.py`がありません。

PEP 420の導入によって、Pythonのimport機構は、sys.pathなどの検索対象を探索した結果、`__init__.py`を持たないディレクトリが条件を満たす場合に、名前空間パッケージとして扱えるようになりました。

これにより、__init__.pyがなくても、その配下のモジュールをimportできるようになりました。

PEP 420では、通常のパッケージと名前空間パッケージを次のように区別しています。

```text
通常のパッケージ
mypackage/
├── __init__.py
└── foo.py

名前空間パッケージ(__init__.py は存在しない)
mypackage/
└── foo.py

```

つまり、PEP 420導入以降は、条件を満たせば`__init__.py`がないディレクトリも、名前空間パッケージとして扱えるようになったということです。

これが「`__init__.py`はなくてもよい」と言われる理由です。


### 3.2 名前空間パッケージの仕組み

なぜ、名前空間パッケージが必要だったのでしょうか？

名前空間パッケージの利点を理解するために、複数のディレクトリに同じパッケージ名が存在するケースを考えてみます。

例えば、以下のような構成があるとします。

```text
distribution_a/
└── mypackage/
    └── foo.py

distribution_b/
└── mypackage/
    └── bar.py
```

`distribution_a/`と`distribution_b/`がsys.pathに含まれている場合、Pythonはそれぞれの場所にある`mypackage/`を見つけることができます。

そして、どちらの`mypackage/`にも`__init__.py`が存在しなければ、2つの`mypackage/`を1つの名前空間パッケージとして扱うことができます。

概念的には、

```text
distribution_a/        distribution_b/
    │                       │
    ↓                       ↓
mypackage/              mypackage/
    │                       │
  foo.py                bar.py
    │                       │
    └──────────┬────────────┘
               ↓
          mypackage
       名前空間パッケージ
          ├── foo
          └── bar
```

という構造になります。

そのため、以下のように、それぞれのモジュールを同じ名前空間でimportできます。

```Python
from mypackage import foo
from mypackage import bar
```

名前空間パッケージによって、複数の配布物に分散している同じパッケージ名前空間を、import時には1つの名前空間として扱うことが可能になります。

PEP 420では、こうした名前空間パッケージを構成する各ディレクトリを「portion（構成部分）」と呼んでいます。



### 3.3 `__init__.py`と名前空間パッケージの関係

ここまでの内容を整理すると、Python 3.3以降では、パッケージには大きく2つの種類があります。

|                           | 通常のパッケージ           | 名前空間パッケージ                   |
| ------------------------- | -------------------------- | ------------------------------------ |
| `__init__.py`             | ある                       | ない                                 |
| 構成                      | 1つのディレクトリで構成    | 複数のディレクトリに分散可能         |
| `__init__.py`による初期化 | 可能                       | できない                             |
| 主な用途                  | 一般的なアプリ・ライブラリ | 複数の配布物にまたがるパッケージなど |

名前空間パッケージには`__init__.py`が存在しないため、`__init__.py`による初期化処理はありません。


Python 3.3で起きた大きな変化は、通常パッケージに加えて、名前空間パッケージという仕組みが追加されたことです。


```text
ディレクトリ
   │
   ├── __init__.pyあり
   │       ↓
   │   通常のパッケージとして扱う
   │
   └── __init__.pyなし
           ↓
   条件を満たす場合、名前空間パッケージとして扱う
```

つまり、`__init__.py`は現在も通常のパッケージで利用されますが、パッケージを構成するための唯一の方法ではなくなったのです。


## 4. PEP 420以後

`__init__.py`は「パッケージを構成するために必須のファイル」ではなくなりましたが、`__init__.py`そのものが不要になったわけではありません。

この章では、Python 3.3以降も残っている`__init__.py`の役割について説明します。

### 4.1 パッケージの初期化

`__init__.py`には、パッケージがimportされた際に実行する初期化処理を記述できます。

例えば、以下のような構成があるとします。

```text
mypackage/
├── __init__.py
├── foo.py
└── bar.py
```

`__init__.py`に、以下を記載します。

```python
print("mypackageを初期化しました")
```

この状態で、以下のimportが記載されたファイルを実行すると、`mypackage`のimport時に`__init__.py`のコードが実行されます。

```python
import mypackage
```


このように、`__init__.py`はパッケージの初期化処理を記述する場所として利用できます。

ただし、`__init__.py`に記述したコードはimport時に実行されるため、注意が必要です。
例えば、ファイルへの書き込みやデータベースへの接続など、外部に影響を与える処理を記述すると、単にパッケージをimportしただけで処理が実行されてしまいます。
このような処理は「import時の副作用」と呼ばれます。

そのため、`__init__.py`には必要最小限の処理だけを記述することが一般的です。

### 4.2 公開APIの設計

`__init__.py`は、パッケージの外部から利用する機能を整理し、公開APIを設計するためにも利用できます。

例えば、以下のような構成があるとします。

```text
api/
├── __init__.py
├── foo.py
└── bar.py
```

`foo.py`に、以下の関数が定義されているとします。

```python
def method():
    ...
```

通常、この関数を利用する場合は、以下のようにimportします。

```python
from api.foo import method
```

一方、`api/__init__.py`に、以下のように記述します。

```python
from .foo import method
```

すると、以下の記述で、import可能になります。

```python
from api import method
```

つまり、`__init__.py`を利用することで、パッケージ内部のモジュール構成を利用者に意識させず、パッケージの入口を整理できるのです。

このように、`__init__.py`はパッケージの公開APIを設計するためにも利用できます。



## まとめ

今回は、`__init__.py`の歴史的な役割と、Python 3.3以降に導入された名前空間パッケージについて整理しました。

今回の記事で押さえておきたいポイントは以下のとおりです。

* `__init__.py`は、Python 3.2以前では通常のパッケージを構成するために重要なファイルだった。
* Python 3.3でPEP 420が導入され、`__init__.py`を持たない名前空間パッケージを構成できるようになった。
* 名前空間パッケージでは、複数のディレクトリに分散した同じパッケージ名前空間を、import時に1つの名前空間として扱える。
* `__init__.py`は現在も、パッケージの初期化や公開APIの整理に利用できる。

最初に感じた「`__init__.py`は無くてもよいとはどういう意味なのか？」という疑問については、Python 3.3以降、パッケージを構成する方法が1つ増えたため、`__init__.py`が必須ではなくなったと理解すると整理しやすいです。

`__init__.py`は古い仕様の名残として残っているだけではなく、現在のPythonでもパッケージの設計に利用されている仕組みです。
