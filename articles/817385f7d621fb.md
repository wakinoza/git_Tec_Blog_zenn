## 1\. `top`コマンドの値

`top`コマンドは、OSやシステム全体の状態をリアルタイムに表示するコマンドです。
タスク、CPU、メモリ、スワップ、各プロセスの情報や利用率が確認できます。
そのため、何らかの障害が発生した場合に、発生原因の一次切り分けとして、よく用いられます。

![topコマンドのスクショ画像](/images/topCommand.png)

`top`コマンドは表示項目が多いため、慣れないうちは、どこを見ればよいのか迷ってしまいます。
この記事では、`top`コマンドの各項目の説明と、値の見かたを説明していきます。

### 1列目：OSの稼働状況

1列目は、OSの稼働状況が表示されます。
まずは、前半から見ていきます。

```plain
top - 14:05:19 up 2 min, 1 user
```
| 項目     | 説明                            |
| -------- | ------------------------------- |
| 14:05:19 | 現在時刻                        |
| up 2 min | OSが起動してからの経過時間      |
| 1 user   | SSHを含めたログインセッション数 |

現在時刻が手元の時計とずれていたら、OS内の時刻設定が日本時間でないか、時刻同期ができていない可能性があります。

次に1列目後半を見ていきます。

```plain
load average: 0.44, 0.33, 0.13
```

「load average」は、「CPUの実行権限を待っている、または得て動いているタスク」および「ディスクI/Oなどの完了を待っている割り込み不可のタスク」の平均数です。
load averageの値は、論理CPUコア数（コア数）とともに解釈します。

具体例として、load averageが常に「2.0」を示している状況を想定します。
クアッドコア（4コア）の環境では、コアの数（4）に対して処理待ちのタスクが少ないため、CPUの処理能力にはまだ余裕があると考えられます。
デュアルコア（2コア）の環境では、コア数と実行待ちプロセス数が拮抗しています。余裕がなくなり、コアが飽和状態です。
シングルコア（1コア）の環境では、コア数を上回る数のプロセスが待ち状態に陥っている可能性があります。

3つの値は、左から、過去1分間の平均値、5分間の平均値、15分間の平均値を表します。
これらの値を見比べることで、「今まさに負荷が増大しているのか」「ピークが過ぎ、負荷が落ち着きつつあるのか」という時間経過を確認できます。

### 2列目：タスクの状況

2列目は、現在のタスクの状態を表示します。
タスクとは、「カーネルが管理・スケジューリングする処理の実行単位」です。
プロセスやその中で動くスレッドの両方を指す場合があります。

```plain
Tasks: 237 total, 1 running, 236 sleeping, 0 stopped, 0 zombie
```
| 項目     | 説明                           | 補足                                                                                                                                                               |
| -------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| total    | 全タスク数                     |                                                                                                                                                                    |
| running  | 実行中または実行待ちのタスク数 | CPUの実行権限を得て稼働しているタスク、または「いつでも動ける状態」で順番を待っているタスク                                                                        |
| sleeping | 待機中タスク数                 | 何らかのイベント（キーボード入力、ディスクI/Oの完了、タイマーなど）が発生するのを待っているタスク。sleeping状態の間はCPUを消費しません。                           |
| stopped  | 停止したタスク数               | Ctrl + Z 等で、明示的に実行がサスペンド（一時停止）されたタスク                                                                                                    |
| zombie   | ゾンビタスク数                 | 子プロセスが終了したものの、親プロセスがその終了ステータス（結果）を受け取っていないため、カーネルの管理表（プロセスデータ構造）だけに名前が残っている不要なタスク |

システムが安定して稼働している場合、大半のタスクは running または sleeping のどちらかの状態にあり、stopped や zombie は 0 または極少数に抑えられています。

stoppedは、明示的に一時停止されたプロセスの存在を示します。シェル上で`Ctrl+Z`により停止されたジョブであれば `jobs` コマンドで詳細を確認できます。

zombieは、子プロセスが終了した後に、親プロセスがまだ終了ステータスを回収していない状態です。CPUを消費しませんが、PIDを保有し続けます。大量に放置されるとプロセステーブルを圧迫し、極端な場合はPID枯渇の原因になります。
ゾンビタスク自体はすでに終了しているため `kill -9` で直接消すことはできません。解消するには、親プロセスが `wait` 系システムコールを実行する必要があります。実運用では親プロセスの再起動や終了によって解消するケースが一般的です。

### 3列目：CPUの状況

3列目は、CPUの総実行時間を100%としたとき、各実行モードに割り当てられた時間の割合を「％」で表します。
CPUが過負荷である場合に、その原因がどこにあるのかを切り分けるために有用です。

```plain
%Cpu(s): 0.0 us, 0.2 sy, 0.0 ni, 98.5 id, 0.0 wa, 0.0 hi, 1.4 si, 0.0 st
```
| 項目 | 説明                                                                                                                   |
| ---- | ---------------------------------------------------------------------------------------------------------------------- |
| us   | user : ユーザー空間（通常のアプリケーション）で消費されたCPU時間                                                       |
| sy   | system : カーネル空間（OSのシステムコールやデバイスドライバなど）で消費されたCPU時間                                   |
| ni   | nice : `nice`コマンド等によって、意図的に優先度を下げられたユーザー空間で消費されたCPU時間                             |
| id   | idle : どのタスクも実行されておらず、CPUが処理を待っている暇な時間                                                     |
| wa   | I/O wait : ストレージ（SSD/HDD）などの I/O待ち中のタスクが存在していた間のCPUアイドル時間                              |
| hi   | hardware interrupt : キーボードやネットワークカード等、ハードウェアからの割り込み（Interrupt）で消費されたCPU時間      |
| si   | software interrupt : カーネル内部のタイマーやネットワークのパケット処理等、ソフトウェア的な割り込みで消費されたCPU時間 |
| st   | steal : 仮想化環境で、ハイパーバイザにCPU時間を奪われた時間                                                            |

一般的なアプリケーションサーバーにおいて、CPUはユーザー空間のプロセス処理に最も時間を費やします。そのため正常稼働時は、CPU利用率の大部分を「us」が占めるか、あるいは処理待ちの「id」が高い状態を維持します。

load averageが高い状態で、「us」以外の割合が高い場合は、何らかの障害が発生している可能性があります。

- 「us」や「ni」が100％近い：アプリケーションの計算・ループ処理・暗号化処理、アクセスの急増でCPUのスペック不足などが原因の「CPUバウンド」な高負荷です。
- 「sy」が高い： 大量のシステムコール、ネットワーク処理、メモリ管理処理などによるカーネル空間でのオーバーヘッドです。
- 「wa」が高い：ディスクへの読み書き（ストレージI/O）やネットワーク越しのデータ転送を待っている状態です。
- 「st」が高い：同じ物理ホストに同居している「別インスタンス」にCPU時間が奪われている状態です。仮想化環境特有の指標であり、高い値が継続する場合はCPUリソース競合が発生している可能性があります。

### 4~5列目：メモリとスワップの状況

4,5列目は、メモリとスワップの利用量を表示します。
4行目がメインメモリの利用量を、5行目がスワップの利用量を表します。

```plain
MiB Mem : 7922.1 total,  4640.1 free,  1123.3 used,  2436.4 buff/cache
MiB Swap: 4096.0 total,  4096.0 free,     0.0 used.  6798.8 avail Mem
```

| 項目       | 説明                             |
| ---------- | -------------------------------- |
| total      | メモリやスワップの全量           |
| free       | 使用していないメモリやスワップ量 |
| used       | 使用中のメモリやスワップ量       |
| buff/cache | キャッシュに利用しているメモリ量 |
| avail Mem  | すぐに用意できる空きメモリ量     |

メモリの全体像は、おおむね「実際に使われている領域（used）」「キャッシュ領域（buff/cache）」「完全に余っている領域（free）」に分類されます。
ただし、カーネル内部の動的メモリ（Slab）などの扱いにより、単純に足し算しても 「total」 と完全には一致しない場合があります。
「buff/cache」の一部は、メモリがひっ迫するとすぐに空きメモリ容量に充てられます。

利用できる空きメモリの総量を知りたい場合は、「avail Mem」を確認します。
「avail Mem」は、「キャッシュをどのくらい解放しても、システムのパフォーマンスに影響を与えないか」を考慮して、実際に利用可能なメモリ量を計算しています。

以前は、「free + buff/cache」から空きメモリ容量を計算していました。
しかし、「buff/cache」には、「書き込み中で、すぐ削除できないデータ（Dirtyページ）」や「OS自身が動作するために必要なデータ」も含まれます。そのため、「buff/cache」のすべてを空きメモリ容量として見積もると、メモリが足りなくなる可能性があります。

そこで、「avail Mem」が表示されるようになりました。
「avail Mem」は、ページキャッシュや reclaim 可能なメモリ量、ウォーターマークなどを考慮して、実際に利用可能と推定されるメモリ量を計算しています。

警戒すべきなのは、Swapの「used」が増加している状態です。
メモリ残量が足りなくなると、カーネルはメモリ内のanonymousページをストレージのスワップ領域に書き出します（スワップアウト）。その後、データが再度必要になると、ストレージからメモリに書き戻します（スワップイン）。
しかし、ストレージへのアクセスはメモリに比べて桁違いに遅くなります。そのため、スワップイン／アウトが高頻度で発生すると、ディスクI/O待ち（%wa上昇）となり、パフォーマンスが低下します（スラッシング）。

### 6列目以下：プロセスの状況

6行目以下は、個別のプロセスの状況を表示します。

```plain
PID  USER    PR  NI    VIRT   RES   SHR  S  %CPU  %MEM     TIME+  COMMAND
53   root    20   0       0     0     0  S  0.7    0.0    0:00.16 kcompactd0
```

| 項目    | 説明                                                                 | 補足                                                                                       |
| ------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| PID     | プロセスID                                                           |                                                                                            |
| USER    | 実行したユーザー                                                     |                                                                                            |
| PR      | 優先度（priority）                                                   | 数値が低いほど優先度が高い。「rt」となっている場合は real-time (最優先) で実行されている。 |
| NI      | 相対的優先度（nice）                                                 | rt の場合を除き、PR ≒ 20 + NI となる。数値が低いほど優先度が高い。                         |
| VIRT    | 確保されている仮想メモリ量（Virtual）                                | スワップも含む。実際には使っていない「予約分」も含みます                                   |
| RES     | 使用している物理メモリ量(Resident)                                   | スワップを含まない。物理メモリのうち、実際に消費されているメモリ容量。                     |
| SHR     | 他のプロセスと共有される可能性のあるメモリ量（Shared）               | RES のうち、共有メモリとして消費されているメモリ容量。                                     |
| S       | プロセスのステータス(Status)                                         |                                                                                            |
| %CPU    | CPU利用率                                                            | 前回サンプリングからの、CPUコア1つあたりに対する使用率。                                   |
| %MEM    | メモリ使用率                                                         | 物理メモリ総量に対する、RES の割合（％）。                                                 |
| TIME+   | プロセスが起動してから、CPU により処理された総時間(100分の1秒単位)。 |                                                                                            |
| COMMAND | 実行プロセス名                                                       |                                                                                            |

プロセスのメモリ利用量を正確に把握するには、「VIRT」ではなく「RES」を確認します。
「VIRT」には「将来使う予定」としてカーネルに申請（コミット）しただけの仮想メモリ領域も含まれるため、実際の物理メモリ消費量とは大きく乖離するケースがあるためです。

「RES」は、プロセスが現在物理メモリ上に保持しているページ量を表します。より厳密に言えば、共有メモリも含まれるため、単純な合計値は実メモリ使用量と一致しません。

「%CPU」の値は、デフォルト（Irixモード）では「CPU1コア = 100％」として計算されるため、4コアの環境であれば1プロセスが最大400％まで表示される場合があります。なお、`top` の実行中に `Shift + i`を押すことで、全コアの合計を100%とするモード（Solarisモード）に切り替えることも可能です。


プロセスのステータス（S）の表示は、以下の通りです。

| 項目 | 説明           |
| ---- | -------------- |
| D    | 割り込み不能   |
| R    | 実行中         |
| S    | スリープ状態   |
| T    | 停止中         |
| Z    | ゾンビプロセス |

## 2 `top`コマンドの表示変更方法

`top` コマンドの実行中に、以下のキーを叩くことで、表示を切り替えられます。


- `M`(`Shift` + `m`)：プロセスを メモリ（Memory）消費量順に並び替えます。
- `P`(`Shift` + `p`)：プロセスを CPU消費量順に並び替えます（デフォルト）。
- `T`(`Shift` + `t`)：通算CPU消費時間（TIME+）が多い順に並び替えます。
- `P`(`Shift` + `n`)：PID順に並び替えます。
- `R`(`Shift` + `r`)：ソート順の昇順/降順を入れ替えます。
- `L`(`Shift` + `l`)：文字列検索欄「Locate string」が表示されます。そのまま「検索したい文字列」 + `Enter` でヒットした文字列がハイライトされます。
- `1` ： CPU利用率をコアごとに表示します。
- `c` ：「COMMAND」の部分が絶対パスで表示されます。
- `u` ：ユーザー検索欄「Which user」が表示されます。そのまま「検索したいユーザー名」 + `Enter` でヒットしたユーザーがハイライトされます。
- `k` ： killするプロセス指定欄「PID to signal/kill」が表示されます。そのまま「killしたいプロセスID」 + `Enter` でkillを実行します。

## 3 値の見かた例

では、簡易的な例を3つ紹介します。
実際の障害は複雑で、`top`コマンドの値だけでは原因が特定できない場合も多いでしょう。
あくまで、`top`コマンドを見慣れてない人向けの、練習教材としてご覧ください。

###  アプリの過負荷

```plain
top - 17:30:00 up 10 days,  2:30,  1 user,  load average: 12.50, 8.10, 4.20
Tasks: 165 total,   6 running, 159 sleeping,   0 stopped,   0 zombie
%Cpu(s): 98.5 us,  1.0 sy,  0.0 ni,  0.0 id,  0.5 wa,  0.0 hi,  0.0 si,  0.0 st
MiB Mem :   7960.5 total,    120.3 free,   3500.2 used,   4340.0 buff/cache

    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
   4120 nginx     20   0  350412  85220  12400 R  99.9   1.1   5:12.30 nginx
   4121 nginx     20   0  350412  85110  12400 R  99.5   1.1   5:10.12 nginx
   4122 nginx     20   0  350412  85150  12400 R  98.8   1.1   5:08.45 nginx
   4123 nginx     20   0  350412  84990  12400 R  98.0   1.1   4:59.88 nginx
```

4コアの環境だとします。

まず、直近1分間のload averageが12を超えています。4コアの環境では、完全にCPUのキャパを超えています。
また、直近15分間は4.20、直近5分間は8.10、直近1分間は12.50と増加傾向であるため、現在進行形で悪化している状況が見えます。

％CPUの列を見ますと、「us」が98.5を占めています。これにより、アプリの計算等のためにCPUの時間のほとんどが費やされているのがわかります。

プロセス欄を見ると、Webサーバーである nginx のプロセスたちが、それぞれ1つのコアを100%利用しています。ステータス（S）もすべて R（Running：実行中） に張り付いています。

これらの状況から、アプリの暴走やアクセスの急激な増加によって、CPUが純粋な計算パワー不足に陥っていることが推測されます。

###  コンテキストスイッチ過負荷

```plain
top - 17:32:00 up 12 days,  8:40,  1 user,  load average: 85.00, 70.12, 50.00
Threads: 8450 total,  42 running, 8408 sleeping,   0 stopped,   0 zombie
%Cpu(s): 15.0 us, 75.0 sy,  0.0 ni,  0.0 id,  0.0 wa,  0.0 hi, 10.0 si,  0.0 st
MiB Mem :   7960.5 total,     60.1 free,   7200.4 used,    700.0 buff/cache

    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
   8910 python3   20   0  125412  12220   4500 R   5.2   0.2   0:01.12 python3
   8911 python3   20   0  125412  12220   4500 R   4.8   0.2   0:01.10 python3
   ... (以下、数千行にわたってpython3の微小なプロセスが敷き詰められる※対話キー 'H' でスレッド表示を有効にした状態を想定) ...
```

4コアの環境だとします。

まず、直近1分間のload averageが85を超えており、直近5分間、直近15分間の値を比べて増加しています。
CPUの負荷が、現在進行形で悪化している状況が見えます。

次に、％CPUの列を見ますと、「sy」(システム・カーネルの処理時間)が75.0%も占めています。これにより、CPUはアプリケーション本体の処理ではなく、アプリケーションが発生させた大量のシステム処理に時間を費やしていると推測されます。

Task（Thread）数を見ると、8450ものタスクを処理していることがわかります。％CPUの「sy」が75.0%と異常に高いことから、アプリケーションが大量のプロセス/スレッドを高速に生成・破棄（fork/exit）しているか、限られたコアを数千のスレッドで激しく奪い合っている（コンテキストスイッチの多発）可能性があります。

### スラッシング

```plain
top - 18:00:00 up  1 days, 12:45,  1 user,  load average: 45.20, 30.10, 15.00
Tasks: 210 total,   1 running, 154 sleeping,   0 stopped,  0 zombie
%Cpu(s):  0.5 us,  4.5 sy,  0.0 ni,  0.0 id, 95.0 wa,  0.0 hi,  0.0 si,  0.0 st
MiB Mem :   3950.1 total,     45.2 free,   3850.4 used,     54.5 buff/cache
MiB Swap:   2048.0 total,      5.0 free,   2043.0 used,     12.0 avail Mem

    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
   6120 java      20   0 8500412 125012  1400 D   4.5   3.1  45:12.02 java
   6121 java      20   0 8500412  95400  1400 D   3.1   2.4  44:10.15 java
```

2コア、メモリ4GBの環境とします。

まず、直近1分間のload averageが45を超えており、直近5分間、直近15分間の値を比べて増加しています。
こちらも、CPUの負荷が現在進行形で悪化している状況が見えます。

次に、％CPUの列を見ますと、「wa」(ディスクI/O待ち時間)が95.0%も占めています。
さらにメモリとスワップの列を見ますと、avail Memはたったの12MiB、メモリのfreeやbuff/cache、スワップのfreeも残りわずかです。スワップのusedもほぼ満杯近く埋まっています。大量のスワップ使用とavail Mem枯渇が同時に発生しているため、メモリ不足に起因するスラッシングが疑われます。


## まとめ

- `top`は、障害の一次切り分けに有効なコマンドである
- load average は「コア数」と比較して評価する
- CPU高負荷時は %Cpu(s) を見て原因を切り分ける
- メモリ不足の判断には avail Mem を見る
- 実メモリ使用量を見るときは RES を確認する
