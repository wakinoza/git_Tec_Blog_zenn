## はじめに

- 個人開発中に、GitHubのブランチ保護ルールを利用した際に、勉強したことをまとめています。
- 間違い等あれば、指摘いただけると助かります。


## 1\. GitHubのブランチ保護とは

チーム開発では、コードレビューが重要です。コードレビューとは、コードを書いた本人以外の開発者がコードを確認し、問題点や改善点についてフィードバックすることです。GitHubでは、多くの場合、Pull Request（PR）を作成し、そのタイミングでコードレビューを行います。

しかし、ブランチ保護を設定していない場合、GitHubではレビューを必須とせずにブランチへ変更をマージできます。そのため、実務では「PRを作成する」「レビューで承認を得る」といった開発ルールを、GitHubの機能によって強制することがあります。

そのときに役立つのがブランチ保護です。

ブランチ保護を利用すると、特定のブランチに対して、さまざまな制約を設定できます。例えば、Pull Request経由での変更を必須にしたり、必要な承認レビュー数を指定したり、強制プッシュ（git push --force）を禁止したりできます。

これにより、PRを作成するだけでなく、必要な承認レビューを取得しなければマージできない仕組みをGitHub上で強制できます。


## 2\. ブランチ保護ルールとルールセット

GitHubには、ブランチを保護する仕組みとして、「ブランチ保護ルール」と「ルールセット」があります。

どちらも、特定のブランチやブランチのパターンに対して、Pull Requestの必須化やレビューの要求、強制プッシュの禁止などのルールを設定するという役割は共通しています。

両者の大きな違いの一つが、複数のルールが同じブランチに該当した場合の挙動です。


ブランチ保護ルールでは、1つのブランチに複数のブランチ保護ルールが該当する場合、優先順位に基づいて、適用されるブランチ保護ルールが1つに決まります。
そのため、複数のブランチ保護ルールを組み合わせて、1つのブランチに同時に適用することはできません。


ルールセットには、ブランチ保護ルールのような「どのルールを優先するか」という仕組みはありません。
1つのブランチに複数のルールセットが該当する場合、それぞれのルールセットが同時に適用されます。
同じ種類のルールが複数のルールセットで設定されていて競合する場合は、より厳しい制限が適用されます。

このように、ブランチ保護ルールが「該当するルールのうち1つだけが適用される」仕組みなのに対し、ルールセットは「複数のルールセットを組み合わせて適用する」ことを前提とした仕組みになっています。

## 3\. ブランチ保護ルールの作成方法

ブランチ保護ルールは、指定したルールに基づいてブランチを保護する仕組みです。

1つのリポジトリ内に、複数のブランチ保護ルールを設定できます。

保護対象には、特定のブランチを指定できるほか、`fnmatch`構文（パターンによって文字列を照合する構文）を使用して、複数のブランチを対象にすることもできます。

例えば、`main`を指定すると`main`ブランチだけが対象になります。

一方、`feature/*`と指定すると、`feature/`で始まるブランチを対象にできます。

また、`*`を指定すると、現在存在するブランチだけでなく、将来作成されるブランチも含めて、すべてのブランチを対象にできます。

:::message
`fnmatch`構文には、`*` が `/`をまたいで一致しないという仕様があります。例えば、`feature/*` は `feature/foo` には一致しますが、`feature/foo/bar` には一致しません。
:::

### 3.1 複数のブランチ保護ルールが同じブランチに該当する場合

1つのブランチに複数のブランチ保護ルールが該当する場合でも、適用されるブランチ保護ルールは1つだけです。どのルールを適用するかは、ルールの優先順位によって決まります。

優先順位は、基本的に次のように決まります。

* 同じブランチに該当するルールの中では、特定のブランチ名を含むルールが高い優先順位を持つ
* 同じ特定のブランチ名を参照するルールが複数ある場合は、先に作成されたルールが高い優先順位を持つ
* `*`、`?`、`]`などの特殊文字を含むパターンのルール同士では、先に作成されたルールが高い優先順位を持つ

例えば、次の3つのルールがあるとします。

```text
*
feature/*
feature/foo
```

新しく`feature/foo`ブランチを作成したとすると、すべてのブランチ保護ルールに該当します。
しかし、`feature/foo`という特定のブランチ名を指定したルールが最も高い優先順位を持つため、実際に適用されるのは`feature/foo`のルールです。

このように、ブランチ保護ルールでは複数のルールを組み合わせて適用することはできません。複数のルールを同じブランチに適用したい場合は、ルールセットの利用を検討する必要があります。

### 3.2 ブランチ保護ルールの作成方法

1. リポジトリのメインページ上部にある ［Settings］をクリックし、左側のサイドバーにある［Branches］をクリックしてください。
2. 初めてルールを設定する場合は、［Add branch protection rules］をクリックしてください。2回目以降の場合は、［Branch protection rules］の右側にある［Add rule］をクリックしてください。
3. ［Branch name pattern］に、対象とするブランチ名またはブランチ名パターンを記述してください。

   * 特定のブランチを対象にする場合：例）`main`
   * `feature/`で始まるブランチを対象にする場合：例）`feature/*`
   * 現在および将来のブランチのすべてを対象にする場合：例）`*`

4. 必要な保護ルールを設定します。

特に重要なのは、「Require a pull request before merging」と「Require approvals」です。

「Require a pull request before merging」は、マージ前のPull Requestを必須にすることで、対象ブランチへの直接マージを禁止します。
しかし、「Require a pull request before merging」だけでは、PRを作ればマージできてしまうため、コードレビューの実施までは必須にできません。
そこで、「Require approvals」を組み合わせます。
「Require approvals」は、Pull Requestをマージする前に、指定した人数以上の承認レビューを必須にします。例えば「1人」に設定すると、少なくとも1人の承認が必要になります。

この2つを組み合わせることで、チーム開発では「レビューを受けて承認された変更だけをマージする」という開発フローを強制できます。

その他の保護ルールは、以下の通りです。

| 項目                                                | 説明                                                                                                                                                                       |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dismiss stale pull request approvals                | 新しいコミットがPull Requestに追加された場合、それ以前に取得した承認を無効にします。承認後にコードが変更された場合、変更後のコードを改めてレビューすることを求められます。 |
| Require review from Code Owners                     | CODEOWNERSファイルで指定したコードオーナーからのレビュー承認を必須にします。特定のファイルやディレクトリについて、担当者によるレビューを必須にできます。                   |
| Require approval of the most recent reviewable push | Pull Requestの最新の変更（reviewable push）について、承認を必須にします。承認後に新しいコミットが追加された場合でも、最新の変更を確認した承認者による承認を要求できます。  |
| Require status checks to pass before merging        | 指定したステータスチェック成功時にのみ、マージを許可します。                                                                                                               |
| Require conversation resolution before merging      | Pull Request上のレビューコメントなど、未解決のConversationが残っている場合にマージを禁止します。レビューで指摘された問題を解決してからマージする運用にできます。           |
| Require signed commits                              | 署名されたコミットのみを受け付けます。コミットが特定の開発者によって作成されたことを暗号学的に検証しやすくします。                                                         |
| Require linear history                              | マージコミットを作成しない、直線的なGit履歴を必須にします。Merge commitを禁止するため、履歴をシンプルに保てます。                                                          |
| Require deployments to succeed before merging       | 指定した環境へのデプロイが成功するまで、マージを許可しません。デプロイ結果をマージ条件にできます。                                                                         |
| Lock branch                                         | ブランチを読み取り専用にします。ブランチへのPushを禁止し、既存のコミット履歴を変更できない状態にします。                                                                   |
| Do not allow bypassing the above settings           | 管理者など、通常はブランチ保護ルールを回避できるユーザーについても、この保護ルールを適用します。                                                                           |
| Allow force pushes                                  | Force pushを許可します。通常の共有ブランチではOFFが推奨されます。                                                                                                          |
| Allow deletions                                     | ブランチの削除を許可します。重要なブランチではOFFが推奨されます。                                                                                                          |


5. 最後に、画面下部の ［Create］ をクリックしてください。ブランチ保護ルール作成が完了します。

なお、ルール作成時点で対象となるブランチが存在している必要はありません。
例えば、まだ存在しない`feature/foo`を対象とするルールを事前に作成しておけば、後から`feature/foo`ブランチが作成された時点で、そのルールの対象になります。

## 4\. ルールセットの作成方法

ルールセットは、ブランチやタグなどに対して適用するルールをまとめた、名前付きのルールの集合です。
リポジトリ単位で設定できるほか、GitHub TeamやGitHub Enterpriseでは、Organizationレベルで複数のリポジトリを対象にすることもできます。
1つのリポジトリには最大75個のルールセットを設定できます。また、Organizationレベルでは最大75個のルールセットを設定できます。
JSONファイルを使って、事前構築済みのルールセットをインポートすることも可能です。

1つのブランチに複数のルールセットが該当する場合、適用可能なすべてのルールセットが適用されます。
同じ種類のルールが複数のルールセットで設定されていて競合する場合は、最も厳しい制限が適用されます。

「ブランチ保護ルール」より新しく提供された「ルールセット」には、柔軟に保護ルールを管理するための仕組みが用意されています。

| 仕組み                         | 説明                                                                                                                                                            |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ルールセットの適用状態を変更   | ルールセットを削除することなく、ルールセットの適用状態（Active:適用、Disabled：非適用）を変更できます。                                                         |
| タグのルールセット             | ブランチだけでなく、タグも対象にできます。                                                                                                                      |
| プッシュルールを設定           | リポジトリへのpushを、ファイルパス、ファイル拡張子、ファイルサイズなどの条件で制限します。GitHub Teamでは、internal/privateリポジトリなどを対象に利用できます。 |
| 複数のリポジトリを対象にできる | Organizationレベルでは、複数のリポジトリを対象にできます。利用可能な範囲はGitHubのプランによって異なります。                                                    |


### 4.1 ルールセットの作成方法

ブランチを対象としたルールセットの作成方法を説明します。

1. リポジトリのメインページ上部にある ［Settings］→ 左側のサイドバーにある［Rulesets］→ ［Rulesets］をクリックしてください。
2. ［New ruleset］→ ［New branch ruleset］をクリックしてください。
3. ［Ruleset Name］に、任意のルールセット名を記述してください。対象となるブランチは別の項目で設定するため、［Ruleset Name］には他のルールセットと識別しやすい名前を記述します。
4. ［Enforcement status］にルールセットの適用状態を選択します。
   - Active：適用
   - Disabled：非適用
5. ［Bypass list］は、通常はルールセットによって禁止・制限される操作を、例外的に許可する対象者のリストを指定します。主に、通常時はルールによって保護しつつ、緊急時などには例外的にルールを回避できるユーザーやチームなどを指定するために使用します。［Bypass list］では、例えば次のような対象者を指定できます。
    - Repository administrators
    - Organization owners
    - Maintain / Writeロールを持つユーザー
    - 特定のTeam
    - GitHub Apps
6. ［Target branches］は、そのルールセットを適用する対象ブランチを指定します。ブランチ名を直接指定することも、ブランチ保護ルールと同様に`fnmatch`構文を使用して、複数のブランチを対象にすることも可能です。
7. ［Rules］で、具体的なルールを指定します。


| 項目                                      | 説明                                                                                                                                                                                |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Restrict creations                        | 対象パターンに一致するブランチやタグの作成を制限します。チェックすると、Bypass権限を持つユーザーだけが対象となるブランチ・タグを作成できるようになります。                          |
| Restrict updates                          | 対象ブランチ・タグへの更新（push）を制限します。チェックすると、Bypass権限を持つユーザーだけが対象ブランチ・タグを更新できます。                                                    |
| Restrict deletions                        | 対象ブランチ・タグの削除を制限します。チェックすると、Bypass権限を持つユーザーだけが削除できます。                                                                                  |
| Require linear history                    | Gitのコミット履歴を一直線に保つことを要求します。merge commit（マージによって作られる統合用コミット）を対象ブランチに入れることを防ぎます。                                         |
| Require deployments to succeed            | 指定した環境へのデプロイが成功するまで、変更をマージできなくします                                                                                                                  |
| Require signed commits                    | 署名され、GitHubで検証済みのコミットだけを対象ブランチに入れられるようにします。                                                                                                    |
| Require a pull request before merging     | 対象ブランチへの変更をPull Request経由にすることを要求します。PRを必須とする設定の追加設定としてレビュー数、Code Owner、stale approval、conversation resolutionなどを設定できます。 |
| Require status checks to pass             | 指定したStatus checks（CIなどの自動チェック）が成功するまで、対象ブランチへの変更を許可しません。                                                                                   |
| Block force pushes                        | Force pushを禁止します。                                                                                                                                                            |
| Require code scanning results             | コードスキャン（ソースコードの脆弱性などを自動検査する仕組み）の結果を、マージ条件にします。                                                                                        |
| Require code quality results              | コード品質分析の結果をマージ条件にします。                                                                                                                                          |
| Restrict code coverage                    | テストカバレッジ（テストがコードをどの程度実行しているか）に最低基準を設けます。                                                                                                    |
| Automatically request Copilot code review | 新しく作成されたPull Requestについて、条件を満たしていればGitHub Copilotによるコードレビューを自動的に要求します。                                                                  |

8. 最後に、画面下部の ［Create］ をクリックしてください。ルールセット作成が完了します。


## 5\. 両方のルールが混在するときの仕様

2026年8月現在では、「ブランチ保護ルール」と「ルールセット」の2つの仕組みが用意されています。

では、1つのブランチに「ブランチ保護ルール」と「ルールセット」の両方が該当した場合、どのような挙動になるのでしょうか。
ブランチ保護ルールについては、該当するルールのうち優先順位の最も高い1つが適用されます。一方、ルールセットについては、該当するルールセットが複数あれば、それらが同時に適用されます。さらに、ブランチ保護ルールとルールセットが同じブランチに該当する場合も、両者のルールが適用されます。
同じ種類のルールが競合した場合は、最も制限の厳しいルールが適用されます。


また、ブランチ保護は便利な仕組みですが、必要以上に設定すると、開発スピードを低下させる可能性があります。
そのため、開発フローに対して過剰な制約となる場合は、ルールを緩和するなど、開発チームの状況に合わせて設定することが重要です。

## 6. 個人開発でのブランチ保護ルールの活用事例

ここまで、ブランチ保護の仕組みと設定方法について説明してきました。

ここでは、私の個人開発でどのようにブランチ保護を利用しているかという実例を紹介します。

今回の開発では、次のようなブランチ運用をしています。

* 1人で開発している
* `main` をデフォルトブランチとして使用
* 機能追加や修正は `feature/*` ブランチで行う
* 開発が完了したらPull Requestを作成して `main` にマージ
* マージ後は、使用したfeatureブランチを削除
* 作業中のfeatureブランチを除き、常設しているブランチは `main` のみ

そのため、保護対象としているのも `main` ブランチだけになります。

### 6.1 個人開発でブランチ保護を利用する理由

ブランチ保護というと、チーム開発でコードレビューやCIを必須にするための機能というイメージがあります。

しかし、個人開発でもブランチ保護にはメリットがあります。
例えば、mainブランチの削除を禁止することで、誤操作によるmainブランチの削除を防ぐことができます。

また、mainブランチへの直接変更やForce pushを禁止することで、自分で決めた開発フローをGitHub上で強制することも可能です。

これにより、誤操作によって完成済みのコードを直接変更したり、リモートのmainブランチの履歴をForce pushによって書き換えるリスクを下げることができます。

### 6.2 実際に設定しているルール

今回の開発では、`main` に対して次のルールを設定しています。

| ルール                                    | 設定   | 設定理由                                                                          |
| ----------------------------------------- | ------ | --------------------------------------------------------------------------------- |
| Target branches                           | `main` | 保護対象がmainだけであるため                                                      |
| Require a pull request before merging     | ON     | `main`への変更をPull Request経由にするため                                        |
| Require status checks to pass             | OFF    | 現在、マージ前に要求するStatus checks（CIなどの自動チェック）を設定していないため |
| Do not allow bypassing the above settings | ON     | ブランチ保護を管理者である自分にも適用させるため                                  |
| Allow force pushes                        | OFF    | `main`の履歴がForce pushによって書き換えられることを防ぐため                      |
| Allow deletions                           | OFF    | `main`が誤って削除されることを防ぐため                                            |

`Require approvals` はOFFにして運用しています。
チーム開発ではコードレビューを必須にするために重要な設定ですが、ひとり開発では第三者による承認を取得できないためです。
