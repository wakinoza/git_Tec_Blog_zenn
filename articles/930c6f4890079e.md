## はじめに

- Python開発を行う際に`.venv`という仮想環境を利用しています。この仮想環境っていったい何だろうと疑問に思ったので、調べてみました。
- この記事では、Pythonの仮想環境.venvの目的・仕組み・Git管理の有無・再構築方法まで整理していきます。
- 間違い等あれば、指摘いただけると助かります。

## 結論

- 仮想環境は、プロジェクトごとにPythonのパッケージ環境を分離するための仕組みです。
- `venv`モジュールを利用して仮想環境を作成し、`.venv`などのディレクトリに環境を構築します。
- `.venv`は環境に依存するファイルを含むため、通常はGitで共有せず、requirements.txtなどを使って各環境で再構築します。
- requirements.txtにはプロジェクトで使用するパッケージとバージョンなどを記録し、別の開発環境でも必要なパッケージ環境を再構築できるようにします。

- Visual Studio Code

# 1. Pythonの仮想環境とは

## 1.1 仮想環境が必要になる理由

Pythonでは、機能を追加するために外部パッケージ（Pythonに機能を追加するライブラリ）を利用することがあります。

例えば、Web APIへアクセスする処理を実装する場合、`requests` というパッケージを利用できます。

パッケージは `pip` というパッケージ管理ツールを使ってインストールします。
`pip`を利用して、`requests` パッケージをインストールする場合は、以下のコマンドを実行します。

```bash
pip install requests
```

しかし、複数のPythonプロジェクトを開発していると、プロジェクトごとに必要なパッケージやバージョンが異なる場合があります。

例えば、次のような2つのプロジェクトがあるとします。

```text
プロジェクトA
└─ requests 2.xが必要

プロジェクトB
└─ requests 3.xが必要
```

通常、1つのPython環境では、同じパッケージについて、複数のバージョンを同時にインストールして使い分けることはできません。
例えば、プロジェクトBの要求に合わせてrequestsを3.xへアップデートすると、2.xを必要としていたプロジェクトAが正常に動作しなくなる可能性があります。

このようなパッケージ間の依存関係（どのパッケージがどのバージョンを必要とするか）の衝突を、「依存関係の競合（コンフリクト）」といいます。

そこで、プロジェクトごとにPythonのパッケージ環境を分離するために利用されるのが、仮想環境（Virtual Environment）です。

仮想環境を利用すると、プロジェクトごとにパッケージを分離して管理できます。

```text
プロジェクトA
└─ .venv
   └─ requests 2.x

プロジェクトB
└─ .venv
   └─ requests 3.x
```

仮想環境を利用すると、プロジェクトごとに独立したPython環境を用意し、それぞれ異なるパッケージやバージョンを管理できます。

Python環境を分離することで、プロジェクトAのためにインストールしたパッケージが、プロジェクトBの環境へ直接影響することを防げます。


## 1.2 仮想環境で何が分離されるのか

仮想環境はPython本体そのものを完全に隔離するのではなく、主に使用するPythonインタープリタとパッケージの環境を分離します。

特に重要なのが、パッケージのインストール先です。

仮想環境を使用せずに `pip install` を実行すると、使用しているPython環境のパッケージ保存先にインストールされます。そのため、そのPython環境を利用する他のプロジェクトからも、インストールしたパッケージが利用可能になります。それは同時に、そのPython環境を利用するすべてのプロジェクトが、インストールしたパッケージの影響を受ける可能性があるということになります。

```text
仮想環境なし

Python環境
├─ プロジェクトA
├─ プロジェクトB
└─ プロジェクトC
       ↑
  同じパッケージ環境を利用
```

仮想環境を有効化して、その環境の `pip`を実行すると、パッケージはその仮想環境の `site-packages` にインストールされます。
これにより、パッケージのインストールや更新による影響範囲を、その仮想環境を利用するプロジェクトに限定できます。

```text
仮想環境あり

Python環境
├─ プロジェクトA
│   └─ .venv
│       └─ site-packages
│            └─ プロジェクトA専用のパッケージ
│
├─ プロジェクトB
│   └─ .venv
│       └─ site-packages
│            └─ プロジェクトB専用のパッケージ
│
└─ プロジェクトC
    └─ .venv
        └─ site-packages
             └─ プロジェクトC専用のパッケージ
```

これにより、あるプロジェクトでパッケージを追加・更新・削除しても、別のプロジェクトの環境へ直接影響を与えにくくなります。


# 2. 仮想環境の仕組み

Pythonの仮想環境を作成すると、プロジェクト内に `.venv` というディレクトリを作ることが一般的です。

この章では、`.venv` の内部にどのようなファイルやディレクトリが作られるのかを見ていきます。

## 2.1 `venv` モジュールとは

Pythonの仮想環境は、Python標準ライブラリ（Pythonに標準で含まれている機能）の`venv`モジュールによって作成できます。

標準ライブラリなので、Pythonがインストールされていれば、仮想環境を作成するために別のパッケージをインストールする必要はありません。

仮想環境を作成するときは、次のコマンドを実行します。

```bash
python -m venv .venv
```

`-m`は、Pythonに「指定したモジュールをスクリプトとして実行する」よう指示するオプションです。
上のコマンドは、現在使用しているPythonインタープリタで`venv`モジュールを実行し、`.venv`ディレクトリに仮想環境を作成するコマンドとなります。

では、このコマンドを実行すると、具体的に何が作られるのでしょうか。


## 2.2 `.venv`ディレクトリの構造

Windows環境で仮想環境を作成すると、`.venv`ディレクトリには、おおむね次のような構造が作られます。

```text
.venv/
├─ Include/
├─ Lib/
│  └─ site-packages/
├─ Scripts/
│  ├─ Activate.ps1
│  ├─ activate.bat
│  ├─ pip.exe
│  └─ python.exe
├─ pyvenv.cfg
└─ .gitignore
```

それぞれ役割が異なります。

| ファイル・ディレクトリ | 役割                                                                  |
| ---------------------- | --------------------------------------------------------------------- |
| `Scripts/`             | Pythonや`pip`などの実行ファイル、仮想環境の有効化スクリプトなどを配置 |
| `Lib/site-packages/`   | 仮想環境にインストールしたパッケージを保存                            |
| `Include/`             | C言語による拡張などで使用されるヘッダーファイルを配置                 |
| `pyvenv.cfg`           | 仮想環境に関する設定を記録                                            |
| `.gitignore`           | Gitで管理しないファイルを指定                                         |

この中でも、特に重要なのが`Scripts`、`site-packages`、`pyvenv.cfg`です。


## 2.3 `Scripts`ディレクトリ

`Scripts`ディレクトリには、仮想環境で使用するPythonや`pip`などの実行ファイルが配置されます。

Windows環境では、例えば以下のようなファイルが作成されます。

```text
Scripts/
├─ python.exe
├─ pip.exe
├─ Activate.ps1
└─ activate.bat
```

`python.exe`は、仮想環境でPythonを実行するための実行ファイルです。

また、`Activate.ps1`や`activate.bat`は、仮想環境を有効化するためのスクリプトです。

例えばWindows環境では、以下のコマンドを実行することで、仮想環境を有効化できます。

```powershell
.venv\Scripts\Activate.ps1
```

仮想環境を有効化すると、`PATH`環境変数の先頭に仮想環境のScriptsディレクトリが追加されます。
そのため、`python`コマンドや`pip`コマンドを実行すると、仮想環境側の実行ファイルが優先して使用されます。

また、仮想環境を有効化すると、ターミナル上では次のようにプロンプトの先頭に`(.venv)`と表示されます。

```text
(.venv) PS C:\work\project>
```

これは、現在のシェルで仮想環境が有効になっていることを示しています。


## 2.4 `Lib/site-packages`ディレクトリ

`Lib/site-packages`は、仮想環境にインストールしたPythonパッケージの保存先です。

例えば、以下のコマンドを仮想環境が有効な状態で実行すると、`requests`とその依存パッケージが仮想環境側の`site-packages`にインストールされます。

```bash
pip install requests
```

インストール後は、例えば次のような構造になります。

```text
.venv/
└─ Lib/
   └─ site-packages/
      ├─ requests/
      └─ ...
```

このように、仮想環境ごとにパッケージの保存先を分離することで、プロジェクトごとに異なるパッケージやバージョンを管理できます。

## 2.5 `pyvenv.cfg`

`.venv`には、`pyvenv.cfg`という設定ファイルも作成されます。

例えば、次のような情報が記録されます。

```text
home = C:\...\Python...
include-system-site-packages = false
```

`home`には、仮想環境の作成元となったPythonのインストール場所が記録されます。

また、`include-system-site-packages`は、仮想環境からベースとなるPython環境の`site-packages`を利用できるようにするかどうかを指定します。

デフォルトでは、「include-system-site-packages = false」となっており、ベースとなるPython環境のパッケージを仮想環境から利用しない設定になっています。


## 3\. .venvディレクトリがGit管理されない理由

`.venv`は通常、`.gitignore`に記載してGit管理から除外します。

なぜ、`.venv`をGitで共有しないのでしょうか。

この章では、`.venv`をGit管理しない理由と、仮想環境を「持ち運ぶ」のではなく「再構築する」理由について説明します。

主な理由は、次の3つです。

- 環境に依存する絶対パスを含んでいる
- OSやCPUアーキテクチャに依存したパッケージがインストールされている
- リポジトリが肥大化する

### 3.1 環境に依存する情報を含む

仮想環境には、作成元となったPythonの場所など、作成した環境に依存する情報が含まれています。

例えば、前章で確認した`pyvenv.cfg`  には、次のような`home`が記録されています。

```text
home = C:\...\Python...
```

仮想環境には、作成元のPythonの場所など、作成時の環境に依存する情報が含まれています。
そのため、作成した`.venv`を別のディレクトリへ移動したり、別の環境へコピーしたりすると、パスなどの環境差によって正常に動作しなくなる可能性があります。

### 3.2 OSやCPUアーキテクチャなど、実行環境に依存する

`.venv`の`site-packages`には、Pythonのソースコードだけでなく、C言語などで実装されたネイティブコード（OSやCPUに合わせてコンパイルされたコード）を含むパッケージがインストールされる場合があります。

例えば、Windowsでは`.pyd`ファイル、LinuxやmacOSでは`.so`などの共有ライブラリが利用されることがあります。

そのため、Windowsで作成した`.venv`を、そのままLinuxやmacOSへコピーしても、含まれているバイナリがその環境に対応しておらず、正常に動作しない可能性があります。

また、OS、CPUアーキテクチャ、Pythonのバージョンなどの違いによって、インストールできるパッケージのバージョンや、利用できるバイナリが異なる場合があります。


### 3.3 リポジトリが肥大化する

`.venv`には、Pythonの実行ファイルやインストールしたパッケージなど、実際に実行するためのファイルが含まれています。

プロジェクトで利用するパッケージが増えるほど、`.venv`のサイズも大きくなります。

このようなファイルをすべてGitで管理すると、ソースコードだけを管理する場合と比べて、リポジトリのサイズが大きくなります。

さらに、パッケージを更新するたびに.venv内のファイルにも変更が発生するため、Gitで管理する対象としても適していません。


## 4. `requirements.txt`

前章からわかるように、`.venv`は異なる環境へそのまま持ち運んで利用することを想定したものではありません。

そのため、`.venv`はGitでディレクトリごと共有するのではなく、それぞれの開発環境で必要に応じて作り直すという考え方が基本になります。

では、プロジェクトで使用しているパッケージを、どのように別の開発環境へ伝えればよいのでしょうか。

そこで利用されるのが、`requirements.txt`です。

### 4.1 `requirements.txt`とは

`requirements.txt`は、プロジェクトで利用するPythonパッケージと、そのバージョンなどを記録するテキストファイルです。

例えば、プロジェクトで`requests`を利用している場合、次のように記録できます。

```text
requests==2.32.5
```

`==`を使ってバージョンを指定することで、`requests`の2.32.5を使用することを明示できます。

複数のパッケージを利用している場合は、それぞれを1行ずつ記述します。

```text
requests==2.32.5
python-dotenv==1.1.1
pytest==8.4.2
```

このファイルをGitで管理しておけば、`.venv`そのものを共有しなくても、プロジェクトで利用しているパッケージの情報を他の開発環境へ共有できます。

### 4.2 `requirements.txt`を作成する

`requirements.txt`は、開発者が手動で作成することもできます。

一方、インストールされているパッケージをコマンドで出力した場合は、`pip freeze`コマンドを利用できます。

```bash
pip freeze > requirements.txt
```

`pip freeze`は、現在のPython環境にインストールされているパッケージとバージョンを一覧として出力するコマンドです。
直接インストールしたパッケージだけでなく、その環境にインストールされている依存パッケージなども一覧に含まれます。
`>`（リダイレクト）を利用して出力結果を、`requirements.txt`へ書き込みます。

例えば、仮想環境を有効化した状態で`pip freeze`を実行すると、その仮想環境にインストールされているパッケージが出力されます。


### 4.3 `requirements.txt`からパッケージをインストールする

`requirements.txt`に記録されたパッケージは、`pip install -r`コマンドでまとめてインストールできます。

```bash
pip install -r requirements.txt
```

`-r`は、指定したファイルに記載されたパッケージを読み込んでインストールするためのオプションです。

例えば、次のような`requirements.txt`があるとします。

```text
requests==2.32.5
python-dotenv==1.1.1
```

この状態で、`pip install`を実行すると、記載されているパッケージがまとめてインストールされます。


### 4.4 `.venv`と`requirements.txt`の関係

ここまでの内容を整理すると、`.venv`と`requirements.txt`にはそれぞれ異なる役割があります。

`.venv`には、実際にPythonやパッケージを実行するためのファイルが保存されています。

一方、`requirements.txt`には、プロジェクトが必要とするパッケージとそのバージョンが記録されています。

そのため、`.venv`をGitで共有する代わりに、`requirements.txt`をGitで共有することで、別の開発環境でも仮想環境を再構築できます。



### 4.5 `requirements.txt`は自動的に作成されるのか

`requirements.txt`は、仮想環境を作成しただけでは自動的に作成されません。

そのため、プロジェクトで利用するパッケージを記録する場合は、開発者が作成してGitなどで管理する必要があります。

例えば、新しいプロジェクトでは次のような流れになります。

```text
1. 仮想環境を作成
      ↓
2. 必要なパッケージをインストール
      ↓
3. requirements.txtを作成
      ↓
4. requirements.txtをGitで管理
```

別の環境で開発するときは、次のように再構築できます。

```text
1. プロジェクトを取得
      ↓
2. 新しい仮想環境を作成
      ↓
3. requirements.txtからパッケージをインストール
      ↓
4. 開発環境を再構築
```

この仕組みによって、`.venv`を直接持ち運ばなくても、プロジェクトに必要なパッケージ環境を別の開発環境で再現できます。



## 5. 仮想環境の作成・再構築

ここまで、仮想環境の仕組みと`requirements.txt`の役割について説明しました。

この章では、実際に仮想環境を作成し、必要なパッケージをインストールする方法を確認します。

仮想環境を利用する場面は、大きく分けて次の2つです。

* 新しくプロジェクトを作成するとき
* 既存のプロジェクトを別の開発環境で再構築するとき

### 5.1 新規プロジェクトで仮想環境を作成する

新しいプロジェクトでは、まずプロジェクト用のディレクトリを作成します。

```text
my-project/
```

このディレクトリで、次のコマンドを実行します。

```bash
python -m venv .venv
```

`venv`モジュールによって、`.venv`ディレクトリに仮想環境が作成されます。

作成すると、次のような構成になります。

```text
my-project/
├─ .venv/
└─ ...
```

次に、仮想環境を有効化します。

Windows PowerShellの場合は、次のコマンドを実行します。

```powershell
.venv\Scripts\Activate.ps1
```

有効化されると、ターミナルのプロンプトに`(.venv)`と表示されます。

```text
(.venv) PS C:\work\my-project>
```

`(.venv)`と表示されたターミナルで、その環境の`pip`を使用してパッケージをインストールすると、パッケージは`.venv`内の`site-packages`にインストールされます。

例えば、`requests`をインストールする場合は次のようにします。

```bash
pip install requests
```

必要なパッケージをインストールしたら、現在の環境にインストールされているパッケージを`requirements.txt`に記録できます。

```bash
pip freeze > requirements.txt
```

これで、プロジェクトは次のような構成になります。

```text
my-project/
├─ .venv/
├─ requirements.txt
└─ ...
```

`.venv`はGitで共有せず、`requirements.txt`をGitで管理することで、別の環境でも同じパッケージ構成を再構築できます。

### 5.2 `requirements.txt`がある既存プロジェクトを再構築する

既存のプロジェクトを別の開発環境で利用する場合、`.venv`そのものをコピーするのではなく、新しい仮想環境を作成します。

例えば、Gitからプロジェクトを取得した場合、次のような状態になります。

```text
my-project/
├─ requirements.txt
└─ ...
```

まず、プロジェクトのディレクトリで仮想環境を作成します。

```bash
python -m venv .venv
```

次に、仮想環境を有効化します。

```powershell
.venv\Scripts\Activate.ps1
```

最後に、`requirements.txt`に記録されたパッケージをインストールします。

```bash
pip install -r requirements.txt
```

これにより、`requirements.txt`に記録されたパッケージが新しく作成した`.venv`にインストールされます。


このように、`.venv`をGitで共有しなくても、`requirements.txt`を利用することで、別の開発環境でもプロジェクトに必要なパッケージを同じバージョンでインストールしやすくなります。

## 6. 仮想環境のメリット・デメリット

ここまで説明した内容をもとに、仮想環境を利用するメリットとデメリットを整理します。

### 6.1 仮想環境のメリット

仮想環境を利用する主なメリットは、プロジェクトごとにパッケージ環境を分離できることです。

プロジェクトごとに異なるパッケージやバージョンを使用できるため、あるプロジェクトでパッケージを更新しても、別のプロジェクトへの影響を抑えられます。

また、`requirements.txt`と組み合わせることで、プロジェクトで必要なパッケージを明確にし、別の開発環境でも同じパッケージ構成を再構築しやすくなります。

### 6.2 仮想環境のデメリット

一方で、仮想環境はプロジェクトごとに環境を作成・管理する必要があるため、仮想環境を利用しない場合と比べて環境構築の手順が増えます。

また、`.venv`は環境に依存するファイルを含むため、通常はGitで共有せず、`requirements.txt`などを利用して各環境で再構築します。

このように、仮想環境には環境構築の手間が増えるという側面がありますが、複数のプロジェクトを開発する場合には、パッケージの競合や他のプロジェクトへの影響を抑えやすくなります。

## まとめ

- 仮想環境を利用すると、プロジェクトごとにPythonのパッケージ環境を分離できます。
- `.venv`には仮想環境を動作させるためのファイルや、インストールしたパッケージなどが含まれるため、通常はGitで共有しません。
- 代わりに`requirements.txt`などで必要なパッケージとバージョンを共有し、各開発環境で`.venv`を再構築します。
- 仮想環境には環境構築の手間が増えるという側面がありますが、複数のプロジェクトを開発する場合、パッケージの競合や他のプロジェクトへの影響を抑えやすくなります。

仮想環境は、必ずしもPythonそのものを完全に隔離する仕組みではありません。

プロジェクトごとに依存するパッケージ環境を分離し、その環境を必要に応じて再構築できるようにする仕組みと捉えると、`.venv`と`requirements.txt`がそれぞれ何のために存在するのかも理解しやすくなります。
