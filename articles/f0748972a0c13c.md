## はじめに

- 現在、LinuCレベル１の取得を目指して勉強中です。
- LinuC教科書に、「環境変数PATHにカレントディレクトリを追加することは、セキュリティ上のリスクがある」と書いてあったので、その理由を調べてみました。
- 間違い等あれば、指摘いただけると助かります。

## 結論

- 環境変数PATHにカレントディレクトリ（.）や空文字を含める行為は、PATHハイジャックを招き、結果として任意コード実行（ACE）や権限昇格につながるリスクがある。

- Linuxシステムを安全に運用する上では、PATHの厳密な管理と、相対パス（./）による明示的な実行が不可欠である。


## 1\. 環境変数PATHの基礎知識

環境変数PATHにカレントディレクトリ（.）を含めるリスクを理解するため、まずはPATHの基本的な挙動と探索メカニズムを整理します。

Linuxで`ls`や`mkdir`コマンドを入力した際、OSは裏側で指定した名前の「コマンド（実行ファイル）」を探し出し、実行しています。

コマンドを捜索する際に利用されるのが、環境変数 PATH です。

PATH には、「コマンドが格納されているディレクトリの場所」が、コロン（:）で区切られた一本の文字列として登録されています。
現在のPATH設定を確認するには、ターミナルで以下のコマンドを実行します。

```Bash
echo $PATH

#出力例
/usr/local/bin:/usr/bin:/bin:/usr/local/sbin:/usr/sbin
```

コマンドを探す際に重要になるのが、「PATH変数の文字列に登録されているディレクトリを、左から右へと順番に探索する」という点です。

例えば、`ls`コマンドを実行した場合、システムは次のように動きます。

1. まず、一番左にある「/usr/local/bin」の中に「ls」というファイルがあるか探す。
2. なければ、すぐ右の「/usr/bin」の中を探す。
3. さらになければ、その右の「/bin」の中を探す。
4. 「/bin/ls」が見つかった時点で探索を終了し、そのプログラムを実行する。
5. もし、指定されたすべてのディレクトリを探してもコマンドが見つからなかった場合に初めて、画面に「command not found」というエラーが表示される。

検索が左から右の順番で行われるため、PATHにパスを追加する際は、優先度に合った追加場所を指定します。

| 優先度 | 追加位置           | コマンド例                       |
| ------ | ------------------ | -------------------------------- |
| 高     | 文字列の先頭に追加 | export PATH=/opt/myapp/bin:$PATH |
| 低     | 文字列の末尾に追加 | export PATH=$PATH:/opt/myapp/bin |


## 2\. PATHに「.」追加は、なぜアンチパターンなのか？

環境変数PATHにカレントディレクトリ（.）を含めることがなぜ危険なのか。
それは、前述の「左から右へ」という探索順序のルールによって、攻撃のきっかけとなる危険な状態を作ってしまうためです。

PATH の先頭に入れた場合と末尾に入れた場合、それぞれで発生する2つの脆弱性を具体例とともに解説します。

### 2\.1\. 先頭に「.」がある場合

PATH の先頭に「.」を追加すると、システムは「今いるディレクトリ（カレントディレクトリ）」を、その他の標準コマンドよりも最優先で探索するようになります。
ここで登場するのが、「PATHハイジャック」という脅威です。

PATHハイジャックとは、環境変数PATHに登録された探索順序を悪用し、攻撃者が用意したプログラムを実行させる攻撃です。
セキュリティの世界では「不信頼な検索パス（CWE-426: Untrusted Search Path）」の一種に分類されます。

具体的な攻撃方法を説明しましょう。

悪意を持った一般ユーザーが、全ユーザーが共有で使うディレクトリ（例：/tmp）に、標準コマンド（`ls`）などと同名の悪意のあるファイルを配置したとします。
悪意のあるファイルには、実行したユーザーの秘密情報を秘密裏に攻撃者のサーバーに送信した後、本来の /bin/ls を実行して何事もなかったかのように見せるスクリプトが書かれています。

この状態で、PATH の先頭に「.」を含めてしまっている別のユーザーが/tmpディレクトリに移動し、`ls`コマンドを実行したとしましょう。

するとシステムは、本来の /bin/ls を見つける前に、カレントディレクトリ（/tmp）にある偽物の悪意のあるファイルを最優先で見つけ、実行してしまいます。
コマンドを実行したユーザーは、裏で不正な処理が走ったことに気づくことすら困難です。

### 2\.2\. 末尾に「.」がある場合

「先頭がダメなら、一番優先度の低い『末尾』に . を入れれば安全なのでは？」と考えるかもしれません。
しかし、これも明確なアンチパターンです。

分類としては先頭の場合と同じく「PATHハイジャック」に該当しますが、末尾にある場合は、攻撃のトリガーとして「タイポスクワッティング（打ち間違い誘導）」の手法が組み合わされるという特徴があります。

タイポスクワッティングとは、ユーザーがコマンドを入力する際の打ち間違い（タイポ）を先回りして予測し、その名前で悪意のある罠を仕掛けておく手法です。

具体例を出して説明しましょう。

PATH の末尾に「.」がある場合、標準コマンド（`ls`や`cd`など）を正しく入力している限りは、左側にある標準ディレクトリ（/bin など）が優先されます。
そのため、標準コマンドと同名の悪意のあるファイルが存在しても、それらのファイルは実行されません。

しかし、人間は打ち間違いをします。
例えば、`ls`と打とうとして、誤って`lss`と打ち間違えてしまうこともあるでしょう。

攻撃者は、人間ならどうしても起こるタイポに付け入ります。
悪意のあるファイルに、よくあるタイポ（`lss`など）の名前を付けるのです。

タイポ名が付いた悪意のあるファイルが存在する場合、システムは次のようにコマンドを探します。

1. 左側の標準ディレクトリ（/usr/bin や /bin など）をすべて探すが、当然 lss というコマンドは見つからない。
2. 最後に、一番右端（末尾）に登録されている .（カレントディレクトリ）を探しに行く。
3. カレントディレクトリに攻撃者が用意した 「lss」という悪意ある実行ファイルが置かれていた場合、それが実行されてしまう。

「末尾への追加」は、一見すると標準コマンドを守っているように見えますが、「ユーザーがタイポした瞬間に、カレントディレクトリの未知のファイルに実行権限を明け渡す」 という脆弱性を生み出しています。


このように、環境変数PATHの先頭に「.」があれば「日常的なコマンド実行」が乗っ取られ、末尾にあれば「うっかりしたタイポ」が命取りになります。

これが、環境変数PATHに「.」を追加することがアンチパターンとされる理由です。

## 3\. 最悪のシナリオ：共有ディレクトリを悪用した権限昇格攻撃

ここまで、PATHハイジャックの危険性を解説しましたが、これらが引き起こす最悪の結末が「権限昇格（Privilege Escalation）攻撃」です。

rootユーザーが攻撃者の配置したプログラムを実行してしまうと、そのプログラムはroot権限で動作します。その結果、攻撃者はそのプログラムを通じて本来持たない管理者権限で処理を実行できるようになり、権限昇格につながります。

具体的に見ていきましょう。

システム全体の共通設定（/etc/profile など）や管理者の環境設定（.bashrc など）で、誤って「.」が PATH に混入していた場合を想定します。

Linuxには、/tmp や /var/tmp といった、すべてのユーザーが自由にファイルを読み書きできる「共有ディレクトリ」が存在します。

悪意のあるユーザーは、この共有ディレクトリの性質を悪用して、以下のような罠を仕込みます。

1. 全ユーザーが書き込める /tmp ディレクトリに移動する。
2. そこに`ls`などの標準コマンドと同名、あるいは`lss`などのタイポを狙った名前のファイルを作成する。
3. そのファイルの中に、root権限でバックドアを設置する、あるいはroot権限で`chmod u+s`を実行してSUIDを付与するようなスクリプトを記載する。
4. rootユーザーが /tmp ディレクトリに移動（`cd /tmp`）し、中身を確認しようと`ls`コマンドを実行する。

この時、rootユーザーの環境変数PATHの先頭（または末尾でタイポした際）に「.」が含まれていた場合、カレントディレクトリにある悪意のあるファイルが管理者権限で実行されてしまいます。

攻撃を受けたのが、一般ユーザーであれば、被害はそのユーザーが持つファイルや権限の範囲内に留まります。
しかし、rootユーザーが攻撃を受けると、その被害範囲は拡大します。
システム全体のパスワードファイルの書き換え、バックドアの設置、ログの消去など、システム全体が悪意のあるユーザーに乗っ取られてしまいます。

これが「権限昇格攻撃」のメカニズムです。


## 4\. その他の類似アンチパターン

「環境変数 PATH に『.』を書かなければ安全」というわけではありません。
「.」 以外にも、意図せずPATHに追加すると脆弱性を生み出してしまうアンチパターンがあります。
代表的な2つの事例を紹介します。

### 4\.1\. 空文字や「:（コロン）」の連続
PATHを書き換える際、以下のような設定をしてしまうケースがあります。

例１：コロン（:）が連続している（::）

```Bash
# ❌絶対にやってはいけない設定例
export PATH=/usr/bin::/bin
```

例２：先頭または末尾がコロン（:）で始まっている / 終わっている

```Bash
# ❌絶対にやってはいけない設定例（末尾にコロンがある）
export PATH=/usr/bin:/bin:
```

一見すると、単なるタイポや区切り文字のミス（あるいは空文字の混入）に見えるかもしれません。
しかし、LinuxやUNIX系OSで広く採用されているPOSIX（IEEE Std 1003.1）では、以下のようなルールが定められています。

POSIX規格の仕様：
PATH の文字列中において、「空のディレクトリ名（長さゼロの文字列）」は、現在のカレントディレクトリ（.）を指すものとみなす。

つまり、連続したコロン（::）、先頭のコロン（:...）、末尾のコロン（...:）は、すべて内部的に「.」が指定されたものとして処理されます。
明示的に「.」と書いていなくても、コロンの打ち間違いや、シェルスクリプトの変数展開によって「見えない .」が PATH に混入し、前章までで解説した脆弱性が発生してしまうのです。

### 4\.2\. 誰でも書き込めるディレクトリをそのままPATHに含める危険性

「.」を PATH に入れないようにしたとしても、「誰でも書き込める（Writable）ディレクトリ」そのものを PATH に追加してしまっては、全く意味がありません。

例として、以下のような設定が挙げられます。

```Bash
# ❌絶対にやってはいけない設定例
export PATH=$PATH:/tmp
```

もし /tmp そのものが PATH に登録されてしまうと、ユーザーが今どこのディレクトリで作業していようが関係ありません。
システムはコマンドを探す際、常に /tmp ディレクトリの中身を見に行ってしまいます。

攻撃者からすれば、わざわざユーザーが罠のディレクトリに来るのを待つ必要すらありません。
PATHに/tmpが含まれている環境では、攻撃者は/tmp/lss（ls のタイポを狙ったもの）などを配置するだけで、システム全体の誰かがタイポした瞬間に、いつでも、どこからでも権限昇格攻撃を成功させることができてしまいます。

## 5\. 何が問題なのか？ 〜セキュリティの基本原則から考える本質〜

前述した問題は、一見すると「タイポしなければ大丈夫」「怪しいディレクトリでコマンドを打たなければいい」と思えるかもしれません。
しかし、環境変数PATHに「.」を含めることの本質的な問題は、単に「騙される可能性がある」という点に留まりません。

セキュリティの基本原則や設計思想の観点から、何が致命的なのかを3つのポイントで解説します。

### 5\.1\. 予測不可能性（状態への依存）
安全なシステムの鉄則は、「誰が・いつ・どこで実行しても、同じコマンドは常に同じ挙動をする（予測可能である）こと」です。

PATHに「.」が入っていると、「今どのディレクトリにいるか」という「状態」によって、実行されるプログラムが動的に変わってしまいます。

そのため、/bin/ls を実行したつもりが、滞在するディレクトリによってはカレントディレクトリ内の悪意のあるプログラムが動く、という予期せぬ挙動が発生します。

このように、システムの挙動にカレントディレクトリという実行時の状態を入り込ませること（予測不可能性）自体が、堅牢なシステム運用におけるアンチパターンです。


### 5.2. 信頼境界（Trust Boundary）の破壊

セキュリティでは、「信頼できるもの」と「信頼できないもの」の境界（Trust Boundary）を明確にし、その境界を不用意に越えないことが重要な設計原則とされています。

通常、PATHには /usr/bin や /bin のように、システム管理者が管理する信頼できるディレクトリが登録されています。システムは、それらのディレクトリに配置された実行ファイルを信頼して探索・実行することを前提に設計されています。

しかし、環境変数PATHにカレントディレクトリ（.）や、誰でも書き込めるディレクトリ（/tmp など）を含めると、この前提が崩れます。本来は信頼すべきではない場所に置かれた実行ファイルまで、システムが自動的な探索対象として扱うようになってしまうためです。

特に共有ディレクトリでは、他のユーザーが自由に実行ファイルを配置できます。そのような場所をPATHに含めることは、「信頼できない領域」と「信頼できる領域」の境界を曖昧にし、攻撃者が配置したプログラムまで自動的な探索対象となり、誤って実行してしまうリスクを高めます。

さらに、これがrootユーザーの環境で発生した場合、信頼できない実行ファイルが管理者権限で実行される可能性があり、システム全体の制御を奪われる重大なインシデントにつながるおそれがあります。

このように、PATHへ不用意に.や共有ディレクトリを追加することは、信頼境界を破壊し、システムが本来信頼すべきではない実行ファイルまで探索対象として扱ってしまう状態を作り出すという点で、セキュリティ設計上のアンチパターンとされています。

### 5\.3\. 意図しないコード実行（ACE）の脆弱性

セキュリティの世界には、「任意コード実行（ACE: Arbitrary Code Execution）」という概念があります。
ACEは、攻撃者が用意した任意のコードが実行されてしまう状態や、そのような攻撃が成立することを指します。

PATHに「.」を追加することは、攻撃者が用意したプログラムを意図せず実行してしまう原因となり、任意コード実行（ACE）につながるリスクがあります。


## 6\. 対策

環境変数 PATH に「.」や不適切なパスを含めることが、セキュリティリスクになることを見てきました。
では、それらのセキュリティリスクを回避するために、どのようにシステムを構築・運用すべきなのでしょうか。

3つの具体的な対策を解説します。

### 6\.1\. 「.」や空文字（不必要なコロン）をPATH に混入させない

最もシンプルな対策は、「.」や空文字（不必要なコロン）をPATHに混入させないことです。

まずは、自分の環境が安全かどうか、以下のコマンドを実行してください。

```Bash
echo $PATH
```

次に、出力された文字列を見て、以下の状態になっていないかを確認してください。

1. 文字列の先頭や末尾に「.」が含まれていないか
2. コロンが連続（::）していないか
3. 文字列の先頭や末尾がコロン（:）で始まったり終わったりしていないか

目視確認では見落としが起きますので、正規表現によるチェックを行うことが推奨されます。
ワンライナー（1行コマンド）で確認を行うには、以下のコマンドを実行します。

```Bash
echo "$PATH" | grep -qE '(^|:)\.(:|$)|::|^:|:$' && echo "⚠️ 警告: 脆弱なPATHが検出されました" || echo "✅ PATHは安全です"
```

これらのコマンドを「.bashrc」や「.profile」に関数として組み込むと、ログイン時に自動チェックが可能です。

もしアンチパターンの記述が含まれていた場合は、自身の .bashrc や .bash_profile、 /etc/profile などの設定ファイルを見直してください。

### 6\.2\. 構成管理ツール等によるチェック（自動化）

個人環境であれば手動のチェックで事足りますが、実務の現場で何十台、何百台ものサーバーを管理する場合、人間の手で一つずつ確認するのは困難です。
設定ミスや一時的な書き換えを見落とすリスクもあります。

そのため、実務ではAnsibleなどの構成管理ツールやCI/CDパイプラインにPATHの検査処理を組み込み、設定ファイルの監視を自動化するのが一般的です。

### 6\.3\. カレントディレクトリのファイルは ./ をつけて実行する

「.」を PATH から削除したら、自作プログラムをカレントディレクトリで実行できなくて不便に思うかもしれません。

ここで登場するのが、Linuxにおける「正しい作法」です。

カレントディレクトリにある「myscript.sh」を実行したいときは、単に `myscript.sh` と打つのではなく、必ずパスを明示して ./（ドット・スラッシュ） を頭に付けて実行します。

```Bash
# ❌ PATHに頼った危険・不適切な実行方法
myscript.sh

# ⭕ パスを明示する、安全で正しい実行方法
./myscript.sh
```

「./myscript.sh」という記述は、「環境変数 PATH からコマンドを探す」という命令ではなく、「『今いる場所（.）』の直下にある『myscript.sh』というファイルを直接ピンポイントで実行する」という明確な指定（相対パスによる直接指定）になります。

PATHによる探索を行わず、指定したファイルを直接実行するため、PATHハイジャックを防止できます。

## まとめ

- PATHハイジャック：PATHに不適切な探索パス（.や書き込み可能ディレクトリなど）が含まれると発生する攻撃。先頭の.では標準コマンドが乗っ取られ、末尾でもタイポをきっかけに悪意あるプログラムが実行される可能性がある。

- 共有ディレクトリを悪用した権限昇格: /tmp などの全ユーザーが書き込めるディレクトリでrootユーザーがコマンドを実行した際、システム全体の掌握（バックドア設置等）を許す致命的なインシデントに発展する。

- POSIX規格における「見えないドット」の罠: 連続するコロン（::）や、先頭・末尾のコロン（:）は、POSIX規格により内部的にカレントディレクトリ（.）として処理されるため、設定ミス自体が脆弱性となる。

- 堅牢化のための原則: PATH内から不要なドットや空文字を排除し、カレントディレクトリの資産を実行する際は必ず ./script.sh のように相対パスを明示する作法を徹底する。実務においては、これらのチェックをAnsibleやCI/CDで自動化することが望ましい。
